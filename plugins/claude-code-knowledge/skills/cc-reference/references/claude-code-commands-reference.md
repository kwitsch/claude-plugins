# Claude Code Commands — Authoring Reference

> Harness-optimized knowledge file. Directives, not prose. Sources: Anthropic official docs
> (commands reference + skills/slash-commands authoring), verified: 2026-08-18.
> Apply when authoring, reviewing, or invoking slash commands or custom skills/commands.

## What a slash command is / when vs a skill

- A slash command is any entry callable as `/name` from the Claude Code prompt or SDK.
- Two source formats produce slash commands:
  - **Skills** (`<dir>/SKILL.md`) — recommended. Supports bundled files, full frontmatter, autonomous + user invocation.
  - **Commands** (`<dir>/<name>.md`) — legacy flat file. Same frontmatter subset; no bundled-file support. Use skills for new work.
- If a skill and a command share the same name, the skill takes precedence.
- Built-in commands are coded into the CLI and cannot be replaced by user files. **Bundled skills can** be replaced: a skill of the same name at any level overrides the bundled one (e.g. a project `.claude/skills/code-review/` replaces `/code-review`).
- Choose a skill/command over a CLAUDE.md entry when the content is a _procedure_ the user or model invokes on demand, not an always-on fact or convention.

## Locations & precedence

Skills and commands are resolved in this order (highest → lowest precedence):

| Level                | Skills path                        | Commands path (legacy)         | Scope                   |
| -------------------- | ---------------------------------- | ------------------------------ | ----------------------- |
| Enterprise (managed) | See managed settings docs          | —                              | All org users           |
| Personal             | `~/.claude/skills/<name>/SKILL.md` | `~/.claude/commands/<name>.md` | All your projects       |
| Project              | `.claude/skills/<name>/SKILL.md`   | `.claude/commands/<name>.md`   | This project only       |
| Plugin               | `<plugin>/skills/<name>/SKILL.md`  | —                              | Where plugin is enabled |

- Enterprise overrides personal; personal overrides project. A same-named skill at any of these levels also overrides a bundled skill. Exception: a custom skill overrides only the bundled skill's primary command name, not its aliases (e.g. a project `code-review` skill replaces `/code-review` but the bundled alias `/review` still runs the bundled one).
- Plugin skills use a `plugin-name:skill-name` namespace — cannot conflict with other levels.
- Skills also load from `.claude/skills/` in every parent directory up to repo root (monorepo support).
- Nested `.claude/skills/` under a subdirectory load on demand when Claude accesses files there.
- `--add-dir` / `/add-dir` directories: `.claude/skills/` and `.claude/agents/` inside them are loaded automatically (exception to the general rule that `--add-dir` is file-access only, not config discovery). The `agents/` folder is NOT watched — after adding/editing an agent file there, restart the session.
- `permissions.additionalDirectories` in `settings.json` grants file access only — does NOT load skills.
- A skill folder with a `.claude-plugin/plugin.json` loads as a skills-directory plugin named `<name>@skills-dir` — it can then bundle `agents/`, `hooks/`, and MCP servers. In a project's `.claude/skills/`, this requires accepting the workspace trust dialog first.
- A `<skill-name>` entry can be a symlink to a directory elsewhere on disk; Claude Code follows it and reads `SKILL.md` from the target, loading the skill once even if the same target is reachable from more than one location. Plugin skills handle symlinks differently (see plugins-reference).
- `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` env var loads `CLAUDE.md` from `--add-dir` directories (not loaded by default).
- Cowork and cloud sessions (including routines) do NOT read `~/.claude/skills/` on your machine — they load the skills enabled for your claude.ai account, synced at session start. Cloud sessions additionally load project skills committed to the cloned repo's `.claude/skills/`, or shipped in a plugin declared in the repo's `.claude/settings.json` (plugins enabled only in user settings do not transfer). A personal-only skill invoked by a routine reports not-found.
- Desktop scheduled tasks run locally and load skills from the same locations as any other local session.

### Synced skills (claude.ai account)

- Skills enabled for your claude.ai account download into `~/.claude/skills/synced/` only during a non-interactive run with `CLAUDE_CODE_SYNC_SKILLS=1` (e.g. `CLAUDE_CODE_SYNC_SKILLS=1 claude -p "..."`); an interactive session then loads the already-downloaded copies. Re-run the sync command after changing skills on claude.ai. `CLAUDE_CODE_SYNC_SKILLS_WAIT_TIMEOUT_MS` tunes how long the run waits for the sync before answering its prompt.
- `synced` is a reserved folder name (any capitalization) at the enterprise, personal, and project skill levels — a folder you author with that name never loads as a skill. `v2.1.227+`; before this a folder named `synced` loaded as a skill.
- A skill/command from any local source (any level above, a plugin, or `.claude/commands/`) overrides a synced skill of the same name; so does an MCP prompt. Claude Code also reserves every built-in command and bundled-skill name against synced skills, even a bundled skill currently turned off (e.g. via `disableBundledSkills`).
- Name matching for the rule above ignores case, spacing, and invisible characters, and normalizes compatibility forms (fullwidth letters, dash variants); a look-alike letter from a different alphabet counts as a different name. `/skills`, `/context`, and the `/` menu label synced skills `claude.ai sync` so you can tell those apart.
- Frontmatter: a synced skill's `allowed-tools` is honored through the normal permission flow in every session type. Display text (e.g. `description`) is sanitized — control characters removed, angle brackets escaped so it can't imitate Claude Code's own formatting.
- Body behavior by session type: cloud session → behaves like a local skill (isolated container). Cowork desktop session → same as local, except every `!` command line is replaced with the `disableSkillShellExecution` placeholder (see Dynamic context). Any other local session → `!` commands don't run, `@` file references aren't attached, and `${CLAUDE_PROJECT_DIR}`/`${CLAUDE_SESSION_ID}` aren't substituted — all reach Claude as literal text.

## Frontmatter reference

All fields optional; only `description` recommended. YAML between `---` markers at top of `SKILL.md` (or legacy `.md` command file).

`v2.1.218+`: boolean fields also accept `yes`, `no`, `on`, `off`, `1`, `0` in any letter case; earlier only `true`/`false` were recognized.

| Field                      | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                     | Display label in listings. Defaults to directory name. In a personal or project skill it **does NOT set the `/command` name** (the directory or `.claude/commands/` file name does). In a plugin skill it sets the command's last segment, with the `<plugin>:` prefix retained. See Namespacing & invocation. **Ignored in `.claude/commands/` files** — only directory/filename drives the command name there.                                                              |
| `description`              | What it does and when to use it. Claude uses this to decide when to apply. Falls back to first markdown paragraph if omitted. Put key use case first; combined with `when_to_use`, truncated at **1,536 chars** in the listing.                                                                                                                                                                                                                                               |
| `when_to_use`              | Extra trigger context / example phrases. Appended to `description` in listings; counts toward 1,536-char cap.                                                                                                                                                                                                                                                                                                                                                                 |
| `argument-hint`            | Autocomplete hint string, e.g. `[issue-number]` or `[filename] [format]`.                                                                                                                                                                                                                                                                                                                                                                                                     |
| `arguments`                | Named positional args for `$name` substitution. Space-separated string or YAML list; names map to positions in order.                                                                                                                                                                                                                                                                                                                                                         |
| `disable-model-invocation` | `true` → only the user can invoke (`/name`); removes description from Claude's context; blocks preload into subagents; blocks running as a scheduled task's prompt (v2.1.196+). Default: `false`.                                                                                                                                                                                                                                                                             |
| `user-invocable`           | `false` → hidden from `/` menu; Claude-only background knowledge. Default: `true`.                                                                                                                                                                                                                                                                                                                                                                                            |
| `allowed-tools`            | Pre-approve tools (no per-use prompt) for the turn that invokes the skill; the grant clears when you send your next message and re-applies on the next invocation. Space/comma string or YAML list. Does NOT restrict other tools; baseline permission settings still apply. Workspace trust does NOT gate this field — a project skill's `allowed-tools` applies even in an untrusted `-p` run; review `allowed-tools` of skills in a repo before running Claude Code there. |
| `disallowed-tools`         | Remove tools from pool while skill is active. Clears on next user message. Space/comma string or YAML list. Use for autonomous skills that must never call a tool (e.g. `AskUserQuestion` in a background loop). Like deny rules, cannot remove `EndConversation` while any other tool remains.                                                                                                                                                                               |
| `model`                    | Override model for the current turn while skill is active. Not saved; session model resumes on next prompt. Accepts same values as `/model`, or `inherit`. A value excluded by the org's `availableModels` allowlist is skipped — session keeps its current model. With `context: fork`, sets the forked subagent's model instead; an excluded value follows the same rules as a subagent model override.                                                                     |
| `effort`                   | Override effort level while skill is active. Options: `low`, `medium`, `high`, `xhigh`, `max`. Available levels depend on model.                                                                                                                                                                                                                                                                                                                                              |
| `context`                  | `fork` → run in an isolated subagent (no conversation history). Runs in the background by default — see the fork note below.                                                                                                                                                                                                                                                                                                                                                  |
| `agent`                    | Subagent type when `context: fork`. Options: `Explore`, `Plan`, `general-purpose`, or any custom agent. Default: `general-purpose`.                                                                                                                                                                                                                                                                                                                                           |
| `background`               | Only with `context: fork`. `false` → wait for the forked subagent's result in the invoking turn instead of running it in the background. Default: `true`. Requires v2.1.218+.                                                                                                                                                                                                                                                                                                 |
| `hooks`                    | Hooks registered when the skill is invoked and kept active for the rest of the session. See hooks reference for configuration shape; includes an `once` option to register a hook only on the first invocation.                                                                                                                                                                                                                                                               |
| `paths`                    | Glob patterns; auto-activate only when matching files are in context. Comma string or YAML list. **Ignored in `.claude/commands/` files.**                                                                                                                                                                                                                                                                                                                                    |
| `shell`                    | `bash` (default) or `powershell` for `!` injection. `powershell` needs the PowerShell tool enabled — on by default on Windows without Git Bash, elsewhere via `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`.                                                                                                                                                                                                                                                                            |
| `metadata`                 | Free-form YAML map for your own key-value data (e.g. entitlement/catalog fields read by external tooling). Claude Code does not act on it and drops a value that isn't a map. Don't reuse another frontmatter field name (e.g. `paths`) as a key.                                                                                                                                                                                                                             |
| `license`                  | License covering the skill. Part of the Agent Skills spec; Claude Code accepts the field but doesn't act on it.                                                                                                                                                                                                                                                                                                                                                               |
| `compatibility`            | Environment requirements string (product/system prerequisites), up to 500 chars, per the Agent Skills spec. Claude Code accepts the field but doesn't act on it.                                                                                                                                                                                                                                                                                                              |

Note: `allowed-tools` is CLI-only. In the Agent SDK, control access via `allowedTools` + `permissionMode: "dontAsk"` on `ClaudeAgentOptions`.

Note: outside Claude Code (claude.ai skill uploads, the Skills API, `package_skill.py` from anthropics/skills), only 6 [Agent Skills](https://agentskills.io) spec fields are allowed: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Any other field (e.g. `argument-hint`) fails packaging/upload with a hard error (`Unexpected key(s) in SKILL.md frontmatter: ...`). Every field in this table works in Claude Code itself, at every skill level including plugin skills.

Note: `context: fork` with `agent: Explore` or `agent: Plan` — those two built-in agents skip loading `CLAUDE.md`/git status, so the forked skill sees only the `SKILL.md` content plus the agent's own system prompt (no project memory).

Note: a `context: fork` skill runs in the background — you keep working and its result arrives when it finishes. Claude Code waits for the result regardless of `background` when: running non-interactively (`-p`) or via the Agent SDK; `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`; a second invocation starts while an earlier one of the same skill is still running; a scheduled task fires with the skill as its prompt. A backgrounded fork also gets the narrower background-subagent tool set (`v2.1.218+`) — set `background: false` when a step needs a tool outside it. Background-fork edits land outside session checkpoints, so `/rewind` does not undo them; revert with git. Before v2.1.218 a forked skill always blocked the invoking turn.

Note: `context: fork` requires an actionable task. A skill holding only guidelines ("use these API conventions") gives the subagent no prompt and returns nothing useful.

Note: malformed frontmatter YAML → the body still loads with empty metadata, so `/name` works but Claude has no `description` to match on. Run with `--debug` to see the parse error.

## Arguments ($ARGUMENTS, $1..$N, named args)

Available string substitutions in skill/command body:

| Variable                | Description                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `$ARGUMENTS`            | All arguments passed at invocation, as the full string typed. If absent from content, arguments are appended as `ARGUMENTS: <value>`.                                                                                                                                                                                                                                               |
| `$ARGUMENTS[N]`         | Specific argument by 0-based index. Example: `$ARGUMENTS[0]` = first arg.                                                                                                                                                                                                                                                                                                           |
| `$N`                    | Shorthand for `$ARGUMENTS[N]`. Example: `$0` = first arg, `$1` = second arg.                                                                                                                                                                                                                                                                                                        |
| `$name`                 | Named argument defined via the `arguments` frontmatter field. Name maps to a position by declaration order.                                                                                                                                                                                                                                                                         |
| `${CLAUDE_SESSION_ID}`  | Current session ID. For logging, session-specific files, correlating output with sessions.                                                                                                                                                                                                                                                                                          |
| `${CLAUDE_EFFORT}`      | Current effort level: `low`, `medium`, `high`, `xhigh`, `max`. Ultracode reports as `xhigh` (not a distinct level).                                                                                                                                                                                                                                                                 |
| `${CLAUDE_SKILL_DIR}`   | Directory containing the skill's `SKILL.md`. For plugin skills, the skill's subdir within the plugin (NOT plugin root). Use in `!` bash injection to reference bundled scripts regardless of cwd. Substituted both in the body and in `allowed-tools` Bash rules — the latter requires v2.1.129+ (earlier it stays a literal string, never matches, and the command still prompts). |
| `${CLAUDE_PROJECT_DIR}` | Project root directory — same path hooks/MCP servers receive as `CLAUDE_PROJECT_DIR`. Use for project-local scripts independent of skill install location. Applies in both the skill body and `allowed-tools` (e.g. `Bash(${CLAUDE_PROJECT_DIR}/scripts/lint.sh *)`). Requires v2.1.196+.                                                                                           |
| `${CLAUDE_PLUGIN_ROOT}` | Plugin's installation directory. Substituted only in plugin skills. Use for scripts/files bundled anywhere in the plugin, including resources shared between the plugin's skills.                                                                                                                                                                                                   |
| `${CLAUDE_PLUGIN_DATA}` | Plugin's persistent data directory (survives plugin updates). Substituted only in plugin skills. Use for installed dependencies, generated files, or caches that must outlive an update.                                                                                                                                                                                            |

- Indexed args use shell-style quoting: wrap multi-word values in quotes to pass as one arg. `/my-skill "hello world" second` → `$0`=`hello world`, `$1`=`second`. `$ARGUMENTS` always expands to the full string as typed.
- An indexed placeholder with no matching argument (`$2` when only one arg was passed) stays in the content unchanged. A named placeholder from `arguments` with no matching argument expands to an empty string.
- Escape a literal `$` before a digit / `ARGUMENTS` / declared arg name with one backslash: `\$1.00`. A backslash before any other `$` is left unchanged. Only a single backslash directly before the token escapes; `\\$1` leaves both backslashes and still expands `$1`. A backslash does NOT prevent substitution of `${CLAUDE_*}` variables; the escape rule covers only argument placeholders.

Example frontmatter + usage:

```yaml
---
arguments: component source target
---
Migrate $component from $source to $target.
```

Invocation `/migrate-component SearchBar React Vue` → `$component`=`SearchBar`, `$source`=`React`, `$target`=`Vue`.

### Stacking multiple skills in one message

- A command is only recognized at the start of a message; trailing text becomes its arguments. A command sent while Claude is responding queues until the turn finishes — `/status`, `/tasks`, and `/usage` run immediately instead.
- `v2.1.199+`: typing several inline user-invocable skills at the start of one message, e.g. `/skill-a /skill-b do XYZ`, loads every named skill and passes the trailing text to each as `$ARGUMENTS`. Up to 6 skills can be chained (first + 5 more stacked after it).
- Expansion stops at the first token that is not an inline user-invocable skill (e.g. a `context: fork` skill such as `/code-review` from `v2.1.218+`, or one whose own arguments may start with `/`, like `/loop`) — that token and everything after it becomes the argument text for every expanded skill. Before v2.1.218 `/code-review` ran inline and stacked.
- Before v2.1.199, only the first skill loaded; the rest was passed to it as literal argument text.

## Dynamic context (!`bash` injection, @file references)

### Inline shell injection

- Syntax: `` !`<command>` `` — runs shell command at skill load time; output replaces the placeholder before Claude sees anything.
- `!` must appear at line start or immediately after whitespace. `` KEY=!`cmd` `` is NOT expanded (left as literal text).
- Output is plain text; not re-scanned for further `` !`...` `` placeholders.
- Multi-line variant: fenced block opened with ` ```! `:

````markdown
## Environment

```!
node --version
git status --short
```
````

- Disable repo-wide with `"disableSkillShellExecution": true` in `settings.json`. Each command replaced with `[shell command execution disabled by policy]`. Bundled and managed skills are not affected.
- Use `ultrathink` anywhere in skill content to request deeper reasoning when the skill runs.

### Injected command execution & failure semantics

- Tool selection: `shell: powershell` with the PowerShell tool enabled → runs through the PowerShell tool. `shell: bash` when bash is unavailable (Windows without Git Bash) → the invocation fails outright (`Skill <name> requires bash ... but Git Bash was not found`). Any other combination → Bash tool when bash is available, else PowerShell tool.
- Working directory follows the session shell's cwd (moves when Claude runs `cd`) — use `${CLAUDE_SKILL_DIR}`/`${CLAUDE_PROJECT_DIR}` for paths that must resolve the same way every time.
- Default `bash` shell merges stderr into stdout (appears in the injected text). Each command runs under the Bash tool's default 2-minute timeout: a command the Bash tool would auto-background still lets the skill render (injected text reports the move + names the background task/output file); a command that isn't auto-backgroundable is killed at timeout, which aborts the invocation. Output past the Bash tool's inline ceiling arrives as a file path + short preview, not truncated text.
- Any non-zero exit code aborts the whole invocation — Claude never sees the skill content for that invocation (`Shell command failed for pattern "..."`, with the command's output under `[stderr]`). One carveout: exit code 1 from a search/comparison command is treated as a normal result (bash: the commands under Output limits; `shell: powershell`: a different set including `grep`/`git diff` but not `find`/`diff`). Append `|| true` to any other command expected to exit non-zero (e.g. a check script that exits 1 on problems found).
- A permission check that doesn't resolve to allow — including a rule that would normally ask — also aborts the invocation (`Shell command permission check failed for pattern "..."`), regardless of `allowed-tools`; pre-approve with `allowed-tools` to avoid the ask-prompt abort, but a matching deny rule still aborts either way.

### Supporting files (@file references)

- A skill directory can include supporting files (templates, examples, scripts, reference docs) alongside `SKILL.md`.
- Reference them from `SKILL.md` so Claude knows they exist and when to load them.
- Bundled files incur zero context cost until accessed — reference at need, not upfront.
- Supported structure example:

```
my-skill/
├── SKILL.md           # Required entry point
├── template.md        # Template for Claude to fill in
├── examples/
│   └── sample.md
└── scripts/
    └── validate.sh
```

- Legacy `.claude/commands/<name>.md` files do NOT support bundled supporting files.
- Keep `SKILL.md` under 500 lines; move detailed reference material into supporting files.

## Namespacing & invocation

### Invocation forms

| Source                                               | Command name                       | Example                |
| ---------------------------------------------------- | ---------------------------------- | ---------------------- |
| `.claude/skills/<name>/SKILL.md`                     | `/<name>`                          | `/deploy-staging`      |
| `~/.claude/skills/<name>/SKILL.md`                   | `/<name>`                          | `/my-util`             |
| `.claude/commands/<name>.md`                         | `/<name>`                          | `/deploy`              |
| Plugin `skills/<dir>/SKILL.md` (no `name:`)          | `/<plugin-name>:<dir>`             | `/my-plugin:review`    |
| Plugin `skills/<dir>/SKILL.md` (`name: fancy`)       | `/<plugin-name>:fancy`             | `/my-plugin:fancy`     |
| Plugin root `SKILL.md` (with `name:` in frontmatter) | `/<plugin-name>:<name>`            | `/my-plugin:review`    |
| Plugin root `SKILL.md` (no `name:` frontmatter)      | `/<plugin-name>:<plugin-dir-name>` | `/my-plugin:my-plugin` |

- Plugin namespace (`plugin-name:skill-name`) prevents conflicts with personal/project skills.
- In a personal or project skill, `name` is a display label only — the directory (or `.claude/commands/` file) name drives the command.
- In a plugin skill, `name` replaces the command's **last segment** and the `<plugin>:` prefix is retained (`v2.1.216+`); the bare `/fancy` also invokes it unless another command already owns that name. Before v2.1.216 `name` replaced the whole command name, so the menu showed the bare `/fancy` and `/my-plugin:fancy` did not autocomplete.
- For a plugin-root `SKILL.md` there is no skill directory to take a name from, so `name` supplies the whole final segment; without it, the plugin's directory name is the fallback.

### Subdirectory organization

- Skills in `.claude/skills/<subdir>/<name>/SKILL.md` are invoked as `/<name>` (subdirectory is not part of the command name).
- On a name collision with another skill, the nested one is exposed under a directory-qualified name instead — the subdirectory path relative to the working directory, then the skill name (e.g. a root `deploy` skill plus `apps/web/.claude/skills/deploy/SKILL.md` → the nested one becomes `/apps/web:deploy`). Both stay invocable; Claude picks the variant matching the files it's working on.
- `v2.1.203+`: invoking the unqualified name still loads the project-root skill, but its content gets the list of directory-qualified variants appended, with an instruction to also invoke any variant whose directory holds the files in use — so the nested variant still applies even when only the unqualified name is invoked.
- Within a plugin, `skills/<subdir>/<name>/SKILL.md` → `/<plugin>:<name>`.

### MCP-exposed prompts

- MCP servers can expose prompts that appear as commands: `/mcp__<server>__<prompt>`, dynamically discovered from connected servers.

### SDK: discovering available commands

At session init, the `system`/`SystemMessage` event with `subtype: "init"` carries a `slash_commands` array listing all available commands (built-in + custom):

```typescript
// TypeScript
if (message.type === "system" && message.subtype === "init") {
  console.log(message.slash_commands);
  // e.g. ["clear", "compact", "context", "usage", "refactor"]
}
```

```python
# Python
if isinstance(message, SystemMessage) and message.subtype == "init":
    print(message.data["slash_commands"])
```

## Invocation control & permissions

### Who invokes (frontmatter)

| Frontmatter                      | You invoke | Claude auto-invoke | When loaded into context                                     |
| -------------------------------- | ---------- | ------------------ | ------------------------------------------------------------ |
| (default)                        | Yes        | Yes                | Description always in context; full skill loads when invoked |
| `disable-model-invocation: true` | Yes        | No                 | Description NOT in context; full skill loads when you invoke |
| `user-invocable: false`          | No         | Yes                | Description always in context; full skill loads when invoked |

- `user-invocable: false` controls `/` menu visibility only — NOT Skill tool access. Use `disable-model-invocation: true` to block programmatic (Claude/subagent) invocation.

### Skill(...) permission rules

- Deny the bare `Skill` tool in `/permissions` to disable all skills.
- `Skill(name)` — exact-match allow/deny. `Skill(name *)` — prefix match with any arguments.
- Permission settings still govern baseline approval; `allowed-tools` does not restrict, only pre-approves.

### skillOverrides setting

Controls skill visibility from `settings` instead of the skill's own frontmatter (for skills you don't want to edit). `/skills` menu writes it to `.claude/settings.local.json` (Space cycles states, Enter saves). Each key = skill name; value is one of:

| Value                   | Listed to Claude   | In `/` menu |
| ----------------------- | ------------------ | ----------- |
| `"on"`                  | Name + description | Yes         |
| `"name-only"`           | Name only          | Yes         |
| `"user-invocable-only"` | Hidden             | Yes         |
| `"off"`                 | Hidden             | Hidden      |

Absent from `skillOverrides` = treated as `"on"`. Plugin skills are NOT affected by `skillOverrides` — manage via `/plugin`. The `/skills` menu labels the `"user-invocable-only"` state `user-only`.

`v2.1.199+`: `"off"` also hides the skill from command lists advertised to Remote Control clients and Agent SDK callers, not only the terminal `/` menu. Invoking a hidden skill by its full name still returns the `skillOverrides` error instead of running it.

## Skill content lifecycle & compaction

- An invoked skill's rendered `SKILL.md` enters the conversation as a single message and stays for the rest of the session. Claude Code does NOT re-read the file on later turns — write standing instructions, not one-time steps.
- Persistence covers instructions only, not permissions: an `allowed-tools` grant clears on your next message even though the content stays.
- Keep the body concise — loaded content is a recurring per-turn token cost. State what to do, not how or why.
- Re-invoking a skill whose rendered content is byte-identical to the copy already in context adds a short "already loaded" note instead of duplicating it. If the render differs (args changed, or a `!` dynamic-context command produced new output), the full content is appended again. Before v2.1.202, every re-invocation appended a full copy regardless.
- Auto-compaction carries invoked skills forward within a token budget: after summary, re-attaches the most recent invocation of each skill, keeping the first **5,000 tokens** of each. Re-attached skills share a combined **25,000-token** budget, filled most-recently-invoked first — older skills can be dropped entirely if many were invoked in one session.
- If a large skill or many later skills push it out, re-invoke after compaction to restore full content.
- A skill that appears to stop influencing behavior after the first response is usually still in context — the model is choosing other tools. Strengthen `description` + instructions, or enforce deterministically with hooks.
- Listing budget: every skill name is always listed, but when combined descriptions overflow the budget (default 1% of the model's context window) Claude Code drops descriptions starting with the least-invoked skills. `/doctor` estimates the listing's cost and biggest contributors; overflow is also written to the debug log (`--debug`).
- In a regular session, skill descriptions load into context but full content loads only on invoke. Subagents with preloaded skills differ: full content is injected at startup; `disable-model-invocation: true` blocks that preload.

### Live change detection

- Adding/editing/removing a skill under a _watched_ dir (`~/.claude/skills/`, project `.claude/skills/`, or a `.claude/skills/` inside an `--add-dir` dir) takes effect mid-session without restart. Live detection covers `SKILL.md` **text** only.
- Creating a top-level skills dir that did NOT exist at session start requires restarting Claude Code so it can be watched.
- For a skill folder that is also a plugin, changes to `hooks/`, `.mcp.json`, `agents/`, and `output-styles/` need `/reload-plugins` to take effect (not live).

## Evaluating a skill (skill-creator)

- A skill triggering only proves Claude found it — measure invocation rate AND output quality separately. Method: baseline comparison — run realistic prompts in fresh sessions with the skill available vs disabled (`skillOverrides: off`), compare.
- The `skill-creator` plugin automates the loop. Install: `/plugin install skill-creator@claude-plugins-official` (if the marketplace is not found, first run `/plugin marketplace add anthropics/claude-plugins-official`), then `/reload-plugins`. Ask e.g. `evaluate my <name> skill with skill-creator`. It produces, inside the skill dir:

| Artifact           | Contents                                                                     |
| ------------------ | ---------------------------------------------------------------------------- |
| `evals/evals.json` | Test cases: prompts, input files, expected behavior                          |
| `grading.json`     | Per-assertion pass/fail with evidence (one subagent per case, clean context) |
| `benchmark.json`   | Aggregated pass rate / time / tokens, with-skill vs without                  |

- Also: blind A/B between two skill versions; description tuning via should-trigger / should-not-trigger prompts; HTML review viewer for qualitative feedback.
