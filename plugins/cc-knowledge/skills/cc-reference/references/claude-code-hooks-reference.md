# Claude Code Hooks — Mechanics Reference

> Harness-optimized knowledge file. Directives, not prose. Source: code.claude.com/docs/en/hooks + code.claude.com/docs/en/hooks-guide, verified 2026-10-09.
> Scope: event catalog, config schema, matchers, I/O, exit codes, decision control, scopes. Out of scope: plugin "mods" (JavaScript function hooks Claude Code calls in-process, can draw UI; separate docs page) — they run alongside the hooks here.
> For choosing a handler `type` (command/.sh/.mjs/binary vs http/mcp_tool/prompt/agent), see **hook-handler-selection.md** — not repeated here.

## Model: three nesting levels

1. **Hook event** — lifecycle point (`PreToolUse`, `Stop`, …).
2. **Matcher group** — `matcher` filter for when it fires.
3. **Hook handler** — the `command`/`http`/`mcp_tool`/`prompt`/`agent` that runs.
   "Hook" alone = the feature. Multiple matched handlers run in parallel; an identical handler defined in more than one settings file runs once (command by command+args, http by url) — a plugin's or skill's copy of the same handler stays separate.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": []
          }
        ]
      }
    ]
  }
}
```

## Hook locations / scope

| Location                      | Scope                                         | Shareable          |
| ----------------------------- | --------------------------------------------- | ------------------ |
| `~/.claude/settings.json`     | all your projects                             | no (local machine) |
| `.claude/settings.json`       | one project                                   | yes (committable)  |
| `.claude/settings.local.json` | one project                                   | no (gitignored)    |
| managed policy settings       | org-wide                                      | yes (admin)        |
| plugin `hooks/hooks.json`     | when plugin enabled                           | yes (bundled)      |
| skill frontmatter             | rest of the session once the skill is invoked | yes (in component) |
| subagent frontmatter          | while that subagent runs                      | yes (in component) |

- Enterprise `allowManagedHooksOnly` blocks user/project/plugin hooks; force-enabled `enabledPlugins` hooks are exempt. Also narrows `statusLine`/`fileSuggestion`/`subagentStatusLine` to managed settings, and disables plugins with a `command` source (incl. force-enabled ones) unless `disableCommandPluginSources` is explicitly `false` (version >= 2.1.229; also gates marketplace `headersHelper` commands the same way, except a marketplace managed settings itself declares).
- File-watcher picks up direct settings edits automatically.
- Plugin `hooks/hooks.json` takes an optional top-level `description` string beside `hooks`.
- Handlers run in the current directory. If it no longer exists (e.g. a deleted worktree/temp dir), Claude Code falls back to the first existing of: session start dir, project root, home dir, system temp dir — logs the fallback in the debug log.
- Settings levels merge, not replace: user/project/local hooks add to managed hooks without removing them; `disableAllHooks` set below the managed level can't disable managed hooks.
- Hooks from settings files, managed policy, and plugins also fire inside subagents — tool events there add `agent_id`+`agent_type` (see Input).

## Matcher semantics

`matcher` evaluation by content:

| Value                                       | Treated as                                                                                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `*`, `""`, omitted                          | match all                                                                                                                                                    |
| only letters/digits/`_`/`-`/spaces/`,`/`\|` | exact string, or list of exacts separated by `\|` or `,` with optional surrounding whitespace (`Edit\|Write`, `Edit, Write`)                                 |
| any other char                              | JavaScript regex, unanchored (`^Notebook`, `mcp__memory__.*`; unanchored means `Edit.*` also matches `NotebookEdit` — use `^Edit$` for a whole-string match) |

- `FileChanged`/`StopFailure` use a narrower exact-match set: letters/digits/`_`/`|` only (no hyphen/space/comma) — a hyphen, space, or comma there keeps the matcher on the regex path, and only `|` separates alternatives for those two events.
- MCP tools appear as `mcp__<server>__<tool>`. To match a whole server you MUST append `.*` (`mcp__memory__.*`) — `mcp__memory` is exact-string and matches nothing. Tools from a plugin-bundled MCP server use a scoped segment `mcp__plugin_<plugin-name>_<server-name>__<tool>` (plugin `my-plugin`, key `db`, tool `query` → `mcp__plugin_my-plugin_db__query`; whole server `mcp__plugin_my-plugin_db__.*`); a matcher written against the bare server key never fires. Use the same scoped name in `if`.
- Windows: the PowerShell tool is the primary shell where enabled, and without Git Bash it is enabled automatically while the Bash tool isn't registered at all → a `Bash`-only matcher never fires there; match `Bash|PowerShell` (and see `if` below: one handler per tool).
- What the matcher filters per event: tool events → `tool_name`; `SessionStart` → `startup|resume|clear|compact|fork` (version >= 2.1.214: `fork`; earlier versions report a forked session as `resume`); `Setup` → `init|maintenance` (which CLI flag fired it); `SubagentStart/Stop` → agent type (`general-purpose`, `Explore`, `Plan`, or custom/plugin-scoped names; a custom subagent's type is its frontmatter `name`, not the filename; a `SubagentStop` from an internal agent carries the session's `--agent`/`agent`-setting name, or `""` when none — a matcher naming agent types doesn't match `""`, while omitted/`""`/`*` or a regex matching the empty string does); `PreCompact/PostCompact` → `manual|auto`; `PreModelSwitch/PostModelSwitch` → canonical name of the target model, derived from `to_model` and ignoring any `[1m]` suffix (an alias, a dated model ID, and a provider-specific ID such as a Bedrock ID all normalize to the same canonical name; when Claude Code can't resolve one, e.g. a custom LLM-gateway model ID, it runs every hook regardless of matcher — check `to_model` in the hook body) — version >= 2.1.251; `SessionEnd` → `clear|resume|logout|prompt_input_exit|other` (`bypass_permissions_disabled` removed in v2.1.234 — drop it from matchers); `Notification` → type (`permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_fired`, `quota_auto_resume_stale`, `quota_auto_resume_disabled` — the last three require version >= 2.1.234; `agent_needs_input`/`agent_completed` require agent-view + version >= 2.1.198, and `agent_needs_input` also covers an agent-team teammate's terminal setup question as of version >= 2.1.248 and, in a terminal session, auto mode's notice about classifier request charges (after ~6s without typing); `agent_completed` fires only while agent view is open in a terminal; `permission_prompt` waits ~6s (each keystroke defers it in a terminal; for a `canUseTool` host it's ~6s from the request, not deferred by typing, and skipped if you or a PermissionRequest hook answer sooner) — use `PermissionRequest` for an immediate signal; `idle_prompt` ~60s after Claude finishes with no typing (not sent while waiting on a usage limit reset); hooks run even with desktop notifications turned off; `permission_prompt` fires in Agent SDK/`canUseTool`-callback sessions as of version >= 2.1.233 (set env `CLAUDE_CODE_DISABLE_PERMISSION_PROMPT_NOTIFY_HOOKS=1` to opt out there), and in terminal sessions also fires for a sandboxed command's network-request prompt as of version >= 2.1.246); `StopFailure` → error type (`rate_limit`, `overloaded`, `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `invalid_request`, `model_not_found`, `server_error`, `max_output_tokens`, `cloud_credential_error` [version >= 2.1.267; earlier versions report credential-load failures as `server_error`/`unknown` instead], `unknown`); `InstructionsLoaded` → load reason; `ConfigChange` → `user_settings|project_settings|local_settings|policy_settings|skills`; `DirectoryAdded` → `slash_command|register_repo_root` (how the directory was added); `UserPromptExpansion` → command name; `Elicitation*` → MCP server.
- `Notification` timing in a terminal: `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog` share one ~6s gate (timer starts when the dialog appears, each keystroke defers it; a request arriving behind another open dialog keeps the gate timed from its own arrival, so its notification can fire while it still waits). `idle_prompt` fires ~60s after Claude finishes only if you haven't typed since AND no background agent (e.g. a background subagent) is still running; while a usage-limit wait is active a `quota_auto_resume_*` type fires instead. `quota_auto_resume_stale` = limit reset while the machine slept >~30 min (waits for `Enter`; a shorter sleep fires `quota_auto_resume_fired`); `quota_auto_resume_disabled` doesn't fire on `Esc`/`Ctrl+C`/"Don't continue automatically". The `preferredNotifChannel` setting (incl. `notifications_disabled`) changes only how you're alerted, not whether hooks run.
- A plugin-scoped agent type (`my-plugin:reviewer`) contains `:` → regex path, not exact-match → anchor it (`^my-plugin:reviewer$`) or it also matches longer names.
- No matcher (silently ignored if set): `UserPromptSubmit`, `PostToolBatch`, `Stop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `WorktreeCreate`, `WorktreeRemove`, `CwdChanged`, `MessageDisplay`.
- `FileChanged` input also carries `event`: `"change"` (modified), `"add"` (created), or `"unlink"` (deleted).

### `if` field (per-handler, tool events only)

- version >= 2.1.85: required (earlier versions ignore `if` and run on every matched call).
- Permission-rule syntax against tool name + args: `Bash(git *)`, `Edit(*.ts)`. Exactly one rule; no `&&`/`||`/list — use separate handlers. A rule matches one tool's calls only, so a `Bash|PowerShell` matcher needs one handler per tool (`Bash(rm *)` and `PowerShell(Remove-Item *)`).
- Directory patterns are single-segment: `Edit(src/**)` matches only `src` in the working directory; use `Edit(**/src/**)` for a `src` at any depth. version >= 2.1.214; earlier versions matched any depth for the single-segment form.
- Only evaluated on `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`; on other events a handler with `if` never runs.
- Bash matching: leading `VAR=val` stripped; each subcommand and `$()`/backtick content checked; patterns more specific than the command name run anyway on `$()`/backtick/`$VAR`. **Fails OPEN on unparseable Bash** → never gate security with `if`; use permission rules.

## Handler types (field tables)

Five `type` values: `command` | `http` | `mcp_tool` | `prompt` | `agent`. **Choice criteria → hook-handler-selection.md.**

Common fields (all types): `type` (req), `if`, `timeout` (defaults: 600s command/http/mcp_tool, 30s prompt, 60s agent; UserPromptSubmit/PreModelSwitch/PostModelSwitch lower command/http/mcp_tool to 30, MessageDisplay to 10; SessionEnd shares a 1.5s budget; `timeout` isn't enforced on an `async:true` command hook, but is on `asyncRewake`), `statusMessage`, `once` (skill-frontmatter only; ignored in settings files/agent frontmatter; removes the hook after its first successful run — a run that fails, blocks with exit 2, or times out leaves it in place).

- `command`: `command` (req), `args` (→ exec form), `async`, `asyncRewake` (bg + wake Claude on exit 2; implies `async`; on exit 2, the hook's stderr — or stdout if stderr is empty — is shown to Claude as a system reminder so it can react to a long-running background failure), `shell` (`bash`|`powershell`; default `bash`, or `powershell` on Windows when Git Bash isn't installed; ignored when `args` is set; no `CLAUDE_CODE_USE_POWERSHELL_TOOL` needed — hooks spawn PowerShell directly), `onFailure` (`"continue"` default | `"block"`; version >= 2.1.295 — see **onFailure** below).
- `http`: `url` (req), `headers` (`$VAR` interp), `allowedEnvVars` (required for any interp; unlisted → empty), `onFailure` (same as `command`). Settings keys `allowedHttpHookUrls` (URL allowlist) and `httpHookAllowedEnvVars` (header-interpolation allowlist) gate every `http` hook from any source, including managed policy, when defined at any settings level.
- `mcp_tool`: `server` (req, must be connected; for a plugin-bundled server use the scoped name `plugin:<plugin-name>:<server-name>`, e.g. `plugin:my-plugin:db`, not the bare key), `tool` (req), `input` (`${path}` substitution from hook JSON, e.g. `"${tool_input.file_path}"`). Result text is read like command stdout (same exit-0 parse rule); `isError: true` → non-blocking error. On events that can block/alter the result (`PreToolUse`, `Stop`) Claude Code waits for a still-connecting server for at most `MCP_TIMEOUT` and within the hook's `timeout`; observational events (`Notification`, `SessionEnd`) don't wait. A `cached`-status server connects when called; never starts an OAuth flow (authenticate via `/mcp` first). Skipped at `SessionStart` launch and on `Setup` (see event catalog).
- `prompt`/`agent`: `prompt` (req; `$ARGUMENTS` = hook input JSON — omit it and the input JSON is appended to the prompt instead; `\$` escapes a literal `$`), `model` (default = the model Claude Code uses for background functionality, the fast model, Haiku), `continueOnBlock` (`prompt` only; default false — see per-event list below). Output contract = JSON `{"ok":true|false,"reason":...}` (NOT exit codes / `decision`). `ok:false` per event: Stop/SubagentStop → `reason` fed back, keeps working; **`impossible:true`** (prompt only) alongside `ok:false` on Stop/SubagentStop signals the condition can never be satisfied — Claude Code allows the stop and the turn ends instead of feeding back; PreToolUse → tool denied, and by default the turn ends with `reason` shown as a chat warning, `continueOnBlock:true` returns `reason` to Claude as the tool error so it can adjust and continue (equivalent to a command hook's `permissionDecision:"deny"`) — version >= 2.1.210; earlier versions used the tool-error-and-continue path as the default; PostToolUse → turn ends + `reason` shown as warning by default, `continueOnBlock:true` feeds `reason` back and continues instead; PostToolBatch/UserPromptSubmit/UserPromptExpansion → turn ends, warning, **regardless of** `continueOnBlock`; PostToolUseFailure/TaskCreated → `reason` returned as tool error + turn continues, regardless of `continueOnBlock`; TaskCompleted → same tool-error-and-continue when a task is marked complete mid-turn, but when it fires because a teammate stops it behaves like TeammateIdle (halts by default); TeammateIdle → stops by default + warning, `continueOnBlock:true` keeps it working instead; PermissionRequest/PermissionDenied → `ok:false` has **no effect** (PermissionDenied's only readable output, `retry`, isn't settable by prompt/agent) — use a `command` hook for these two. `agent` is EXPERIMENTAL (may change; prefer `command` for production); 60s default timeout, up to 50 tool-use turns; agent hooks have no `continueOnBlock` field and don't support `impossible`; on `ok:false` Claude Code handles them as a prompt hook with `continueOnBlock:true` on the same event (so on PreToolUse/PostToolUse the turn continues). An `agent` hook configured on PermissionRequest is skipped — permission flow proceeds unchanged.

### `onFailure` (fail-closed for `command`/`http`)

- version >= 2.1.295. `"onFailure": "block"` on a `command` or `http` hook makes a hook FAILURE block the action; default `"continue"` = failure is a non-blocking error and the action proceeds (a wrong path or crashing script lets everything through).
- Counts as failure: can't start (missing script/executable); command exit code other than 0 or 2 — even when it printed allow-JSON such as `permissionDecision:"allow"` (to return a JSON decision, exit 0); HTTP connection failure or non-2xx; reaching `timeout`; invalid output (JSON that can't be parsed or fails schema validation; for http a 2xx body that is neither empty nor a JSON object). Plain-text stdout from a command hook is NOT a failure.
- With `"block"`, a failure does what exit 2 does on that event (`PreToolUse` blocks the call, `UserPromptSubmit` blocks the prompt, a timed-out `PreToolUse` hook blocks instead of falling through), except `PermissionRequest` → denies the request. Block message contains `failed; blocking because onFailure is "block"` (`timed out` instead of `failed` after a timeout) plus the hook's own error output.
- No effect on: `Stop`, `SubagentStop`, `TaskCompleted`, `TeammateIdle` (exit 2 there sends Claude back to work, and Claude can't repair a hook that won't run); background command hooks (`async`/`asyncRewake`).
- Use it for policy gates written as hooks; `if` still fails OPEN on unparseable Bash and `mcp_tool`/`prompt`/`agent` hooks have no `onFailure`.

### Which events support which handler types

- All 5 types (`command`/`http`/`mcp_tool`/`prompt`/`agent`): `PermissionDenied`, `PostToolBatch`, `PostToolUse`, `PostToolUseFailure`, `PreToolUse`, `Stop`, `SubagentStop`, `TaskCompleted`, `TaskCreated`, `TeammateIdle`, `UserPromptExpansion`, `UserPromptSubmit`.
- `command`/`http`/`mcp_tool`/`prompt` (no `agent` — Claude Code skips an agent hook there): `PermissionRequest`.
- `command`/`http`/`mcp_tool` only (no `prompt`/`agent`): `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `Elicitation`, `ElicitationResult`, `FileChanged`, `InstructionsLoaded`, `MessageDisplay`, `Notification`, `PostCompact`, `PostModelSwitch`, `PreCompact`, `PreModelSwitch`, `SessionEnd`, `StopFailure`, `SubagentStart`, `WorktreeCreate`, `WorktreeRemove`.
- `command`/`mcp_tool` only: `SessionStart`, `Setup`.

### Exec vs shell form (command)

- `args` present → **exec form**: `command` resolved on PATH, spawned directly; each `args` element = one arg, no shell, no quoting; placeholders substituted as plain strings. Use whenever referencing a path placeholder. If `command` is a bare name with no path separator and the full invocation including `args` contains whitespace, Claude Code logs a warning — there is no executable named e.g. `node script.js`; move extra tokens into `args` elements instead.
- `args` absent → **shell form**: `sh -c` (macOS/Linux), Git Bash/PowerShell (Windows); enables pipes, `&&`, globs, var expansion. Quote placeholders.
- Windows: `.cmd`/`.bat` shims aren't executables → use shell form, OR exec via `node` + script path (`node` + path works everywhere).
- Path placeholders (also exported as env vars): `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}` (changes per update), `${CLAUDE_PLUGIN_DATA}` (survives updates). Both forms substitute them. `${CLAUDE_PROJECT_DIR}` (project root where the session started) is also set in the env of stdio MCP servers and plugin LSP servers. After Claude enters a worktree it stays at the session-start root (a script under it still runs from the main checkout), while the input `cwd` follows Claude (worktree root; new dir after `cd`) → read `cwd` to know where Claude works. Prefer exec form for any placeholder; in shell form double-quote each one.
- Plugin hooks also substitute `${user_config.*}`, **exec form only**. A shell-form plugin hook whose `command` references `${user_config.*}` FAILS with an error instead of running → either set `args` (switch to exec form) or read the exported `$CLAUDE_PLUGIN_OPTION_<KEY>` env var (`$CLAUDE_PLUGIN_OPTION_WEBHOOK_URL` for a `webhook_url` option). version >= 2.1.207; earlier versions also substituted it in shell form.
- PowerShell shell-form (`"shell": "powershell"`): write `${CLAUDE_PROJECT_DIR}`/`${CLAUDE_PLUGIN_ROOT}`/`${CLAUDE_PLUGIN_DATA}` — version >= 2.1.198 rewrites them to PowerShell `${env:NAME}` form for settings/plugin/skill hooks alike (works inside double-quoted strings, NOT single-quoted, where PowerShell never expands variables; earlier versions rewrote plugin hooks only, others need `$env:` form or exec form). Never write the bare `$CLAUDE_PROJECT_DIR` spelling in PowerShell — it parses as an undefined local variable (resolves to `$null`); not rewritten, warning only in debug log. Claude Code auto-detects `pwsh.exe`, falling back to `powershell.exe`.

## Exit codes (command)

Claude Code reads JSON output from stdout on **every** exit code, not only exit 0. Exit 2 is the one outcome JSON can't override.

- **0** = success; intended exit when printing JSON for structured control. stdout reaches Claude directly only on `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, `PostModelSwitch` (version >= 2.1.251); elsewhere written to debug log only. Stdout is parsed as JSON only when (ignoring surrounding whitespace) it starts with `{` AND ends with `}`; starts with `{` but doesn't end with `}`, or starts with anything else (a JSON array or quoted string included) → plain text. Two+ lines that each parse as JSON on their own and none sets a field → plain text; if one does set a field the whole output is a parse failure. Valid JSON that fails schema validation → non-blocking error (transcript notice). Stderr on exit 0 → debug log only, Claude never sees it (to warn Claude from `PostToolUse`/`PostToolUseFailure` exit 2 instead). version >= 2.1.248: stdout shaped like JSON (starts `{`, ends `}`) that fails to parse is now ALSO a non-blocking error (parse message), and on the context-injecting events above the text is dropped rather than delivered as plain-text context; earlier versions silently fell back to plain-text delivery there instead.
- **2** = blocking error; always blocks regardless of JSON. stderr becomes the blocking reason (or the JSON decision's reason if present). exit 2 + JSON that fails schema validation still blocks (validation failure goes to debug log only). version >= 2.1.214; earlier treated that as non-blocking. On `Elicitation`/`ElicitationResult`, Claude Code applies `hookSpecificOutput` only on exit 0 and ignores it on any other exit code (an exit-2 hook still blocks/declines). Exception: on `Stop`, `SubagentStop`, `TaskCompleted` and a plugin's `UserPromptSubmit` hook, exit 2 with empty stdout whose stderr says a file is missing (e.g. `No such file or directory`) is treated as a non-blocking error, not a block.
- **other** = for events using the standard decision model: valid JSON that passes schema validation → exit code ignored, JSON decides outcome, hook not reported as error; unparseable JSON-shaped stdout, plain-text stdout or empty stdout → non-blocking error (transcript `<hook name> hook error` notice + first stderr line prefixed `Failed with non-blocking status code:`; full stderr only in the debug log). `WorktreeCreate` aborts on any non-zero regardless of JSON; events outside the standard decision model that discard hook output (e.g. `StopFailure`) ignore JSON on every exit code except side-effect fields such as `terminalSequence`. A hook that can't start (script path missing/not executable → shell exit like 127, `/bin/sh: <path>: No such file or directory`) lands in the same non-blocking bucket → a mistyped path silently disables a policy gate; check for the notice on first run, or set `onFailure:"block"` (see **onFailure**).
- Pick ONE approach: exit-code signaling OR exit 0 + JSON. If mixed: exit 2 still blocks AND JSON fields are still read; other mixed exits follow the valid-JSON-or-error rule above.
- **exit 1 does NOT block** (Unix convention trap). Only exit 2 blocks for most events. Exceptions: `WorktreeCreate` aborts on any non-zero; `WorktreeRemove` non-zero fails removal if the dir still exists.
- **Timeout ≠ exit 2, with two exceptions**: apart from an `async:true` command hook, a `command`/`http`/`mcp_tool` hook that reaches its `timeout` is canceled with no effect — output discarded, never blocks, even on `PreToolUse` (the call proceeds through the normal permission flow). Don't rely on a stalled hook as a gate — to block when a `command`/`http` hook times out, set `onFailure:"block"` (version >= 2.1.295). Exception 1: a `PreModelSwitch` hook that times out BLOCKS the switch (version >= 2.1.251) — the one event where timeout behaves like exit 2. Exception 2: an Agent-SDK-registered callback hook (not a settings/plugin/skill hook) on `PreToolUse`, or on `UserPromptSubmit` as of version >= 2.1.208 (earlier ended the turn with an execution error instead), also blocks on timeout (on PreToolUse Claude gets an error result naming the timeout; another hook's explicit deny still takes precedence).

### exit 2 effect per event

Blocks: `PreToolUse` (blocks call), `UserPromptSubmit` (prompt never reaches Claude, but its text persists in the transcript file and prompt history — see UserPromptSubmit specifics), `UserPromptExpansion` (block expansion), `Stop`/`SubagentStop` (prevent stop), `TeammateIdle` (keep working), `TaskCreated` (rollback), `TaskCompleted` (prevent complete), `ConfigChange` (block, except policy), `PostToolBatch` (stop loop), `PreCompact` (block), `PreModelSwitch` (blocks the switch; version >= 2.1.251), `Elicitation` (deny), `ElicitationResult` (decline), `WorktreeCreate` (any non-zero fails), `WorktreeRemove` (any non-zero fails removal if the dir still exists afterward). `ConfigChange` and `Elicitation*` blocks surface no message anywhere (`ConfigChange`: debug log only).
No-block (stderr shown to Claude/user, or ignored): `PostToolUse`, `PostToolUseFailure`, `PermissionRequest` (exit 2 not honored — permission flow proceeds unchanged; deny via `decision` object instead), `PermissionDenied` (use `retry:true`, ignored when no classifier verdict), `StopFailure` (output and exit ignored except `terminalSequence`), `Notification` (exit code and stderr ignored), `SubagentStart`/`SessionStart` (exit-2 stderr is rendered as a `<hook name> hook error` transcript notice, Claude doesn't see it, the session/subagent proceeds; SubagentStart's notice lands in the subagent's own transcript), `Setup` (exit code and stderr ignored), `SessionEnd`, `CwdChanged`, `DirectoryAdded` (stderr → debug log only, never shown to user — the add already completed), `FileChanged`, `PostCompact`, `PostModelSwitch` (shows stderr to user; model already switched — version >= 2.1.251), `InstructionsLoaded`, `MessageDisplay` (original text displayed).

## HTTP response handling

- 2xx empty body = success (≈exit 0 no output); 2xx JSON object body = parsed as JSON output (schema-invalid body = non-blocking error); 2xx any other body (e.g. plain text) = non-blocking error like a non-2xx — the text is NOT added to Claude's context.
- Non-2xx / connection failure = non-blocking error → proceeds; timeout = canceled (see Timeouts above). An event with its own failure contract (e.g. `WorktreeCreate`) applies it to a failed HTTP hook too. **Cannot hard-block via status alone** → return 2xx + JSON `decision:"block"` or `permissionDecision:"deny"`. To block when the request fails or returns non-2xx, set `onFailure:"block"`.

## JSON output (exit 0)

stdout must be ONLY the JSON object (shell-profile noise breaks parsing: an unconditional `echo` in a profile sourced by the hook shell — Git Bash, or `BASH_ENV` → `~/.bashrc` — prepends text so the output no longer starts with `{` and is treated as plain text; on exit 0 nothing is reported, only the debug log; guard profile echoes with `[[ $- == *i* ]]`). `hookSpecificOutput` requires `hookEventName` = the event name. A field at the wrong level (e.g. top-level `permissionDecision`/`additionalContext`) still parses but is silently ignored — debug log line `Hook JSON output had unrecognized keys`. `additionalContext`, `systemMessage`, `initialUserMessage` and plain stdout are each capped at **10,000 chars** (each string measured on its own, even across hooks) → overflow saved to a file in the session directory and replaced by the path + preview of the first ≤2,000 chars; Claude isn't asked to read the file; no setting raises this cap.

Universal fields: `continue` (false → Claude stops entirely; precedence over decision fields; for `PreToolUse`/`PostToolUse` applies even when the call fails or completes mid-stream), `stopReason` (shown to the user when `continue` is false; stays in the conversation, so Claude sees it if the conversation continues), `suppressOutput` (no-op: accepted but has no effect — hook stdout never appears in transcript), `systemMessage` (user warning; in Agent SDK and `--output-format stream-json` output it can arrive as an `SDKInformationalMessage`), `terminalSequence` (emit notification on your behalf; ≥v2.1.141).

- `terminalSequence` allowlist: OSC `0`/`1`/`2` (titles), `9` (incl `9;4` progress), `99` (Kitty), `777`, bare BEL; ST/BEL terminators. Anything else (CSI, OSC 8/52/1337, colors) → field ignored. Use instead of `/dev/tty` (unavailable to hooks). Works even on events that discard `systemMessage`/`continue` (`Notification`, `StopFailure`) but is written only in an interactive session while the UI is on screen (ignored in `-p`/Agent SDK); a `WorktreeCreate` command hook can't return JSON (stdout = path), an `http` one can.
- `additionalContext` (inside `hookSpecificOutput` + `hookEventName`): injected as a system reminder at the hook's fire point; Claude reads on next request. Write as factual statements ("This repo uses `bun test`"), not imperative system commands (triggers prompt-injection defenses). Static rules → CLAUDE.md instead. Placement: SessionStart/SubagentStart → start of the conversation (subagent's, for SubagentStart) before the first prompt; UserPromptSubmit/UserPromptExpansion → alongside the prompt; PreToolUse/PostToolUse/PostToolUseFailure/PostToolBatch → next to the tool result; Stop/SubagentStop → end of turn, conversation continues; PostModelSwitch → next request. Several hooks' values are all delivered. Saved to transcript → stale values (timestamps/SHAs) replay on `--resume` for mid-session events; SessionStart re-runs on resume.

Content rewriting: PreToolUse `updatedInput` (before run), PostToolUse `updatedToolOutput` (after; `updatedMCPToolOutput` is an MCP-only alias, prefer `updatedToolOutput`), PermissionRequest `decision.updatedInput`, UserPromptSubmit injects `additionalContext` only (can't replace prompt). Redact outbound at PreToolUse, inbound at PostToolUse.

- `updatedToolOutput` must match the tool's output shape — built-in tools return structured objects (Bash → `{stdout, stderr, interrupted, isImage}`), and a value that doesn't match the schema is silently IGNORED (original output used); MCP tool output passes through unvalidated. Model-visible only: the tool already ran, and telemetry captured the original.
- PostToolUse `decision:"block"` puts `reason` next to the tool result; Claude still sees the original output → use `updatedToolOutput` to replace it.
- **PreToolUse: top-level `decision`/`reason` are DEPRECATED** for this event → use `hookSpecificOutput.permissionDecision`/`permissionDecisionReason`. (Deprecated `approve`/`block` → `allow`/`deny`.) PostToolUse/Stop still use top-level `decision`.
- **PreToolUse `permissionDecision:"allow"` alone is insufficient** for `AskUserQuestion`/`ExitPlanMode` (both require user interaction; in `-p` they're offered only when the run has a permission host such as an Agent SDK `canUseTool` callback or a `--permission-prompt-tool` MCP tool) — pair it with `updatedInput` carrying the answer (an `answers` object for `AskUserQuestion`). ≥v2.1.199: an MCP tool whose server marks it `_meta["anthropic/requiresUserInteraction"]` is stricter still — no hook can skip its approval prompt via `"allow"`, with or without `updatedInput`. Connector tools an org set to `ask` also prompt regardless of `"allow"`.
- **`"ask"` in auto mode** forces the prompt: the classifier may still deny the call but can no longer approve it silently. version >= 2.1.211; earlier versions let the classifier approve a Bash command running outside the sandbox without showing the requested prompt (its own safety rules still applied, and a hook `"deny"` was always honored).
- **`defer`** (≥v2.1.89, `-p` only): pauses Claude with the pending tool call preserved (`stop_reason:"tool_deferred"`, `deferred_tool_use.{id,name,input}` in the SDK result); the calling process resumes via `claude -p --resume <session-id>`, re-triggering the same `PreToolUse` call, then returns `"allow"` + `updatedInput` with the answer. Only works when the turn makes a single tool call — a batch of calls ignores `"defer"` with a warning. Session persists until resumed, subject to `cleanupPeriodDays` (default 30). If the deferred tool is unavailable on resume (e.g. its MCP server disconnected), the process exits `stop_reason:"tool_deferred_unavailable"`, `is_error:true`. There is no timeout or retry limit; the hook may return `"defer"` again on resume if the answer isn't ready, and the calling process ends the loop by eventually returning `"allow"`/`"deny"`. `claude -p --resume` restores no stored permission mode (it starts as a new `claude -p` run would → pass `--permission-mode`/`--dangerously-skip-permissions` again), while `claude --resume` without `-p` restores the stored mode with exceptions (see the sessions docs, "permission mode on resume"). Resuming a deferred session in plan mode needs `--permission-prompt-tool` alongside `--resume` to actually restore plan mode — version >= 2.1.246; without it Claude Code doesn't restore plan mode.
- **Stop**: fires whenever Claude finishes responding (not only at task completion); does NOT fire on user interrupts (API errors fire `StopFailure` instead). Block cap: Claude Code overrides a Stop hook after it blocks 8 consecutive times without progress (the count resets each time Claude calls a tool). Read input field `stop_hook_active` (true once a continuation already triggered) → exit 0 early. Raise cap via env `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. On `SubagentStop`, `decision:"block"` + `reason` keeps the subagent running with `reason` as its next instruction — to inject context into the PARENT session after a subagent returns, use `PostToolUse` on the `Agent` tool instead. Built-in: `/goal` is a shortcut for a session-scoped prompt-based `Stop` hook — no hook config needed. `reason` is required with `decision:"block"`. `hookSpecificOutput.additionalContext` (Stop/SubagentStop) = non-error feedback that keeps the conversation going under the same loop protections (`stop_hook_active`, 8-continuation cap) but is labeled `Stop hook feedback` instead of a hook error.
- **PreCompact**: blocking effect depends on trigger. Proactive auto-compact (before the context limit) is skipped and the conversation continues uncompacted. Blocking a recovery compaction (already-returned context-limit error from the API) surfaces that underlying error and fails the current request. For a manual `/compact` the exit-2 stderr is shown to the user; `systemMessage`/`continue` are discarded.
- **PostToolBatch**: fires once with the whole batch (`PostToolUse` fires per tool, concurrently for parallel calls); `additionalContext` is injected once before the next model call; `decision:"block"` or `continue:false` stops the loop before the next model call (reason from `reason`/`stopReason`/exit-2 stderr, shown as a transcript warning and kept in the conversation).
- **PermissionRequest vs PreToolUse**: PreToolUse runs for every call; PermissionRequest only when Claude Code is about to ask, or would otherwise auto-deny a call that can't prompt (background subagents in `-p` → denied unless a hook decides). `permission_suggestions` isn't an exact list of the dialog's options (some dialogs derive options from the request; `allowManagedPermissionRulesOnly` hides rule-saving options; a dialog can offer options with no suggestion entry, e.g. "Yes, and switch to auto mode", which changes the mode directly). An exit-2 hook without a `decision` object leaves the flow unchanged and its stderr is discarded.
- **PermissionDenied**: fires only for auto-mode denials — not on a manual deny, a `PreToolUse` block, or a matching `deny` rule. `retry:true` adds a message telling the model it may retry; the denial itself isn't reversed. No JSON or `retry:false` → denial stands.
- **ConfigChange**: fires for settings files, a changed `managed-settings.json`/`managed-settings.d/` file, and skill files; NOT when server-managed settings arrive/refresh, nor for macOS managed preferences / Windows registry policy changes, nor (WSL with `wslInheritsWindowsSettings`) for a changed Windows-side managed settings file applied on its policy poll. Managed-policy hooks fire only when `managed-settings.json` or a file in `managed-settings.d/` changes. `reason` is accepted but never shown; a blocked change surfaces no message to anyone (debug log only); `policy_settings` blocks are ignored; `systemMessage`/`continue` discarded.
- **Multi-hook merge**: every matched hook runs to completion before merge — a `deny` does NOT stop sibling hooks (don't rely on it to suppress another hook's side effects). Multiple PreToolUse `updatedInput`: last-to-finish wins, order non-deterministic → avoid >1 hook rewriting the same tool input.

## SessionStart specifics

- `CLAUDE_ENV_FILE` (also Setup/CwdChanged/FileChanged): append `export` lines → persist env into later Bash. Use `>>`.
- `reloadSkills:true` re-scans skill/command dirs after SessionStart hooks (skills the hook installed become available same session). Re-runs on resume with `source:"resume"`, or `"fork"` under `--fork-session`.
- Plain stdout already reaches Claude here → context-only hooks can skip JSON. Stderr of an exit-0 hook is informational only (`reloadSkills` still applies).
- Interactive launch, `--continue`/`--resume` at launch, and `/clear`: hooks run in the background — you can type at once and a resumed conversation appears without waiting — but Claude's first response (and a prompt sent during startup) waits for them; `Esc` takes the prompt back into the input, the hooks keep running. Switching conversations with in-session `/resume` waits for the hooks instead. If `/clear` or a conversation switch happens while background hooks still run, nothing they return applies.
- A plugin's SessionStart `initialUserMessage`/`sessionTitle` are ignored if the plugin finishes installing after the SessionStart hooks have run → install the plugin before the session starts.
- `fork` source = a session forked from an existing one: `--fork-session` with `--resume`/`--continue`, the `/fork` background copy, `/branch`, or a conversation moved to the background.
- `model` can be omitted (e.g. after `/clear` or conversation recovery) → check before reading. `session_title` = custom title only (`--name`, `/rename`, a hook's `sessionTitle`, SDK `renameSession()`), never a generated one.
- `CLAUDE_ENV_FILE` content runs as a script preamble before each Bash command; variables persist until the next `CwdChanged`, which clears them.

## Setup specifics

- Fires ONLY on `claude --init-only`, or `--init`/`--maintenance` combined with `-p`; never on normal interactive startup. `--init-only` also runs `SessionStart` (`startup` matcher), then exits without starting a conversation.
- Can't block: execution continues on any exit code (incl. 2); exit code and stderr are ignored. With `-p`, a Setup hook's stdout/stderr/exit code surface only as `hook_response` events under `--output-format stream-json --verbose`; with `--init-only` nothing prints on success (check via `claude --debug-file <path> --init-only`). In `-p` you still need a prompt (argument/stdin), unless a `SessionStart` hook supplies `initialUserMessage` or you resume a deferred tool call.
- Unlike SessionStart, plain stdout does NOT reach Claude here, and Claude Code discards every JSON output field on every exit code (`systemMessage`, `continue`, `hookSpecificOutput.additionalContext`) → Setup cannot inject context. Setup input carries `trigger` (`init`/`maintenance`). Only `command` hooks run on Setup (`mcp_tool` always skipped). `CLAUDE_ENV_FILE` is available.
- Setup does not fire on every launch → a plugin needing a dependency must check-and-install on first use (e.g. test for `${CLAUDE_PLUGIN_DATA}/node_modules`), not rely on Setup (marketplace plugins may not need this: Claude Code installs eligible Node.js package dependencies automatically when it caches the plugin).

## Async hooks (`async`/`asyncRewake`, `command` only)

- Response fields that control behavior (`decision`, `permissionDecision`, `continue`, …) have no effect — the triggering action has already proceeded by the time the hook completes.
- Output delivered on the next conversation turn; if idle, waits for the next user interaction. Exception: `asyncRewake` + exit 2 wakes Claude immediately even while idle. After the process exits, the `additionalContext` and `systemMessage` from its JSON response go to Claude on that turn — unlike a synchronous hook, neither is shown to the user. `timeout` isn't enforced once it runs in the background (it is for `asyncRewake`). Results are delivered only while the session runs.
- Malformed JSON output: fields with the wrong type are dropped (warning under `--debug`); version >= 2.1.202 fixes a prior crash-on-malformed-JSON that recurred on every resume of the session.
- Completion notifications suppressed by default; show them via `Ctrl+O` (verbose) or `--verbose`.
- In `-p` mode, Claude Code kills any async hook still running at session teardown (outcome `cancelled`) — start a fully detached process from the hook if its work must outlive the session.
- Each firing spawns its own background process — no deduplication across multiple firings of the same async hook.

## PreModelSwitch / PostModelSwitch specifics

- version >= 2.1.251. `command`/`http`/`mcp_tool` only (no `prompt`/`agent`).
- PreModelSwitch triggers: `/model <name>` + picker, `Option+P`/`Alt+P` picker, the `/config` Model setting, a fast-mode toggle that changes the model, or an Agent SDK/Remote Control `set_model`/`apply_flag_settings` model change. Does NOT run for Claude Code's own switches (automatic model fallback, resume-restore) — those reach PostModelSwitch only.
- PostModelSwitch additionally runs after: an `opusplan`-style setting entering/leaving plan mode. It does NOT run when a fallback-model-chain substitution serves just one turn (session model unchanged).
- Matcher = canonical name of `to_model`, ignoring any `[1m]` suffix — an alias (`opus`), a dated ID, and a provider-specific ID (e.g. Bedrock) all normalize to the same canonical name. When Claude Code can't resolve a canonical name (e.g. a custom LLM-gateway model ID), it runs every hook regardless of matcher — check `to_model` in the hook body rather than relying on the matcher alone.
- Input adds (both events): `from_model`, `to_model`, `requested_model` (alias/full-ID/`null` for the default model), `source` (`"command"`|`"picker"`|`"sdk"` on PreModelSwitch; PostModelSwitch adds `"auto"` = automatic fallback/other self-initiated change and `"resume"` = model restored on session resume; `requested_model` is `null` for `"auto"`, the saved model setting for `"resume"`), `context_tokens`, `prompt_cache_warm`, `cache_ttl` (`"5m"`|`"1h"`), `estimated_cache_write_usd`, `pricing` (`"configured"`|`"catalog"`|`"default"`).
- PreModelSwitch decision, timeout, and merge rules — see the Decision control table above. An exit code other than 0 or 2 with no JSON decision doesn't block: stderr is shown and the switch applies. `systemMessage` is shown to the user regardless of decision (a cost-report hook can return only `{"systemMessage":"…"}`).
- PostModelSwitch can't block (model already changed) — see the Decision control table above for its delivery timing.

## SessionEnd specifics

- Default timeout **1.5s** (not the general 600s) — applies to session exit, `/clear`, and switching sessions via interactive `/resume`. Budget auto-raises to the highest per-hook `timeout` configured in settings files, up to 60s; timeouts on plugin-provided hooks don't raise it; a hook without its own `timeout` still keeps the 1.5s default. Override explicitly via env `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` (milliseconds) — this also becomes the timeout for each hook lacking its own `timeout` (version >= 2.1.268; earlier, the env var raised only the overall budget and left timeout-less hooks canceled at 1.5s).

## DirectoryAdded specifics

- Fires after `/add-dir` (matcher `slash_command`) or an SDK `register_repo_root` control request (matcher `register_repo_root`). Does NOT fire for: the `--add-dir` startup flag (`SessionStart` covers those directories instead), adding a directory via the `/permissions` Workspace tab, or adding a directory that's already a working directory or inside one (the add fails with an error instead).
- Sandbox/permission state is refreshed BEFORE the hook fires — sandboxed tools already see the new directory when the hook runs. The hook command itself runs unsandboxed.
- Can't block: the add has already completed. Claude Code doesn't wait for the hook — it runs in the background with the normal 600s `command`/`http`/`mcp_tool` default timeout.

## UserPromptSubmit specifics

- Not only typed prompts: also runs when a scheduled task fires (incl. a `/loop` iteration), a background subagent reports back to the session that started it, or another session messages your main conversation. A hook that assumes human-typed input must handle those.
- To block the prompt when a `command`/`http` hook times out or fails, set `onFailure:"block"` (version >= 2.1.295); the default is cancel-and-discard (see next bullet).
- Default `command`/`http`/`mcp_tool` timeout is 30s (not 600s): the hook blocks model processing before every prompt. A timed-out hook is canceled and its output (incl. `additionalContext`) discarded — the prompt still reaches Claude without that context; the transcript shows a notice naming the hook and timeout. An Agent SDK callback hook that times out instead blocks the prompt with a message naming hook + timeout (version >= 2.1.208; earlier ended the turn with an execution error).
- Context via exit-0 plain stdout or `hookSpecificOutput.additionalContext`; neither makes a visible transcript entry — each is injected as a system reminder starting with the hook's name (verify in the debug log).
- A blocked prompt never reaches Claude, yet by default the block message ends with `Original prompt:` + the submitted text and Claude Code writes that message to the session transcript file. `suppressOriginalPrompt:true` (inside `hookSpecificOutput`) drops the text from the message, for `decision:"block"` or exit 2 + JSON; an exit-2 hook printing no JSON always includes it. The text can still sit in the transcript and prompt history → blocking is not a way to keep a secret off disk. The hook can't replace the prompt text.

## FileChanged / CwdChanged specifics

- FileChanged uses a filesystem watcher, so it fires whatever wrote the file (Edit/Write, a Bash script, an outside process); a `PostToolUse` hook on `Edit|Write` doesn't run for those Bash/external rewrites.
- `matcher` does two jobs: it is split on `|` into literal filenames registered in the working directory (regex is useless here: `^\.env` watches a file literally named `^\.env`), and it filters which groups run against the changed file's basename using the standard matcher rules.
- The watcher starts only when something names a file: seed with a group whose matcher names ≥1 file, or a `SessionStart`/`CwdChanged` hook returning `watchPaths`. Give the group that handles dynamic paths an omitted matcher (matches every watched file, adds nothing to the list); `"*"` also matches every file but is registered as a literal file named `*`.
- `watchPaths` (CwdChanged/FileChanged/SessionStart output) = absolute paths replacing the dynamic list; `matcher` paths are always watched; `[]` clears it. `systemMessage` shows as a brief terminal notification in interactive sessions (not in the SDK stream); `continue` discarded.
- Claude Code reruns the hook after every rewrite → a hook that rewrites the watched file must no-op when nothing needs changing (e.g. `grep -q` guard before `perl -i`), else it loops forever.
- CwdChanged fires when a shell command in the main conversation changes the working directory (e.g. `cd`); direnv-style pattern = `SessionStart` + `CwdChanged` both writing `direnv export bash > "$CLAUDE_ENV_FILE"`.

## SubagentStop specifics

- Input adds `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message`, plus the parent-scoped `background_tasks`/`session_crons`. Fires for Claude Code's internal agents too (prompt suggestions, `/btw` side questions) — their `agent_type` is the session's own agent name (`--agent`/`agent` setting) or `""`; see the matcher note.
- Decision control = same format as Stop (`decision:"block"` + `reason` keeps the subagent running with `reason` as its next instruction; exit 2 delivers stderr the same way; `additionalContext` = non-error feedback). Parent-session context after a subagent returns → `PostToolUse` on the `Agent` tool.
- SubagentStart can't block but its `additionalContext` goes into the subagent's context before its first prompt; on a rerun for the same subagent it is injected only if the subagent's context no longer holds the earlier copy (keeps the prompt cache intact), and again after auto-compaction discards that copy.

## Elicitation / ElicitationResult specifics

- Matcher = MCP server name. `command`/`http`/`mcp_tool` only. Claude Code applies `hookSpecificOutput` only on exit 0.
- `Elicitation` input: `mcp_server_name`, `message`, optional `mode` (`form`/`url`), `url`, `elicitation_id`, `requested_schema`. Exit 0 + `hookSpecificOutput` with `action` answers without a dialog: `accept` + `content` (keys = `requested_schema.properties` names), `decline`, or `cancel`. No output + exit 0 = leave it to the dialog (dialog **Decline** sends `decline`, `Esc` sends `cancel`). URL mode: `accept` skips the dialog, so the URL never opens.
- An `Elicitation` hook that answers → `ElicitationResult` hooks do NOT run for that request.
- `ElicitationResult` input: `mcp_server_name`, `action`, optional `mode`, `elicitation_id`, `content`. No output = response unchanged; `accept` + new `content` REPLACES the user's whole `content` object (include unchanged fields); `decline` blocks (server gets `decline`, without the user's values); `cancel` sends `cancel` WITH the submitted values (return `decline` to withhold them). Return `action` with `content` — a `hookSpecificOutput` without `action` is ignored.
- `ElicitationResult` also runs when the user declined/cancelled and your `action` replaces theirs → check input `action` is `accept` before returning `accept`, or a declined request becomes accepted.
- Other ways to decline (both events; server gets `decline`): exit 2 (that hook's `hookSpecificOutput` is ignored); top-level `decision:"block"` (overrides an `action` in the same output). Several matched hooks: a decline overrides another hook's `accept`/`cancel`. Neither user nor server sees why — stderr and `reason` aren't shown; `reason`/`systemMessage`/`continue` are discarded whatever `action` returns.
- Debug log line for a hook-answered request ends `Elicitation resolved by hook: {...}`. Top-level `decision` was ignored on both events from v2.1.105 until the fix in v2.1.284.

## Hooks in skills/agents (frontmatter)

- Same config format as settings hooks, defined in the component's YAML frontmatter. Lifetime differs: **subagent** hooks run only while that subagent runs and are removed when it finishes; **skill** hooks register when you or Claude invoke the skill and keep running for the rest of the session, on turns after the skill's own turn too. All events supported.
- Subagent `Stop` auto-converts to `SubagentStop`. `once:true` honored ONLY in skill frontmatter (removes the hook after its first successful run).
- Frontmatter hooks in a PROJECT **skill** follow the same trust rule as settings-file hooks: registered on invocation, including in `-p` mode in folders you haven't explicitly trusted.
- Frontmatter hooks in a PROJECT **subagent** run only after the workspace-trust dialog is accepted for the folder the agent file came from; a `-p` session doesn't count as accepting it. version >= 2.1.218; earlier versions ran them from untrusted folders.
- **Workspace trust for settings-file hooks**: in interactive sessions, hooks from ALL settings files (including `~/.claude/settings.json`) are held back until the workspace trust dialog is accepted for the folder. In `-p`/SDK sessions, the folder is treated as trusted automatically — hooks from committed `.claude/settings.json` run even in folders never interactively trusted. Trust granted to a parent directory extends to its subfolders. Before scripting `claude -p` over an unknown repo, review its `.claude/` settings, start with `--bare`, or pass `--settings '{"disableAllHooks": true}'`.
- **Cloud sessions** (Claude Code on the web): don't read local `~/.claude/settings.json`; hooks come from the repo's `.claude/` files and org managed settings only. In a self-hosted environment, Claude Code additionally runs hooks the operator seeded from the runner host's `~/.claude/`, plus the runner image's managed settings file when it's among the managed sources actually applied (by default, only when neither server-managed settings nor an MDM-delivered policy already supplies the managed tier).

## /hooks menu & disabling

- `/hooks` = read-only browser; per type `[command|http|mcp_tool|prompt|agent]` + source (`User`/`Project`/`Local`/`Plugin`/`Session`/`Built-in`). Edit JSON to change. `All events` (end of the list) also shows events with no hooks configured; under `allowManagedHooksOnly` the menu shows `Only hooks from managed settings run here` and user/project/local settings hooks aren't listed (they don't run).
- `disableAllHooks:true` disables all (no per-hook disable). Claude Code reads the value left after settings precedence, so a project `"disableAllHooks": false` overrides a user `true`. Respects managed hierarchy — only managed-level can disable managed hooks. Per-run override: `--settings '{"disableAllHooks": true}'` (takes precedence over project/local settings).

## Hard constraints / security

- PreToolUse fires BEFORE any permission-mode check (every mode, incl. `dontAsk`) → `permissionDecision:"deny"` blocks even in `bypassPermissions` / `--dangerously-skip-permissions`. Reverse fails: `"allow"` never overrides settings deny rules, ask rules, org-set-to-`ask` connector tools, or `requiresUserInteraction` MCP tools (hooks tighten, never loosen). Deny rules from any scope (incl. managed) outrank hook approvals. A plugin "mod" handling `tool.check` can approve a call your `PreToolUse` hook blocked, unless the hook is in managed settings.
- No controlling terminal (macOS/Linux ≥v2.1.139): no `/dev/tty`. Surface via `systemMessage`; notify via `terminalSequence`.
- Security/irreversible gates → permission system, NOT hooks. `if` and http/mcp_tool fail OPEN (see hook-handler-selection.md). A `command`/`http` hook used as a gate can fail CLOSED with `onFailure:"block"` (version >= 2.1.295 — see **onFailure**).
- `command` holds no state between fires; stateful/expensive init → persistent server via `mcp_tool`/`http`.
- Hook-only `mcp_tool` triggers are config-driven; keep them off the model tool surface to avoid context/token cost.
- Debug hook execution: `claude --debug-file <path>` or `/debug` mid-session (`claude --debug` logs to `~/.claude/debug/<session-id>.txt`, nothing to the terminal); set `CLAUDE_CODE_DEBUG_LOG_LEVEL=verbose` for granular matcher/query detail. `Ctrl+O` transcript view: successful run = nothing shown (unless JSON surfaces e.g. `systemMessage`/Stop feedback); blocking error = feedback; non-blocking error = `<hook name> hook error` notice.
- Hook hygiene: command hooks run with your full user permissions → validate/sanitize input, always quote shell variables (`"$VAR"`), block path traversal (`..`), use absolute paths (exec form + `${CLAUDE_PROJECT_DIR}` needs no quoting), skip sensitive files (`.env`, `.git/`, keys).
