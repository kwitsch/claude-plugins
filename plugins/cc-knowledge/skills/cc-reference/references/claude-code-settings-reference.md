## settings.json: locations & scope precedence

Scopes from highest to lowest priority (higher overrides lower for scalar keys; arrays merge):

| Scope              | File path                           | Shareable              |
| ------------------ | ----------------------------------- | ---------------------- |
| Enterprise managed | platform/MDM/plist/HKLM/HKCU/remote | Yes (admin-controlled) |
| Command-line args  | `--allowedTools`, `--model`, etc.   | No (session only)      |
| Project local      | `.claude/settings.local.json`       | No (gitignored)        |
| Project            | `.claude/settings.json`             | Yes (commit to repo)   |
| User               | `~/.claude/settings.json`           | No (machine-local)     |

- Array settings (`permissions.allow`, `sandbox.filesystem.allowWrite`, etc.) **concatenate and deduplicate** across scopes rather than override.
- Exception: `fallbackModel` — the highest-precedence scope that defines it supplies the entire chain.
- `version >= 2.1.175:` `availableModels` — a managed/policy value replaces lower-precedence entries entirely.
- Within the managed tier only ONE source applies; the others are ignored, not merged. Highest first: a configured `policyHelper` script's output (which then becomes the ONLY managed source, and parent settings are never merged) → remote/server-managed → MDM/OS policy → file-based (`managed-settings.json` + `managed-settings.d/*.json` merged) → HKCU registry.
- `version >= 2.1.211:` `.claude/settings.local.json` is read/written at the git repository root (resolved through worktrees to the main checkout), so one file covers every subdirectory. Earlier versions used the launch directory; a file left there is still read, and the repo-root value wins on a key collision.
- `Read`/`Edit` `/path` rules in local settings anchor at the session's primary working directory (the launch directory until `/cd` moves it), not the repo root.
- The repo-root local-settings file applies only when the repo root is owned by your user and isn't your home directory, and not on Windows; otherwise (and outside a git repo) the file stays at the starting directory instead.
- `/cd <path>` moves the primary working directory. `version >= 2.1.246:` the new directory's project settings, hooks, MCP servers, and skills apply immediately; earlier versions waited until the session was resumed.
- `--settings <file-or-json>` merges per-key like any other layer; omitted keys leave lower layers intact. It can set any key a user settings file can set; it cannot set `Managed` or `Global config` keys.
- Env vars are not a settings level; precedence is decided per pair: `ANTHROPIC_MODEL` beats the `model` key from any file, while `ANTHROPIC_DEFAULT_MODEL` applies only when no file sets `model`. An `env` block inside a settings file is an ordinary key and follows the scope levels.
- Cloud sessions: single-repo sessions read the clone's `.claude/settings.json`; multi-repo sessions read only `enabledPlugins` and `extraKnownMarketplaces` from each; user and local settings are not read; only server-managed settings (not device-deployed managed files) reach them.
- Windows: `~/.claude` resolves to `%USERPROFILE%\.claude`.
- Run `/status` → **Status** tab → `Setting sources` line to see which files are loaded; the line lists files read, NOT which file supplied each key. `claude doctor` lists entries Claude Code rejected.
- Settings files are strict JSON: a `//` comment or trailing comma is a syntax error. `"$schema": "https://json.schemastore.org/claude-code-settings.json"` gives editor validation (the schema can lag the CLI, so a schema warning on a documented key is not by itself an invalid config).
- Broken file handling: a user/project/local file with invalid JSON or a rejected value → **Settings Error** dialog at interactive start (fix with Claude, exit, or continue without); individual bad entries (malformed permission rule, unknown hook event name) → **Settings Warning**, only those entries skipped; `-p` shows no dialog and skips the broken file/values; an unparseable managed document is the one case that doesn't fall through. A `~/.claude.json` parse failure is copied to `~/.claude/backups/.claude.json.corrupted.<timestamp>` (the five most recent `.claude.json.backup.<timestamp>` files are restorable).
- Edits apply live: Claude Code watches user/project/local/managed-file settings and reloads without restart (`permissions`, `hooks`, `apiKeyHelper` included), and loads a settings file created mid-session if its folder existed at start (a new project `.claude/` folder is picked up too). It runs the `ConfigChange` hook per detected file change, not for MDM/console-delivered managed settings (those arrive on a schedule). Some keys are read once at session start; `model` and `effortLevel`/`modelSettings` are switched mid-session with `/model` and `/effort`, not by file edit.
- `/config` menu (CLI only; not the VS Code chat panel or desktop app) saves most options to `~/.claude/settings.json`, a few (e.g. **Show tips**) to `.claude/settings.local.json`, and global config options to `~/.claude.json`; `/config key=value` sets one option. `/model`'s `s` key switches without saving; `/model` otherwise saves `model` to user settings — if that file is read-only the change lasts one session.
- Three ways to change a setting for one session without writing a file: `--settings` (above user/project/local, below managed), a per-key flag (`--model` for `model`, `--effort` for `effortLevel`/`modelSettings`), a paired env var (`ANTHROPIC_MODEL` for `model`). Which one wins is decided per key.
- First write of `.claude/settings.local.json` in a git repo adds `**/.claude/settings.local.json` to the global git excludes file (`core.excludesFile` when set to an absolute or `~` path, else `$XDG_CONFIG_HOME/git/ignore`, else `~/.config/git/ignore`); a hand-created file needs a manual `.gitignore` entry. The file is written when you pick "Yes, and don't ask again" on a Bash/WebFetch prompt; Claude Code applies its `allow` rules without the trust step only while the file is untracked.
- Shared `.claude/settings.json` is read from the session's primary working directory, so start Claude Code at the repo root to use a root file; after `/cd` both project files are read from the new directory.
- Keys the settings index scopes `User, local, or managed`, `User or managed`, `Managed`, or `Global config` never apply from the shared project file (apart from a few a repo file can still switch off); `Global config` keys apply only from `~/.claude.json`. Keys that wait for workspace trust: `permissions.allow`, `permissions.additionalDirectories`, `extraKnownMarketplaces`, most `env` values; `deny`/`ask` rules apply at once.

### Exceptions to managed settings precedence

For these keys, Claude Code honors a restrictive value from a scope that otherwise couldn't override managed settings — a stricter value always wins regardless of which scope set it:

| Key                                               | Value honored                                                                                                          | Notes                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `disableClaudeAiConnectors`                       | `true` from any scope                                                                                                  | Honored even when a managed source sets `false`                                       |
| `enableArtifact`                                  | `false` from any scope; `disableArtifact: true` from any scope                                                         | Honored even when managed sets `true`; nothing re-enables it. `version >= 2.1.242:`   |
| `isolatePeerMachines`                             | `true` from any scope                                                                                                  | Honored even when a managed source sets `false`                                       |
| `permissions.blockReadsOutsideWorkingDirectories` | `true` from any scope                                                                                                  | Honored even when a managed source sets `false`. `version >= 2.1.257:`                |
| `autoMode.classifyAllShell`                       | `true` from `~/.claude/settings.json` or `--settings`                                                                  | Honored even when a managed source sets `false`                                       |
| `remoteControlAtStartup`                          | `false` from `.claude/settings.json` or `.claude/settings.local.json`                                                  | Honored even when managed sets `true`; a project/local `true` is ignored              |
| `crossSessionInbound`                             | A stricter value from `.claude/settings.json`/`.claude/settings.local.json` on the `accept` < `hold` < `refuse` ladder | Honored over managed/`--settings`/user; a non-stricter project/local value is ignored |
| `useAutoModeDuringPlan`                           | `false` from any managed source, `--settings`, user, or local settings                                                 | A `false` in `.claude/settings.json` (shared project) is ignored                      |
| `syncClaudeAiSkills`                              | `false` from any managed source, `--settings`, user, or local settings                                                 | A `false` in `.claude/settings.json` (shared project) is ignored                      |
| `syncClaudeAiPlugins`                             | `false` from any managed source, `--settings`, user, or local settings                                                 | A `false` in `.claude/settings.json` (shared project) is ignored                      |
| `maxEffortLevel`                                  | The lowest cap from any scope, including `--settings`                                                                  | `version >= 2.1.267:`                                                                 |

A platform embedding Claude Code that sets `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` in its env is also an exception: its model configuration takes precedence over `model`/`fallbackModel`/`modelPicker`/`modelOverrides` from every managed source and over model-selection env vars in a managed `env` block; a managed `availableModels` allowlist stays in force unless the host supplies its own.

## Environment variables

Numeric values accept scientific notation and digit separators (`2e3`, `64_000`) except where a row says plain digits only; `version >= 2.1.211:` earlier versions could silently truncate such a value (e.g. `1e6` read as `1`). Boolean toggles: `1`/`true`/`yes`/`on` on, `0`/`false`/`no`/`off` off, any casing — except `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `CLAUDE_CODE_TMUX_TRUECOLOR`, `FALLBACK_FOR_ALL_PRIMARY_MODELS`, `IS_DEMO` (any non-empty value including `0` turns ON; unset/empty turns off), and `FORCE_HYPERLINK` (numeric; only `0` turns off).

- `env` block in a settings file: values are copied into Claude Code's environment as written — no shell expansion (`~`, `$HOME` stay literal), so write absolute paths (e.g. `CLAUDE_CONFIG_DIR`). A running session applies new/changed values on save, except features that read variables once at startup (e.g. OpenTelemetry); removing a variable doesn't unset it until relaunch. A settings `env` entry replaces the shell's value in most sessions. To override a variable you can't unset (e.g. a stale `CLAUDE_CODE_USE_VERTEX`), set it to `""` — empty counts as unset for provider selection, subprocesses still inherit the empty value.
- Precedence is per pair, not per level: for `ANTHROPIC_MODEL` and `CLAUDE_CODE_AUTO_CONNECT_IDE` the variable is read first and the `model`/`autoConnectIde` setting is used only when it is unset. `--model`/`/model` override `ANTHROPIC_MODEL`; `CLAUDE_CODE_EFFORT_LEVEL` overrides `--effort` and `/effort`. Check each variable's row for its own rule.
- Variables ignored when delivered through a settings `env` block (set them in the launching environment): `CLAUDE_CODE_RESTRICTED`, `CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT`, `CLAUDE_CODE_DISABLE_SUBSTITUTION_RM_PROMPT`, `CLAUDE_CODE_DISABLE_INLINE_SHELL_RM_PROMPT`, `CLAUDE_CODE_DISABLE_POWERSHELL_CMD_RM_DENY`, `CLAUDE_CODE_DISABLE_ADMIN_ENV_UNION`, `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC`, `CLAUDE_CODE_MESSAGING_SOCKET`/`_TOKEN`; project/local settings additionally can't set `CLAUDE_CONFIG_DIR` or the OpenTelemetry exporter variables (apart from a few off values) and `CLAUDE_AFK_*`.

## Permissions

### Rule syntax

```
ToolName                      # bare name: matches any call to ToolName
ToolName(*)                   # equivalent to the bare name
ToolName(glob)                # positional-arg match: glob against first argument
ToolName(prefix *)            # prefix glob (trailing space + * is prefix match)
mcp__server                   # all tools from a specific MCP server
mcp__server__toolname         # specific MCP tool
mcp__server__*                # all tools from a specific MCP server (allow only)
*                             # deny/ask: every tool; NOT valid in allow rules
mcp__*                        # deny/ask: every MCP tool; NOT valid in allow rules
```

- Evaluation order: `deny` → `ask` → `allow`; first match wins, specificity does NOT reorder. A broad deny blocks even a narrower allow; a matching ask prompts even with a narrower allow.
- Allow rules: tool-name globs accepted **only** after a literal `mcp__<server>__` prefix (server segment must be glob-free); bare globs like `"*"` or `"B*"` in allow are skipped with a warning.
- Deny/ask rules: accept glob patterns in the tool-name position; pattern must match the full name (`"*"` = every tool, `"mcp__*"` = every MCP tool).
- A deny rule matching a bare tool name (or a bare-name glob) removes that tool from Claude's context; a scoped rule like `Bash(rm *)` leaves the tool present and blocks matching calls.
- `EndConversation` is the exception to bare-name removal: no deny rule can remove it while any other tool remains, and an ask rule never prompts for it.
- A deny/ask rule whose tool name matches no known tool produces a startup warning (tool names with `_` or `*`, and names of tools Claude Code has removed such as `TaskOutput`, are exempt).
- An `mcp__` rule written with parentheses is skipped when a settings file loads (listed in the invalid-settings dialog and `claude doctor`); to match a parameter on an MCP tool, pass a deny rule via `--disallowedTools`.
- Use canonical tool names: the transcript label can differ (e.g. `Stop Task` → canonical `TaskStop`); rules/hook matchers match the canonical name only.
- Project `.claude/settings.json` `permissions.allow` + `additionalDirectories` are read but NOT applied until the workspace trust dialog is accepted (trust is keyed on the git repo root); `deny`/`ask` are unaffected since they only restrict. `.claude/settings.local.json` goes through the same check whenever the repo could have supplied it (committed, or `.claude` is a symlink); it is exempt outside a git repo or inside your own config home (`CLAUDE_CONFIG_DIR`). The tracked/symlink check runs only once the folder (or a parent) is trusted; until then the local file's rules are held like project settings (except in your config home). `version >= 2.1.207:` that holds for an untracked file too — earlier versions applied its rules before the dialog was accepted.
- Trust is keyed on the git repo root (a worktree uses the main checkout's root, a nested repo such as a submodule needs its own); outside a repo it is keyed on the start directory and covers its subdirectories except nested repos; started in your home directory it is held for the session only and not written to disk. The dialog lists the allow rules and directories the folder would grant; it is interactive-only.
- Before the folder is trusted (only a parent trusted, or `claude -p`/SDK which never shows the dialog): settings-file hooks, the `env` block, helper commands such as `apiKeyHelper`, and a project skill's hooks/`allowed-tools` ARE used (`allowed-tools` is never trust-gated); `permissions.allow`/`additionalDirectories` are NOT (`-p` prints `this workspace has not been trusted` to stderr); frontmatter hooks in project subagents, `@skills-dir` plugins, `extraKnownMarketplaces` entries, and inline subagent `mcpServers` are NOT; `.mcp.json` servers prompt (parent-only trust) or connect without asking (`-p`/SDK); a `headersHelper` doesn't run. Trust by hand with `projects["<path>"].hasTrustDialogAccepted: true` in `~/.claude.json`. For `claude -p` in a repo you didn't write: `--setting-sources user`, `--bare`, `--settings '{"disableAllHooks": true}'` (user-settings alone isn't enough — project settings outrank them), or a `disabledMcpjsonServers` entry.
- "Yes, and don't ask again" saves permanently only for Bash commands and WebFetch domains (to `.claude/settings.local.json` at the repo root, resolved through worktrees; `version >= 2.1.211:` earlier versions saved at the start directory); file-edit approvals last until session end; a compound command saves one rule per subcommand needing approval (up to 5); a file-path approval escapes gitignore characters (`[`, `]`, `*`) so the rule matches only that literal path (earlier than `version >= 2.1.202` saved unescaped; your own rules are never escaped). A prompt that can't show everything an option would allow offers only a one-time approval — add the rule in `/permissions`.
- Permission prompt: `Tab` on Yes/No opens a comment field (not on WebFetch/browser prompts or the session-wide/save-rule options); Yes sends the comment after the result, No sends it as the denial reason (a No without comment on a main-conversation prompt stops the turn). `/permissions` lists every rule with its source file; `version >= 2.1.234:` rule edits apply from Claude's next tool call in the same turn; an **Auto mode** tab shows classifier rules and a **Recently denied** tab lets you retry a blocked action with `r`.
- A `PreToolUse` hook cannot override rules: deny/ask are evaluated regardless of an `"allow"` decision. A hook exiting 2 blocks BEFORE rules are evaluated, so it also beats allow rules. Hooks run for every tool except `EndConversation`.
- A mod (plugin that handles `tool.check`) answers after rules and `PreToolUse` hooks and can replace their outcome: it can approve a call an ask rule would prompt for, approve a call a non-managed `PreToolUse` hook blocked, and skip the `auto` classifier. Deny rules hold over a mod by default on machines with managed settings or Team/Enterprise sign-in; elsewhere a mod can approve a denied call.

### Input-parameter matching (deny/ask only)

`Tool(param:value)` matches a top-level scalar input field set to that exact value (allow rules keep each tool's own specifier syntax):

| Rule                           | Matches                                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| `Agent(model:opus)`            | Agent calls requesting the `opus` alias (literal, pre-normalization; not a full ID) |
| `Agent(isolation:worktree)`    | Agent calls requesting a git worktree                                               |
| `Bash(run_in_background:true)` | Bash calls running in background                                                    |

- One parameter per rule; `*` is a wildcard; an omitted param is never matched (`Agent(model:*)` skips a call with no `model`). Only direct top-level fields are matchable (nested object/array fields are not). Whitespace around the colon is ignored; run with `--verbose` to see the exact parameter names and values of each tool call. To gate on two parameters write two rules.
- `Skill(skill:<name>)` deny rules match the skill under any of its names (alias or display name).
- Canonicalized fields are NOT matchable this way: `command` (Bash/PowerShell), `file_path` (Read/Edit/Write), `path` (Grep/Glob), `notebook_path` (NotebookEdit), `url` (WebFetch) — such rules are ignored with a startup warning. Use `Bash(rm *)`, `Read(./path)`, `WebFetch(domain:host)` instead.

### Per-tool specifiers

- `Bash(cmd arg)` / `PowerShell(...)`: command string as a glob, wildcard at any position; recognizes separators (`&&`, `||`, `;`, `|`, `|&`, `&`, newlines) and matches each subcommand independently.
  <!-- markdownlint-disable-next-line MD038 -- the code span deliberately shows a leading space before the asterisk: `:*` is equivalent to a trailing SPACE + `*`, not a bare `*` -->
  `:*` suffix == trailing ` *`, recognized ONLY at the end of a pattern (in `Bash(git:* push)` the colon is literal).
  - `*` matches any text including spaces. A trailing space + `*` also matches the bare command (`Bash(ls *)` matches `ls`) only when it is the rule's only wildcard (`Bash(* --help *)` matches `npm --help x`, not `npm --help`). The space before a trailing `*` is part of the rule: `Bash(ls*)` also matches `lsof`. Put `*` after the subcommand — an allow rule with `*` before it (`Bash(git * main)`) warns at startup and matches every git subcommand and option.
  - Stripped wrappers: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, the builtins `command`/`builtin`, zsh `noglob`, and bare `xargs` (only with no flags). NOT stripped: `command -v`, zsh `nocorrect`.
  - NOT stripped and therefore dangerous in a prefix rule: environment runners `direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec` — `Bash(devbox run *)` matches `devbox run rm -rf .`. Write one rule per inner command instead.
  - Always prompt, never auto-approved by a prefix rule: exec wrappers `watch`, `setsid`, `ionice`, `flock`, and `find` with `-exec`/`-delete`.
  - Leading assignments: an allow rule matches past only known-safe env assignments; a deny/ask rule matches past any (`Bash(rm *)` still catches `FOO=bar rm -rf tmp/`).
  - Compound commands: a deny/ask rule applies when ANY subcommand matches, including one nested in a subshell, command substitution, or control-flow body such as a `for` loop (`Bash(git clean *)` as ask still prompts for `cd /tmp && git clean -f` and `echo "$(git clean -f)"`, even in `auto`); an allow rule must match EVERY subcommand; `npm test &&` with nothing after is unparseable and no allow rule approves it.
  - A Bash rule is NOT a security boundary: it matches the command text as written after splitting and wrapper stripping. A deny/ask `Bash(curl *)` stops `curl …` but not `/usr/bin/curl …` or `sh -c 'curl …'`; `Bash(rm *)` misses `/bin/rm …` and `bash -c 'rm …'`; `Bash(git push *)` misses `git -C . push`, `git -c push.default=current push`, `git 'push'`. For enforcement independent of command text use the sandbox; to inspect the full command text use a `PreToolUse` hook. Argument-constraining rules (`Bash(curl http://github.com/ *)`) are fragile (options before the URL, `https`, redirects, variables) — deny `curl`/`wget` and allow `WebFetch(domain:github.com)` instead, paired with the sandbox allowlist when the restriction must hold.
  - Built-in read-only set (`ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, read-only forms of `git`) runs without a prompt in every mode (except as `permissions.blockReadsOutsideWorkingDirectories` changes for outside paths); the set is not configurable — add an `ask`/`deny` rule to force a prompt. Unquoted globs are fine for commands whose every flag is read-only (`ls *.ts`). Still prompts in Manual: an unquoted glob with write/exec-capable flags (`find`, `sort`, `sed`, `git`), `docker` aimed at another daemon (`-H`, `--context`), `file -m`/`-f`, Windows UNC paths, writes to special shell variables (`PATH`, `IFS`), unparseable commands and commands over 10,000 characters, `cd` into a different directory combined with `git`, and `cd` combined with a redirect other than `/dev/null`.
  - Redirection targets are checked too: `> file`/`>> file`/`2> file` against `Edit` allow/deny + protected paths; `< file` against `Read` allow/deny (`version >= 2.1.257:` for input redirects). A `~`-prefixed target, a glob target, or a relative target following an in-command `cd` always needs approval even when a rule covers it. Not checked: `/dev/null`, fd-forms (`2>&1`), here-docs/here-strings. `version >= 2.1.269:` files a `tee` command writes (incl. mid-pipeline, e.g. `make | tee build.log`) are checked the same way; a `Bash(tee *)` allow rule doesn't cover a destination outside the working directories.
  - PowerShell: cmdlet aliases are canonicalized (`PowerShell(Get-ChildItem *)` also matches `gci`/`ls`/`dir`), matching is case-insensitive, and the AST is parsed so each subcommand is checked.
- `Read`/`Edit`: gitignore-anchored path patterns, NOT plain globs — `//abs` (filesystem root), `/anchored at the settings source`, `~/home`, bare/`./` (cwd). Bare filename matches any depth (`Read(.env)` == `Read(**/.env)`). Merged with sandbox filesystem rules.
  - A `.claudeignore` file has no effect — move its entries into `Read` deny rules. `Read` rules are applied best-effort to Grep/Glob, `@file` mentions, and IDE selection/open-file context. Read/Edit deny rules also cover recognized Bash file commands (`cat`, `head`, `tail`, `sed`, `tee`) and redirect targets, but NOT a command that reads files without naming them (`grep -r pattern .`) or an arbitrary subprocess (a Python/Node script opening files itself) — use the sandbox for OS-level enforcement.
  - Windows: paths are normalized to POSIX form before matching (a `C:` drive path becomes `/c/...`); `//c/**/.env` matches `.env` anywhere on that drive, `//**/.env` on all drives. A deny/ask rule whose path isn't a usable gitignore pattern still guards that exact path; an allow rule with an unusable pattern approves nothing; parentheses in a path need no escaping.
  - `version >= 2.1.210:` file checks match ONLY `Edit(path)` and `Read(path)`. A `Write(path)`, `NotebookEdit(path)`, or `Glob(path)` rule is accepted but never matched, and warns at startup — use `Edit(...)` (covers every file-editing tool) and `Read(...)` (covers Grep/Glob) instead. A path-less tool-name rule such as a bare `Write` deny is unaffected.
  - `version >= 2.1.208:` a `Read` deny rule also blocks `Edit` on the same path, including creating a new file there; `version >= 2.1.228:` also blocks `Write`. `NotebookEdit` is not covered — add an `Edit` deny for paths no tool may change.
  - A deny/ask pattern starting with `!` is a gitignore negation that carves paths out of the `path`/`./path` rules listed BEFORE it in the same source's list (`Read(*.env)` then `Read(!sample.env)`). It is read relative to cwd even after `/`, `~/`, `//`, cannot reopen a file inside a directory a rule blocks whole, and never cancels a deny from another settings source.
  - If the path to edit is itself a symlink, Edit/Write refuse and point Claude to the target. A write through a symlinked directory or from Bash/PowerShell whose resolved target is outside the working directories is not auto-approved in `acceptEdits`, and in `auto` prompts instead of using the classifier unless an allow rule approves; resolving to a protected path the requested path doesn't name prompts instead of routing to the classifier.
  - Single-segment relative dir patterns differ by rule type: `Edit(src/**)` as an ALLOW matches only `<cwd>/src`, but as a DENY/ASK matches a `src` directory at any depth. Every other shape (`/src/**`, `**/src/**`) matches identically in all rule types.
  - Symlinks: an allow rule needs BOTH the link path and its target to match; a deny rule fires when EITHER matches. `version >= 2.1.268:` on macOS/Linux, a deny/ask rule written through a symlinked directory with a `//`, `~/`, or `/` pattern also applies at the directory's real (resolved) location (earlier versions didn't reach the real-location spelling).
  - `/path` anchors at the rule's settings source: project and local → primary working directory, user → `~/.claude`, `--settings <file>` → that file's directory, CLI flags/session rules → primary working directory. A user-settings `Read(/secrets/**)` blocks `~/.claude/secrets/**`, not a project dir — use `//` or `~/` there.
- `WebFetch(domain:host)`: matches URL hostname, case-insensitively, trailing `.` stripped from both sides; `*.example.com` = any subdomain at any depth (not the apex); `domain:*` covers every URL but is NOT the same as bare `WebFetch` (in `deny`, bare removes the tool; `domain:*` keeps it and refuses each fetch). Wildcards need `version >= 2.1.172` to match fetches. A wildcard in any other position matches only between two dots (`example.*` matches `example.org`, not `example.evil.com`). A bare `WebFetch` allow/deny only gates the tool (doesn't touch the sandbox domain list or auto-mode's per-command host list); only a `domain:` rule also opens/closes that host for sandboxed commands. `version >= 2.1.268:` a bare `WebFetch` deny/ask no longer applies to Artifact-page reads (`claude.ai`/`*.claudeusercontent.com`) — only a `domain:` rule covering that host, or an `Artifact` rule, gates those (earlier versions: a bare deny blocked every artifact read, a bare ask prompted before each one).
- `mcp__<server>` / `mcp__<server>__<tool>`: a claude.ai connector tool your org set to `ask` ignores allow rules — it prompts every call even in `auto`/`bypassPermissions` and is denied in `dontAsk`; connector tools appear as `mcp__claude_ai_<server>__<tool>`. In a Cowork session deny rules naming the whole `Bash`/`WebFetch` tool also apply to `mcp__workspace__bash`/`mcp__workspace__web_fetch`; allow rules never carry over.
- `Agent(AgentName)`: gate a subagent — `Agent(Explore)`, `Agent(Plan)`, `Agent(my-custom-agent)`; add to `deny` to disable.
- `Cd(<path-pattern>)`: gates the `/cd` command (not model-invocable); any `Cd` allow rule switches `/cd` to allowlist mode, a bare `Cd` deny disables `/cd` entirely, and deny checks every spelling of the target including each symlink hop. Anchors are shared with Read/Edit but matching is whole-path, not gitignore-style: `*` = exactly one segment, `**` = across segments, and a trailing `/**` also matches its named root.

### Working directories & `/cd`

- Extend file access with `--add-dir <path>` (startup), `/add-dir` (session), or `permissions.additionalDirectories` (persistent). Added directories follow the same permission rules as the launch directory. Most network (UNC) paths can't be added; on Windows map the share to a drive letter and pass it with `--add-dir`.
- Additional directories grant file access, not configuration. Loaded only from `--add-dir`/`/add-dir` directories (not `permissions.additionalDirectories` entries): `.claude/skills/` (live reload), `.claude/commands/` and `.claude/agents/` (no live reload; the project's own same-named command wins), `enabledPlugins` and `extraKnownMarketplaces` from their settings files, and CLAUDE.md/`.claude/rules/`/`CLAUDE.local.md` only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Output styles come from the cwd and parents, `~/.claude/`, and managed settings. Hooks and other `.claude/settings.json` keys load from the cwd's `.claude/` with no parent fallback.
- `version >= 2.1.257:` `/add-dir` on a subdirectory of the primary working directory loads its skills/commands/subagents for the rest of the session without prompting and without adding a working directory.
- `/cd <path>` moves the primary working directory, keeps the conversation, loads the new directory's `CLAUDE.md`, and prompts for trust if needed. It applies the new directory's project settings (permission rules, hooks), `.mcp.json` servers (same approval as startup; local-scope servers too), plugins its settings enable, skills, subagents, and `env` values (layered on top of the previous directory's, which stay in effect); disconnects the previous directory's project/local MCP servers and servers of plugins no longer enabled; takes `additionalDirectories` from the new directory's settings but keeps `--add-dir`/`/add-dir` directories. Hooks still receive `${CLAUDE_PROJECT_DIR}` set to the project root where the session started. An untrusted target's trust prompt lists the allow rules, directories, hooks, and helper commands it would activate. `version >= 2.1.246:` this applies immediately; earlier versions waited for a resumed session. Gate targets with `Cd` rules.

`permissions.allow` rules in settings do NOT pre-approve these writes; the check runs before allow rules are evaluated. In modes that prompt, a `.claude/` write offers **Yes, and allow Claude to edit its own settings for this session**, which covers later `.claude/` writes that session.

- `bypassPermissions`: only use in isolated environments (containers/VMs); refuses to start as root/sudo on Linux/macOS unless in a recognized sandbox. Admins block it via `permissions.disableBypassPermissionsMode: "disable"`. Can't be entered from a session started without it enabled: start with `--permission-mode bypassPermissions` / `--dangerously-skip-permissions` (or `permissions.defaultMode: "bypassPermissions"` in user/`--settings`/managed settings); `--allow-dangerously-skip-permissions` only adds it to the Shift+Tab cycle without activating it. First interactive use shows a warning dialog; accepting sets `skipDangerousModePermissionPrompt` in `~/.claude/settings.json` (declining exits; `-p` shows no dialog; a `--bg` background session is refused until accepted once interactively). Also refused under `--restricted`.
- `defaultMode: "auto"` (`version >= 2.1.142:`) and `defaultMode: "bypassPermissions"` (`version >= 2.1.257:`; any file before that) are ignored from project/local settings — set them in user/managed settings, or pass `--permission-mode` for one session. Claude Code on the web additionally ignores `dontAsk` and `bypassPermissions` as `defaultMode` from EVERY settings file.
- `auto` mode mechanics: classifier checks each non-trivial action; drops broad code-exec allow rules (`Bash(*)`/`PowerShell(*)`, wildcarded interpreters, package-manager run commands, `Agent` allows, and `version >= 2.1.236:` `Monitor` allows) on entry, restores on exit — set `autoMode.classifyAllShell` to suspend ALL shell allow rules. Pauses to prompting after 3 consecutive or 20 total blocks (not configurable; an allowed action resets only the consecutive counter). Subagent task descriptions are pre-checked `version >= 2.1.178:`. `version >= 2.1.199:` an MCP tool with `_meta["anthropic/requiresUserInteraction"]` skips the classifier and always prompts directly instead.
- Classifier inputs: user messages, tool calls, CLAUDE.md — tool RESULTS are stripped. It trusts the working dir and the remotes configured at session start; `version >= 2.1.200:` a remote added/repointed mid-session with `git remote add`/`set-url` is NOT trusted. Boundaries you state in conversation ("don't push") block matching actions but are re-read from the transcript, so compaction can lose them — use a deny rule for a hard guarantee.
- `version >= 2.1.210:` the classifier itself runs on Sonnet 5 by default (not your `/model`; a classifier model Anthropic configures server-side takes precedence), falling back to the session's model when the first auto-mode request finds Sonnet 5 unavailable, the session runs Sonnet 4.6, or `availableModels` excludes Sonnet 5, or to an Opus model on a Fable-model session (off the Anthropic API: `ANTHROPIC_DEFAULT_OPUS_MODEL`, else Opus 5, without consulting the allowlist). `version >= 2.1.198:` sandbox network verdicts are cached per host+port instead of re-checked per connection.
- Auto-mode review scope: the classifier also reviews each subagent's finished work and final report before the parent reads it (a flag, or a separate API safety check refusing the review, still delivers the report prefixed with a security warning; an unavailable classifier delivers it with a verify-first note); a subagent's `permissionMode` frontmatter is ignored. Before a command that would discard uncommitted work (`git reset --hard`, `rm -rf`) Claude Code runs `git status` itself and shows the classifier whether staged, modified, or untracked work exists (untracked files reported even with `status.showUntrackedFiles=no`). Pushing to any branch of the current repo and creating a matching PR run without a prompt unless the blocked list applies (secrets/sensitive data leaving the repo, a PR targeting another repo or org); add `permissions.ask` rules (matched against the command as written) for a human checkpoint. Reads and working-directory edits outside protected paths skip the classifier. In `-p` without `--permission-prompt-tool` repeated blocks have no prompt to fall back to: the action doesn't run and Claude keeps working. A denial from a separate safety check refusing the classifier's own request counts toward neither threshold. `/auto-mode-setup` drafts `autoMode.environment` entries (needs feature-flag fetching).
- Server-side classifier review (`version >= 2.1.271:`): in `auto` the server can review actions as part of the session's model requests instead of Claude Code sending its own classifier requests. Asks by default: direct Anthropic API — interactive terminal `version >= 2.1.271` on Pro/Max/Team and `version >= 2.1.278` on Enterprise/API accounts, `-p`/Agent SDK/VS Code/desktop `version >= 2.1.281`, any session that doesn't fetch feature flags `version >= 2.1.282`; Claude Platform on AWS/Bedrock/Agent Platform/Foundry or any `ANTHROPIC_BASE_URL` gateway `version >= 2.1.278`; signed-in Claude apps gateway `version >= 2.1.280`. If the server doesn't review the session Claude Code falls back to its own requests; if it gives no verdict for an action the action is denied (turn stops after ten responses in a row with no verdict). `CLAUDE_CODE_AUTO_MODE_SERVER=0` always uses Claude Code's own requests; with `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` and the variable unset it also stops asking (apart from the exceptions the LLM gateway protocol docs describe).
- Feature-flag fetching is skipped when `DISABLE_GROWTHBOOK`, `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set, on a third-party provider (unless a host sets `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`), and in Claude apps gateway sessions.
- Starting-mode resolution for a new terminal session, first match wins: `--permission-mode`/`--dangerously-skip-permissions`; `permissions.defaultMode` from a settings file (`auto`/`bypassPermissions` set in project/local are ignored and the session uses the built-in default, or Manual for `bypassPermissions`); built-in default. Built-in default: any settings file with `disableAutoMode: "disable"` → `default`; `-p`/Agent SDK → `default` when the session fetches feature flags, otherwise (third-party provider, telemetry off) `auto` with `version >= 2.1.285` and `default` earlier, and `default` when org policy withholds the `auto` default; an eligible session in an org with the HIPAA configuration applied → `default` with `version >= 2.1.285` (auto stays selectable via Shift+Tab, `--permission-mode auto`, or `permissions.defaultMode: "auto"` in user/managed settings); terminal/VS Code → `auto` with `version >= 2.1.283` (earlier: `auto` on Pro/Max/Team in sessions that fetch feature flags, `default` otherwise). A selected `auto` that is unavailable (unsupported model, settings off, server-side off) starts in Manual. The VS Code extension never reads project settings for the starting mode and reads `claudeCode.initialPermissionMode` (`default`/`manual`/`acceptEdits`/`plan`/`bypassPermissions`, not `auto`) first.
- Shift+Tab cycle from `auto`: `default` → `acceptEdits` → `plan`, then enabled optional modes (`bypassPermissions` first, `auto` last); `dontAsk` is never in the cycle (set it with `--permission-mode dontAsk`); cycling to `auto` needs no confirmation. The status bar shows `⏸ manual mode on` for `default`. `version >= 2.1.247:` in Manual/`acceptEdits`, a Bash prompt can offer **Yes, and switch to auto mode** (not on PowerShell prompts, nor prompts forced by an `ask` rule or hook).
- The classifier also reviews each `SendMessage` to another agent before delivery, in `auto` and in plan mode while the classifier reviews commands (`version >= 2.1.222`). A PostToolUse hook's `classifierContext` field annotates a result for the classifier (`version >= 2.1.236`).
- The classifier's default blocked/allowed-by-default action lists have grown across releases (`version >= 2.1.211`: commits/pushes that would send secrets outward, pushing to any branch of the current repo allowed by default, except a branch named like a deploy/publication target such as `production` or `gh-pages`, which is judged on its own terms; earlier only the starting branch, Claude-created branches, and routine default-branch pushes; `version >= 2.1.257`: cloud instance-metadata credential requests, node-identity credential reads, and sibling-container/pod/VM access now blocked by default; `version >= 2.1.261`: posting a link to a public paste/data-sharing service where the URL itself carries the shared content; also `version >= 2.1.198`: `git commit --amend` on an already-pushed commit; `version >= 2.1.203`: content from a sensitive local store (session transcripts, SSH/cloud credentials, browser profiles, shell history) entering a commit, push, PR/issue text, gist, or publish unless you named source and destination; `version >= 2.1.205`: writes to session transcript `.jsonl` files under `~/.claude/projects/`, and a recursive forced delete whose target is a shell variable unassigned in the visible conversation — name the exact path or re-run with the resolved literal path to clear it). Blocked by default, no version gate in the docs (sample): `curl | bash`, force push, production deploys, `git reset --hard`/`git clean -fd`-style discards, amending a commit not created this session, merging an unapproved PR, changing `git remote` unless you named the new remote. Run `claude auto-mode defaults` for the live, authoritative list rather than relying on a fixed enumeration here; narrow false positives via `autoMode.environment`.
- `--resume` restores the permission mode that was active at defer-time; exceptions: `plan` and `bypassPermissions` are never carried over.

### Critical paths (`rm`/`rmdir`)

- Critical-path targets: filesystem root, top-level directories (`/usr`, `/etc`), home, Windows drive roots and their top-level dirs, the working directory and its parents, and additional directories and their parents only for a glob under them (`rm -rf <dir>/*`).
- Also critical: a glob or trailing slash directly under a shell variable or positional parameter (`rm -rf "$DIR"/*`, `"$1"/*`), a variable plus one common top-level name (`"$TMPDIR/mnt"`), a variable assigned from a directory-printing substitution (`D=$(pwd); rm -rf "$D"`), a recursive `rm` whose target is only command-substitution output, a trailing substitution after a critical path (`~/$(cmd)`), a lone backslash target, and some targets ending in `/*` or `/*/` (`rm -rf logs/*/*`, `cd logs && rm -rf a/*`). Nested forms (subshell, brace group, command/process substitution, `sh -c`/`bash -c` scripts) are inspected: a double-quoted `-c` script has its variables expanded by the invoking shell first (`find . -exec sh -c "rm -rf \"$1\"/*" _ {} \;` is flagged), while a single-quoted script that binds `$1` to a real value (`sh -c 'rm -rf "$1"/*' _ {}`) is not. Rewrite `"$DIR"/*` as `"${DIR:?}"/*` (a fully guarded removal passes and runs without a prompt in `bypassPermissions` unless another check flags it) or a literal path; for `$HOME`-style variables, a variable assigned from a directory-printing substitution (`"${D:?}"` does NOT clear it), or substitution-only output, use a literal path / run the substitution first and remove the printed paths. Per-check switches, set in the launching environment (ignored in a settings `env` block): `CLAUDE_CODE_DISABLE_SUBSTITUTION_RM_PROMPT=1` (substitution-only target), `CLAUDE_CODE_DISABLE_INLINE_SHELL_RM_PROMPT=1` (`version >= 2.1.288:` a critical path typed directly in a `-c` script).
- No `permissions.allow` rule and no `PreToolUse` `"allow"` approves them in any mode; a deny rule still blocks outright. Outcome: `default`/`acceptEdits`/`plan` ask; `auto` asks in the terminal with a two-minute countdown and denies where no terminal prompt can show (`-p`, Agent SDK, VS Code chat panel, Desktop); `dontAsk` denies; `bypassPermissions` asks (countdown in the terminal). A matching `ask` rule asks without a time limit. Expired countdown → denied; after three unanswered prompts in a session further removals are denied immediately. `version >= 2.1.281:` the countdown handling; turn it off with `CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT=1`.
- PowerShell tool (when enabled): `Remove-Item` on a system path (root, top-level dirs, drive roots, home) or a wildcard target (bare `*`, `/*`, `\*`) is denied in every mode before the classifier sees it; on the working directory or a parent with `-Recurse` it follows the mode's normal flow (`bypassPermissions` skips it). `version >= 2.1.283:` the system-path denial also covers `rd`/`rmdir`/`del`/`erase` run through `cmd`.

### Effort levels

`low`/`medium`/`high`/`xhigh`/`max` (model-dependent; `xhigh` `version >= 2.1.111` as a capability). Set via `/effort`, `--effort`, `CLAUDE_CODE_EFFORT_LEVEL` (highest precedence), the `effortLevel` setting, or skill/subagent frontmatter `effort`. `low`/`medium`/`high`/`xhigh` persist (saved per-model in `modelSettings`, or via `effortLevel` as the fallback default); `max` is session-only. `ultracode` persists only through its own boolean `ultracode` setting. `ultrathink` in a prompt requests deeper reasoning for that turn without changing the level.

- Support: Fable 5.1 / Fable 5 / Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Opus 5 / Sonnet 5 / Opus 4.8 / Opus 4.7 take all five; Opus 4.6 and Sonnet 4.6 have no `xhigh`; models not listed don't support effort. An unsupported level falls back to the highest supported level at or below it (`xhigh` runs as `high` on Opus 4.6). Default is `high` everywhere except Opus 5.5, Sonnet 5.5, and Haiku 5.5 (`medium`) and Opus 4.7 (`xhigh`); an org-set default effort for the org default model applies to that model.
- Resolution order, first match wins: `CLAUDE_CODE_EFFORT_LEVEL` / `--effort` / `/effort`; saved settings (per-model `modelSettings` level or `effortLevel`); the model's default. A top-level `effortLevel` in USER settings doesn't set the level for Opus 5.5 or models released after it (they start at their own default until you choose a level with `/effort` or the `/model` picker); a top-level `effortLevel` in project/local/managed settings or `--settings` applies to every model. In `-p` runs `/effort` applies to that session only.
- After an automatic model fallback the session keeps the effort level the flagged request ran at instead of the fallback model's default, unless settings or an org default for that model set one, or you choose a level, pick a model, or resume.
- `max` is session-only EXCEPT when set through `CLAUDE_CODE_EFFORT_LEVEL`. `CLAUDE_CODE_EFFORT_LEVEL=auto` resets to the model default; `/effort auto` clears your saved level for the active model; `/effort status` shows the level in effect. Skill/subagent frontmatter `effort` overrides the session level while it runs but not `CLAUDE_CODE_EFFORT_LEVEL`, and a `maxEffortLevel` or org cap still limits it. A managed `effortLevel` applies at the settings step (users can still change the level with `/effort`/`--effort`; use `maxEffortLevel` to hold a ceiling). A level picked from a Remote Control phone/browser control applies to that session only (`version >= 2.1.234`).
- `ultracode` is a Claude Code setting, not a model level: Claude orchestrates dynamic workflows for substantive tasks at whichever effort level the session runs at. One-session toggle via `/effort ultracode`, the `/effort` slider (Tab flips the toggle, Enter applies), or `--effort ultracode` (`version >= 2.1.203`; also sets `xhigh`, as does the Agent SDK `effortLevel: "ultracode"`); persists across sessions only via the dedicated `ultracode` boolean setting (settings file, `--settings`, or an Agent SDK control request). `version >= 2.1.284:` `/effort ultracode off`, the slider toggle, and keeping ultracode on at levels other than `xhigh` work, and toggling it leaves the level unchanged (earlier: turning it on set `xhigh`, picking another level turned it off, an effort cap below `xhigh` made it unavailable). Neither `effortLevel` nor `CLAUDE_CODE_EFFORT_LEVEL` accepts it; if `CLAUDE_CODE_EFFORT_LEVEL` or an effort cap sets the level, ultracode stays on at that level. Unavailable when workflows are off or the model lacks `xhigh` (`--effort ultracode` then starts with it off at the highest level the model and cap allow, up to `xhigh`).
- `version >= 2.1.195:` Enterprise admins can cap the max effort level per model per custom role (org config, not a settings key); levels above the cap are hidden from `/effort` and a higher request runs at the cap instead.
- `version >= 2.1.257:` the `/effort` slider / `/model` picker's `Enter` key saves a level as your per-model default (`modelSettings`); its `s` key applies the level to the current session only.
- `version >= 2.1.267:` `maxEffortLevel` setting caps the effort level any session may reach; the lowest cap from any scope (including `--settings`) applies, overriding even a higher managed cap.

### Fallback chains

```json
{
  "fallbackModel": ["claude-sonnet-4-6", "claude-haiku-4-5"]
}
```

- Position carries meaning; the highest-precedence scope that defines `fallbackModel` supplies the entire chain. Capped at 3 models after dedup; `--fallback-model` flag overrides; `"default"` expands to the default model.
- Switch lasts the current turn only; only fires on overload/unavailable/non-retryable server errors — never auth/billing/rate-limit/request-size/transport errors, nor a denial by an org policy check.
- Elements outside `availableModels` or pointing at a retired model are dropped/skipped.
- `version >= 2.1.178:` the chain also covers compaction, but never falls back to a model with a SMALLER context window than the primary's; if every fallback is smaller, compaction surfaces the original error.
- Separate from content-based fallback (`version >= 2.1.219`; safety-classifier flags on the Fable models, Opus 5.5, Sonnet 5.5, and Opus 5): from Fable 5.1 / Fable 5 / Opus 5.5, biology-flagged requests re-run on Opus 5 and cybersecurity-flagged ones on Opus 4.8; from Sonnet 5.5, cybersecurity re-runs on Sonnet 5 while biology ends in a refusal; from Opus 5, cybersecurity re-runs on Opus 4.8 while biology ends in a refusal (no biology fallback model). An excluded fallback target means refusal instead. `switchModelsOnFlag: false` pauses with a choice instead of switching automatically (no prompt where there's no fallback or the target is blocked). On Bedrock/Agent Platform/Foundry fallback only runs when Claude Code can identify the models: pin `ANTHROPIC_DEFAULT_OPUS_MODEL` (and `ANTHROPIC_DEFAULT_FABLE_MODEL` for Fable sources, `ANTHROPIC_DEFAULT_SONNET_MODEL` or a Sonnet 5 entry for Sonnet 5.5) or map via `modelOverrides`; otherwise the request ends with a refusal. The fallback target must also have a context window at least as large as the session's. A flag can fire on the first request from workspace context alone (CLAUDE.md, git status): test with `claude --safe-mode`. `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` turns the automatic switch off. `/config` → **Switch models when a message is flagged** → **Ask each time** equals `switchModelsOnFlag: false`; the first flagged switch in an interactive session may ask whether to switch automatically from then on and saves the answer as that key (dismissing saves nothing). No prompt in subagents (re-run on the fallback), in non-interactive/SDK sessions that can't show it (the turn ends with a refusal), or when `availableModels` blocks the target. After a fallback the session stays on the fallback model until you run `/model`.
- `version >= 2.1.247:` the chain also covers subagents — a subagent whose request fails over tries the configured fallback models in order and continues on the one that accepts it, instead of ending the subagent (earlier versions ended it on such a failure); the parent session's model is unchanged.

### Merge behavior

- `availableModels` set only in user/project/local: arrays merge + dedup.
- `availableModels` (or `enforceAvailableModels`) set in managed/policy: replaces the merged result entirely; lower scopes cannot widen. `version >= 2.1.175:` this is the only way to enforce a strict allowlist (earlier versions merged the managed list). Admin-deployed managed sources do NOT merge with each other, so deploy the pair in the highest-precedence managed source — a list in a managed settings file is ignored once the admin console delivers any keys.
- `availableModels: []` blocks named selections but leaves the account-type Default usable, so `enforceAvailableModels` cannot lock users out of every model.
- `modelOverrides` maps Anthropic IDs → provider IDs; allowlist still matches the Anthropic ID, not the override value.
- Within the effective list, an entry naming a specific model in a family (a version prefix or full ID) disables that family's wildcard entry: `["sonnet", "claude-sonnet-4-5"]` allows only Sonnet 4.5, not every Sonnet model.
- All other model arrays follow the standard concatenate-and-deduplicate rule.
- With `deniedModels`/`availableModelsMatch: "exact"` (`version >= 2.1.283`, managed only), a blocked model is hidden from `/model`, rejected by `/model <name>`, and dropped at startup (the Default option resolves instead); a hook or background request naming a denied model runs on the session's model. A Default that would resolve to a blocked model steps down: newest permitted version of the same family, then the newest permitted Sonnet, then Haiku, then the first permitted `availableModels` entry; if none is permitted a session starting on Default refuses to start.
- Allowlist coverage also includes: `ANTHROPIC_DEFAULT_*_MODEL` (cannot redirect an allowed alias outside the list), `/fast`, subagent/teammate/skill models, `advisorModel`/`--advisor`, and plan-mode upgrades. On the Anthropic API and Claude Platform on AWS a blocked family alias (`opus`/`sonnet`/`haiku`/`fable`) substitutes the newest permitted version of that family (`version >= 2.1.205`; `version >= 2.1.222` for subagents). Entries starting with `anthropic.` become custom picker options when the Bedrock Mantle endpoint is enabled and count as specific entries.
- Org-level restrictions (Enterprise admin console, `version >= 2.1.187`) apply alongside `availableModels`: a model is selectable only when both permit it; they reach Anthropic API and LLM-gateway sessions only. A restricted model is hidden from `/model`; naming it via `--model`/`ANTHROPIC_MODEL`/`model` starts on an allowed model with a notice, `/model <name>` is rejected, and a family alias substitutes the newest permitted version of the family. Haiku models are always available and can't be disabled (every member keeps one usable model); admins can restrict org-wide or per custom role (a member with several roles gets the union); an access change takes effect on new requests within about a minute. The org default model (Enterprise, `version >= 2.1.196`) is a starting point, not a lock: `--model`, `ANTHROPIC_MODEL`, managed/`--settings` `model`, and a user/project/local `model` (incl. a `/model` save) outrank it unless the admin turned on override; it is read once at startup and reaches only Anthropic API sessions (use managed `model` elsewhere).

### Context window & auto-compaction

- Native 1M window with no `[1m]` suffix: Fable 5.1, Fable 5, Sonnet 5 and later, Haiku 5.5, Opus 4.7 and later (also on Bedrock/Agent Platform/Foundry/Claude apps gateway). Opus 4.6 and Sonnet 4.6 reach 1M only through `[1m]` (Opus 4.6 1M is included on Max/Team/Enterprise and needs usage credits on Pro; Sonnet 4.6 1M needs usage credits on every plan; Claude Code checks this only on a direct Anthropic API connection). 1M uses standard pricing with no premium above 200K, except Haiku 5.5 (costs more on prompts over 100K tokens).
- With no auto-compact window set, Claude Code compacts at the model's context limit, except: cloud sessions (as the conversation approaches the limit), Sonnet 4.6/Opus 4.6 without extended context (200K boundary), native-1M models under `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` (200K boundary; setting a larger window doesn't lift the hold), native-1M models otherwise (before the window fills, ~967K), and unrecognized model IDs (the window Claude Code assumes for the ID). With auto-compaction off a held 200K session stops at the context-limit error.
- Behind an LLM gateway each recognized model gets its Anthropic-API window; if the gateway rejects requests above 200K set `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000` so every model compacts there.
- Correcting the window for a custom ID with `CLAUDE_CODE_MAX_CONTEXT_TOKENS`: an unrecognized provider/custom spelling (not starting `claude-`, or carrying a stripped suffix such as `@YYYYMMDD` — `version >= 2.1.259:` counts the stripped suffix) without `[1m]` applies it directly and compaction continues at the declared window; the same spelling WITH `[1m]` assumes 1M and the variable applies only if `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` is also set (a declared window above 200K then shows a startup warning that the 200K limit isn't enforced); an ID that resolves to a recognized model (e.g. `anthropic/claude-opus-4-8`, `us.anthropic.claude-…-v1:0`, `claude-sonnet-4-5@20250929`) or a bare `claude-` name takes effect only with `DISABLE_COMPACT=1`. `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1` compacts only after a recognized too-long API error.
- Pinned third-party IDs: a model with a native 1M window runs at 1M without a suffix when the pinned ID contains its Anthropic API ID (`us.anthropic.claude-opus-4-8` contains `claude-opus-4-8`) or a `modelOverrides` entry maps it; an unmatched pinned ID runs at 200K unless it carries `[1m]`. Setting an `ANTHROPIC_DEFAULT_*_MODEL` variable replaces the family's built-in `/model` rows (incl. 1M rows) with one row; `/model opus[1m]` still applies the suffix to the variable's model. A matched provider ID in an `availableModels` allowlist must be the full provider-form ID (`us.anthropic.` prefixes aren't stripped) or mapped via `modelOverrides`; an allowlist delivered by MDM/managed file applies on third-party providers, server-managed settings aren't delivered there.

## Output styles

Output styles modify the system prompt to set role, tone, and output format. They do not change Claude's knowledge.

### Discovery

Output styles are markdown files loaded from:

- User: `~/.claude/output-styles/`
- Project: `.claude/output-styles/`
- Managed policy: `.claude/output-styles/` inside the managed settings directory
- Plugins: `output-styles/` inside the plugin directory

### Built-in styles

| Style       | Behavior                                                                                                                                                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Default     | Built-in software-engineering system prompt (no style selected; `default` appears in the `/output-style` list; the four other built-ins keep it and add their own instructions)                                                                                                                              |
| Proactive   | Executes immediately, makes reasonable assumptions on routine decisions, doesn't enter plan mode unless asked; instructed (not enforced) to check in the conversation before deleting data or changing shared/production systems. Doesn't change the permission mode, so permission prompts appear as before |
| Concise     | `version >= 2.1.237:` Leads with the result, skips preamble/narration, short by default; full detail on request; always keeps full error-report/security-warning/destructive-action-confirmation text                                                                                                        |
| Explanatory | Adds educational "Insights" while doing software-engineering tasks                                                                                                                                                                                                                                           |
| Learning    | Collaborative learn-by-doing; adds `TODO(human)` markers for you to implement                                                                                                                                                                                                                                |

Project styles load from every `.claude/output-styles/` between cwd and repo root; `version >= 2.1.178:` on a name collision the directory closest to cwd wins.

### Frontmatter

| Field                      | Purpose                                                                                                                                 | Default   |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| `name`                     | Style name if not the file name                                                                                                         | file name |
| `description`              | Shown in the `/config` picker                                                                                                           | none      |

### Custom styles

- Create `<name>.md` in a discovery directory. In the terminal, style files are read at startup — restart Claude Code to pick up a file created or edited mid-session.
- Custom styles add their instructions to the end of the system prompt and drop built-in software-engineering instructions unless `keep-coding-instructions: true`. That section exists only in the full system prompt — on the shorter prompt `keep-coding-instructions` has no effect; set `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0` to select the full prompt on any model. A style's instructions are sent with every request (prompt caching offsets the input cost after the first request); Explanatory/Learning lengthen output, Concise shortens it. In the VS Code extension the **Output styles** menu can also create a style file (`version >= 2.1.261`).
- All output styles (built-in and custom) trigger reminders to Claude to adhere to style instructions during the conversation.
- Output styles are **not** loaded from `--add-dir` directories (only the current working directory, parents, `~/.claude/`, and managed settings).
- Styles apply to the MAIN conversation only: a subagent runs its own system prompt, so a style never changes how it responds. A fork is the exception — it inherits the parent's full system prompt.
- An output style is an instruction Claude follows, not a guarantee. Use it for voice/length/format/role across a whole session; project conventions → CLAUDE.md (stays loaded whichever style is active); instructions for one kind of task → a skill; something that must happen every time (format after each edit, block a command) → a hook; a focused helper with its own model/tools → a subagent; an addition passed at launch → `--append-system-prompt`. They combine.

### Activate

Run `/config` → **Output style** or `/output-style <style>` (both save to `.claude/settings.local.json`; `/output-style` ignores case), or set the `outputStyle` field directly (case-sensitive: `explanatory` gives the Default style; a project's settings files take precedence over a `~/.claude/settings.json` value). The VS Code extension has an **Output styles** menu in the `/` command menu (`version >= 2.1.257`); in the desktop app set `outputStyle` in a settings file. `version >= 2.1.251:` a mid-session switch applies starting with your NEXT message (earlier versions waited for `/clear` or a new session). The standalone `/output-style` command was deprecated v2.1.73 and removed v2.1.91; `/output-style <style>` remains (lists/marks current with no arg). `version >= 2.1.269:` `/output-style` also works in `-p`/Agent SDK/Remote Control sessions (Remote Control lists/selects built-in styles only).

## Statusline

A customizable bar at the bottom of Claude Code's interface. Configured via `statusLine` in settings.

### Configuration

```json
{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh",
    "padding": 2
  }
}
```

| Field                  | Description                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `type`                 | Must be `"command"`                                                                                                            |
| `command`              | Shell command or path to script; runs on each status refresh                                                                   |
| `padding`              | Optional integer; horizontal padding around the output (default `0`)                                                           |
| `refreshInterval`      | Optional; re-run the command every N seconds (min `1`) on top of event-driven updates; use for time-based data or idle periods |
| `hideVimModeIndicator` | Optional boolean; suppress the built-in `-- INSERT --` text when the script renders `vim.mode` itself                          |

- Use `/statusline <description>` to have Claude Code generate a script and configure `statusLine` automatically.
- Script receives JSON on stdin; print one or more lines to stdout; each line becomes a row. Runs once at session start (including on resume), then after each assistant message, after `/compact`, on permission-mode change, on vim-mode toggle, on a `command` change in `statusLine` (skips the debounce), on each `refreshInterval` tick, when a `rate_limits` window reaches its `resets_at`, and when a warm `prompt_cache` reaches its `expires_at`; debounced 300ms; in-flight execution cancelled on a new trigger.
- Forward slashes in `command` paths; `~` expands to home directory on all platforms.
- `version >= 2.1.153:` read terminal size from `COLUMNS`/`LINES` env vars (`tput cols` cannot read it).
- Requires workspace trust (blank until accepted; `claude --debug` logs `Status line command skipped: workspace trust not accepted`); disabled when `disableAllHooks: true` outside managed settings, where only a managed `statusLine` still runs; with `allowManagedHooksOnly` only a managed `statusLine` runs.
- Output goes through a captured pipe: size to the terminal via `COLUMNS`/`LINES`, ANSI colors and OSC 8 links are supported; `claude --debug` logs the script's stderr on every invocation and its exit code on the first.
- Windows: Claude Code routes through Git Bash when available, PowerShell otherwise.
- Output is shown only after the script exits `0`: a non-zero exit or empty output blanks the status line; a slow script blocks updates until it finishes (a new trigger cancels the in-flight run) — keep it fast and cache slow calls (e.g. `git status`). Fields may be `null` before the first API response: read with fallbacks (`// 0` in jq). The line hides temporarily during the help menu and permission prompts, runs locally, and consumes no API tokens. Multiple lines, ANSI colors, and OSC 8 links (Cmd/Ctrl+click; needs iTerm2/Kitty/WezTerm; Terminal.app doesn't support them; `FORCE_HYPERLINK=1` overrides detection) are supported. Prefer `printf '%b'` over `echo -e` for escape sequences; complex multi-line escape output is more prone to display glitches.
- A custom status line renders in its own row above the footer badges and removes most footer keyboard hints (`esc to interrupt`, `? for shortcuts`, `hold space to speak`); the `footerLinksRegexes` setting adds footer link badges without a script. Outside fullscreen rendering notifications share the status-line row (right side; verbose mode adds a token counter; narrow terminals may truncate the line).

### `subagentStatusLine`

Same object shape (`type`/`command`); renders a custom row body per subagent in the agent panel. stdin = base hook fields + `columns` + a `tasks` array (each: `id`, `name`, `type` (`local_agent`), `agentType`, `status` (`running`/`completed`/`failed`/`killed`), `description`, `label`, `startTime` (epoch ms), `model`, `effort`, `contextWindowSize`, `tokenCount`, `tokenSamples` (last 16 readings), `cwd`); `agentType` is the subagent type the task runs as (built-in `Explore` or a custom name; same value hooks receive as `agent_type`) and requires `version >= 2.1.293`. `model` (resolved model ID) and `contextWindowSize` (that model's window in tokens) require `version >= 2.1.205` and are omitted for a task whose model isn't resolved yet. `effort` requires `version >= 2.1.213`, reports the configured value as written (an effort-level string or a numeric token budget — the applied effort may differ if the model lacks that level), and is absent when the subagent inherits the session level. Emit one JSON line per overridden row: `{"id":"<task id>","content":"<row body>"}`; omit `id` to keep default; empty `content` hides the row. Plugins can ship a default in their `settings.json`, but unlike hooks a plugin's value does not run under `allowManagedHooksOnly` even when the plugin is force-enabled in managed `enabledPlugins`; the same workspace-trust and `disableAllHooks` gates as `statusLine` apply. Runs once per refresh tick with all visible rows in one JSON object.

## Sandboxed Bash tool

OS-level filesystem and network isolation for Bash commands. Platform: macOS, Linux, WSL2.

### Scope, modes & known limits

- Covers Bash, PowerShell, and Monitor commands and the processes they start; native Windows runs commands unsandboxed (use WSL2). Built on `@anthropic-ai/sandbox-runtime`; off by default. Linux/WSL2 need `bubblewrap` and `socat` (ripgrep is bundled; the seccomp filter via `npm install -g @anthropic-ai/sandbox-runtime` is optional and adds Unix-socket blocking); on Ubuntu 24.04+ an AppArmor profile for `bwrap` may be needed when `kernel.apparmor_restrict_unprivileged_userns` is `1`.
- `/sandbox` panel tabs: **Mode** (auto-allow vs regular permissions), **Overrides** (`allowUnsandboxedCommands`), **Config** (resolved settings; lists **Denied within allowed** paths), plus **Dependencies** on Linux/WSL2 when something is missing (restart after installing). Mode choices save to `.claude/settings.local.json`; enable across projects via `sandbox.enabled` in user settings. `/sandbox` refuses with `Sandbox settings are overridden by a higher-priority configuration` when managed settings or `--settings` set `sandbox.enabled`, `autoAllowBashIfSandboxed`, or `allowUnsandboxedCommands`.
- Runs OUTSIDE the sandbox: built-in Read/Edit/Write/WebFetch/WebSearch (they follow permission rules — `denyRead` doesn't stop the Read tool, `allowedDomains` doesn't limit WebFetch), command hooks, local MCP servers, plugin monitors, LSP servers, helper commands (status line, `apiKeyHelper`), processes a mod starts, commands typed at the `!` prompt in most sessions, `excludedCommands` matches, and unsandboxed retries. Subagents use the parent session's sandbox; a background session sandboxes when its own settings enable it. To put those behind a boundary too, run Claude Code itself in a container, VM, the sandbox runtime, or the dev container.
- Sandbox modes: **auto-allow** approves sandboxed commands without a prompt; explicit deny rules, critical-path `rm`/`rmdir`, and content-scoped ask rules (`Bash(git push *)`) still apply, and a bare `Bash` ask rule is skipped for sandboxed commands except in plan mode. It works independently of the permission mode except plan mode, an `auto`-mode command carrying per-command allowed domains, and server-side classifier review. **Regular permissions** sends every Bash command through the normal flow even when sandboxed.
- Unsandboxed retry (`dangerouslyDisableSandbox`) approval: `bypassPermissions` runs it without a prompt; Manual/`acceptEdits` prompt "Bash command (unsandboxed)"; `auto` has the classifier judge the underlying command; `dontAsk` denies; plan mode follows its own gating. A matching allow rule (`Bash(curl *)`) also approves the retry with no prompt; an ask rule `Bash(dangerouslyDisableSandbox:true)` forces a prompt (also in `auto`/`bypassPermissions`) and outranks a matching allow. When the sandbox blocks a connection Claude Code names the denied host in the command result. `permissions.blockReadsOutsideWorkingDirectories` makes some retries prompt even in `auto`/`bypassPermissions`.
- `$TMPDIR`: sandboxed commands get the per-user temp directory (unless `filesystem.disabled`); unsandboxed commands inherit the shell's `$TMPDIR`, falling back to a `CLAUDE_CODE_TMPDIR` override or the OS temp dir when unset/empty — pass files between the two via the working directory.
- Network: no direct route out; a proxy on your machine checks each host against allowed/denied domains (Linux/WSL2: separate network namespace; macOS: Seatbelt). Tools that read the proxy variables (`curl`, `npm`, `git` over HTTPS) connect once the host is allowed (an `allowedDomains` entry with no port allows every port); tools that ignore them (plain `ssh`, most database drivers) can't connect even to an allowed host; anything non-TCP (UDP, HTTP/3 over QUIC, `ping`) can't leave. Symptoms: `Operation not permitted`/`Could not resolve host` (macOS) or `Network is unreachable` (Linux/WSL2); a proxy-using tool to a non-allowed host gets a prompt or a `403`. Fix by running that command outside with `excludedCommands` (pair it with an `ask` rule). On macOS git over SSH fails even for an allowed host (switch the remote to HTTPS or exclude `git fetch *`/`git pull *`/`git push *`); on Linux/WSL2 it works once the host is allowed on port 22 and the key is readable (the sandbox can block the `ssh-agent` socket; a `denyRead`/`credentials` entry for `~/.ssh` hides key files).
- Known incompatibilities and fixes: `watchman` (`jest --no-watchman`); `docker` (exclude e.g. `docker compose *`); `pbcopy`/`xclip`/`wl-copy` (use `/copy`; excluding them doesn't take a piped call out of the sandbox); Go-based CLIs failing TLS on macOS (exclude the tool, or `enableWeakerNetworkIsolation` with a MITM proxy); `open`/`osascript` error `-600` on macOS (`allowAppleEvents` from user/managed/CLI settings, or exclude `open *`); `Can't mount proc` in an unprivileged container (`enableWeakerNestedSandbox`); `unable to unlink old` from `git merge`/`checkout` on a denied path; a server on localhost (macOS: `network.allowLocalBinding`; Linux/WSL2: a command's localhost is private — exclude the command). A killed Linux/WSL2 session can leave 0-byte read-only placeholder files at `.claude` settings paths that block settings writes ("Yes, and don't ask again" fails): `claude doctor` lists them (`version >= 2.1.257:` flagged; earlier versions left them silently) — delete with `rm` while no other session runs in the project.
- To deny sandboxed commands read access to home directories and mounted volumes while keeping working directories readable, set `permissions.blockReadsOutsideWorkingDirectories` instead of writing path rules; a `denyRead: ["~/"]` + `allowRead: ["."]` pair resolves `.` to the project root only from project settings (from user settings `.` is `~/.claude`). Excluded-command patterns: no wildcard = exact match (`docker` matches only bare `docker`; end with ` *` for arguments); a pattern covering an interpreter, a script in the working directory, or a tool acting on a file there (`docker compose` and its compose file) lets Claude write that file and run it outside the sandbox — keep patterns narrow. An excluded command still goes through the normal permission flow (read-only/allowed commands run, `auto` classifier reviews, `bypassPermissions` runs unless an ask rule matches).
- Verify the sandbox by asking Claude to run `touch ~/sandbox-probe` (fails `Operation not permitted` / `Read-only file system`) and `curl --noproxy '*' https://example.com` (fails `Could not resolve host`); a command typed at the `!` prompt usually isn't sandboxed so doesn't test it. Decline an offered unsandboxed retry.
- Security limits: the proxy decides from the client-supplied hostname without inspecting TLS, so a broad domain such as `github.com` opens exfiltration paths (domain fronting) — use a custom TLS-inspecting proxy when the threat model needs it; `allowUnixSockets` with `/var/run/docker.sock` grants host access; writes to `$PATH` directories, system config, or shell rc files enable escalation; `enableWeakerNestedSandbox` considerably weakens Linux isolation; computer use runs on the real desktop. Effective sandboxing needs BOTH filesystem and network isolation — check an `allowWrite`, broad `allowedDomains`, or `excludedCommands` entry doesn't undo the other side.

- Array keys (`filesystem.allowWrite`, etc.) **merge across all scopes**; user, project, and managed entries are combined.
- Boolean keys (`enabled`, `failIfUnavailable`): managed value wins, local ignored.
- Settings files are automatically write-denied inside the sandbox at every scope, so a sandboxed command cannot modify its own policy — unless `filesystem.disabled` turns the layer off, which drops these deny rules too. `version >= 2.1.210:` the deny rules resolve symlinks, so a symlink appearing at a protected settings path has its target denied for the next command.
- Default writable set = the working directory plus the session temp dir, and `$TMPDIR` points sandboxed commands at the latter (unsandboxed commands keep your shell's `$TMPDIR`, so the two resolve differently).
- `version >= 2.1.191:` approving a domain prompt allows that host for the rest of the session instead of re-prompting.
- Auto-allow mode skips a bare `Bash` (or `Bash(*)`) ask rule for sandboxed commands, but never a content-scoped ask rule or a deny rule. `version >= 2.1.212:` the skip does NOT apply in plan mode — there a bare `Bash` ask rule prompts even for sandboxed read-only commands. `version >= 2.1.218:` root/home `rm`/`rmdir` targets go to the classifier instead of a prompt when auto mode is active. Add `Bash(dangerouslyDisableSandbox:true)` as an ask rule to be prompted on every unsandboxed retry.
- `version >= 2.1.271:` in `auto` mode with sandboxing on, each Bash/PowerShell/Monitor command can carry its own list of hosts beyond the sandbox allowlist (domain, wildcard, or IP, each with optional `:port`); the classifier reviews the hosts with the command, and an approved list opens them for that one command only (nothing persists to session/settings). `deniedDomains` still blocks; `strictAllowlist`/`allowManagedDomainsOnly` refuse per-command lists entirely. A connection to an unlisted host is refused outright (no prompt/classifier check) and the command is re-run with the host added.
- Linked git worktree: the main repo's shared `.git` is writable (so `git commit` works) but `hooks/` and `config` inside it stay denied.
- WSL2: whether a sandboxed command can launch a Windows binary (`cmd.exe`, `powershell.exe`, anything under `/mnt/c/`) follows the Unix-socket settings — the optional seccomp filter (`npm install -g @anthropic-ai/sandbox-runtime`, adds Unix-domain-socket blocking) must be installed for the socket to be blocked at all; to allow launches set `network.allowAllUnixSockets`. Linux/WSL2 require `bubblewrap` and `socat`.
- Security note: `allowUnixSockets` with `/var/run/docker.sock` effectively grants host access.
- Credential masking (`mode:"mask"`) needs: `network.tlsTerminate` (without it the sentinel reaches the server unchanged and auth fails; `claude doctor` warns `TLS termination is unavailable`); every `injectHosts` host also in `network.allowedDomains` (no `injectHosts` = every `allowedDomains` host); a trusted scope — `mask` entries, `tlsTerminate`, `allowPlaintextInject`, `awsPairs`, `sigv4` are honored only from user/managed/`--settings` (server-managed delivery of them counts as a setting that needs approval). `deny` beats `mask` for the same variable in any scope; `deny` entries merge from every scope and none can be removed by another. AWS: mask `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` together (the proxy re-signs SigV4 from the access-key sentinel, `version >= 2.1.221`; masking only the secret fails at AWS); streaming uploads, presigned URLs, and SigV4A fail rather than forward a broken signature unless `credentials.sigv4` forwards them. File masks: one file per entry (list each); falls back to `deny` for a directory, glob, file over 8 MiB, or non-UTF-8 file; no `extract`/`decode` replaces the whole file with one sentinel; the default `onExtractNoMatch: warn` skips the entry so commands read the real file unmasked (on macOS `mask` applies as `deny` while filesystem isolation is on) — use `deny` when the secret might be present but the pattern might miss. `claude doctor` flags `injectHosts` entries that can never match. There is no built-in credential deny list; `sandbox.credentials` covers sandboxed Bash only (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` covers all subprocesses). Excluding the user settings source with `--setting-sources` keeps its `deny` entries and file masks as restrictions (no longer authorizing substitution) but drops its env-var masks.
- Hosts outside `allowedDomains`: the command stays sandboxed and waits for a decision. `bypassPermissions` (and plan mode with bypass available) allows without a prompt; Manual/`acceptEdits`/other plan prompts; `auto` refuses unless the command listed the host and the classifier approved; `dontAsk` refuses. `strictAllowlist`/`allowManagedDomainsOnly` refuse in every mode; `deniedDomains` always refuses. "Yes, and don't ask again" saves a `WebFetch(domain:...)` allow rule to local settings (to user settings while the sandbox is admin-required). A bare `*` in a `WebFetch(domain:*)` rule is honored by the sandbox from `version >= 2.1.186`; a leading `*.` also works; other wildcard positions have no effect on sandboxed commands.
- `version >= 2.1.284:` after a hostname passes the allowlist the proxy resolves it and refuses a name that resolves only to local addresses (loopback, link-local such as `169.254.169.254`, the machine's own addresses; `localhost`/`*.localhost` may resolve to loopback; skipped when an upstream corporate proxy resolves the name). Allow such a name by adding the resolved IP (with port) to `allowedDomains`. Earlier versions connected to whatever address resolved.
- IPv6 in `allowedDomains`/`deniedDomains`/`WebFetch(domain:...)`: write brackets (`"[::1]"` all ports, `"[::1]:443"`; `version >= 2.1.229`); unbracketed entries are ambiguous (deny lists block every reading, allow lists rewrite to host:port or drop the entry). In `credentials.*[].injectHosts` write the bare canonical compressed address (`"::1"`); `claude doctor` flags entries that can never match.
- Admin-required sandbox (`version >= 2.1.285`): in effect when `allowUnsandboxedCommands: false` is set in managed settings or via `--settings` (unless managed sets `true`), or `network.allowManagedDomainsOnly: true` is set in managed settings. It does not turn the sandbox on (set `enabled` too). Then loosening settings come only from managed settings, `--settings`, and user `~/.claude/settings.json`; Claude Code ignores these in a repo's `.claude/settings.json`/`.claude/settings.local.json`: `excludedCommands`, `ignoreViolations`, `network.allowedDomains`/`allowUnixSockets`/`allowMachLookup`/proxy ports (every entry); the sandbox write access from `filesystem.allowWrite`, `Edit(...)` allow rules, and `permissions.additionalDirectories` (Claude's file tools still follow them); the sandbox host from `WebFetch(domain:...)` allow rules; `true` for `enableWeakerNestedSandbox`/`enableWeakerNetworkIsolation`/`network.allowAllUnixSockets`/`network.allowLocalBinding`; `false` for `enabled`/`failIfUnavailable` when user settings say `true`; `filesystem.allowRead` entries at or under a path managed/`--settings`/user settings deny reading. Repo `deny` entries and `autoAllowBashIfSandboxed` still apply. From 2.1.282 to 2.1.284 the same settings made Claude Code ignore a repo's `excludedCommands` entries.
- Locks without an admin-required sandbox (`version >= 2.1.285`): `network.deniedDomains` or a `WebFetch(domain:...)` deny in managed/`--settings` → repo proxy ports ignored; `network.strictAllowlist` in managed/`--settings`/user → repo proxy ports, `allowedDomains`, `WebFetch(domain:...)` allow rules ignored; `filesystem.denyRead`, a `Read(...)` deny, or a `credentials.files` entry in managed/`--settings` → repo `allowRead`/`allowWrite`/`Edit(...)` allow/`additionalDirectories` entries at or under a path denied for reading ignored. Unless managed settings set them, user settings or `--settings` can turn on `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `network.allowAllUnixSockets`, `network.allowLocalBinding`, and a repo's `.claude/settings.json` can too unless the sandbox is admin-required (set them `false` in managed settings to forbid); `allowAppleEvents` can't be turned on from a repo.
- Excluding a settings source with `--setting-sources`/SDK `settingSources` (`version >= 2.1.246`) makes the sandbox ignore its `sandbox.filesystem` entries, `Edit` rules, `Read` deny rules, and (project/local) `credentials` entries.
- Sandbox-protected paths (write-denied even inside writable dirs; no `allowWrite`/`Edit` allow lifts them; only `filesystem.disabled` does): `.claude` settings files and `.claude/skills|agents|commands|hooks`, `.mcp.json`, `.claude/workflows`, `.claude/scheduled_tasks.json` (in the working dir and above); shell startup files, `.gitconfig`, `.vscode`, `.idea`, `.git/hooks` and `.git/config` (working dir only); files that would turn the working dir into a bare repo (`HEAD`, `objects`, `refs` at the top level, plus an existing `config`/`hooks` entry when a `HEAD` sits beside it; a file named `config` is denied even with no `HEAD`; Linux/WSL2 deletes a stray top-level `HEAD`/`objects`/`refs` that appears mid-command); most of `~/.claude` (or `CLAUDE_CONFIG_DIR`) plus `~/.claude.json` and `.credentials.json`. Typed `!` shell-mode commands run unsandboxed except in background sessions and Linux sessions with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`, where strict sandbox mode sandboxes them.

### Path prefixes (sandbox)

Paths in `filesystem.*` use standard conventions (NOT the `//` Read/Edit anchoring):

- Absolute paths: `/tmp/build`
- Home-relative: `~/.kube`
- `./` or no prefix: project root for project settings, but `~/.claude` for user settings.
- The older `//path` absolute form still works. If you used single-slash `/path` expecting project-relative resolution, switch to `./path`.
- Same prefixes apply to `credentials.files`.
- `version >= 2.1.224:` a trailing slash or trailing `/**` is stripped, so `~/build`, `~/build/`, and `~/build/**` are equivalent (earlier versions passed a trailing slash through, letting reads/writes under a `denyRead`/`denyWrite` path written with one slip past).
- Wildcard (`*`/`?`/`[`) support differs by list and platform: `allowWrite`/`denyWrite` support wildcards on macOS only — on Linux/WSL2 the sandbox mounts concrete paths, so a wildcarded entry (including one added from an `Edit` allow rule) is skipped with no effect; the `/sandbox` **Config** tab lists the `Edit` rules Claude Code skipped this way. `denyRead`/`allowRead` support wildcards on every platform.
