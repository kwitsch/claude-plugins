## What a plugin is / components

- Plugin = self-contained directory of components that extends Claude Code.
- Components: skills, agents, hooks, hooks modules (hooks as JS functions that can also draw panes/add commands; a plugin with one is a "mod"; manifest `types` declares its `.d.ts`), MCP servers, LSP servers, monitors, themes, bin executables.
- An enabled plugin is in EVERY session: name+description of each skill/agent/command Claude can invoke on its own sit in context every turn (full text loads on use) — those tokens count toward usage and shrink the context window even in sessions where nothing from the plugin runs; plugin MCP servers run alongside each session (their per-turn context cost follows MCP tool search), hooks fire at their events; all of it runs as the user. Check cost via the `/plugin` **Context cost** estimate (official-marketplace plugins), `claude plugin details`, Installed tab **Not used recently** group.
- Plugin vs standalone: skills, subagents, hooks, MCP servers all work on their own (e.g. a skill in `~/.claude/skills/` is available in every project). Package as a plugin only to bundle several of them as one unit — installable with one command, updated from a marketplace, shareable with teammates, versioned releases.
- An installed plugin must be present at three layers before its skills run: settings (added marketplaces + enabled plugins), disk (`~/.claude/plugins/`), session (plugins load at startup or on `/reload-plugins`).
- Not Claude Code plugins: the VS Code extension and the JetBrains plugin (Claude Code inside an IDE). The same plugin format also installs on claude.ai and in Cowork, where a different set of components loads.
- Two loading paths: **marketplace install** (copied to plugin cache `~/.claude/plugins/cache/`) or **skills-directory** (loaded in place from `~/.claude/skills/<name>/` or `<cwd>/.claude/skills/<name>/` as `<name>@skills-dir`).
- Installed plugins cannot reference files outside their directory — no `../shared-utils`; use symlinks for shared files (see [Symlink resolution](#symlink-resolution)).
- Orphaned version directories (after update/uninstall) are auto-deleted after 14 days; Glob/Grep skip them. Grace period lets concurrent sessions on the old version keep running.
- `CLAUDE.md` at plugin root is NOT loaded as project context (`claude plugin validate` warns when it finds one) — ship instructions via a skill.
- Single-skill plugin: a `SKILL.md` at plugin root (no `skills/` dir, no `skills` manifest field) loads as one skill (version >= 2.1.142). Invocation name = frontmatter `name`, else directory basename — ALWAYS set frontmatter `name`, since the basename fallback for a marketplace-installed plugin is the install dir, a version string that changes on every update.
- Plugin-shipped agents accept only `name`, `description`, `model`, `effort`, `maxTurns`, `tools`, `disallowedTools`, `skills`, `memory`, `background`, `isolation` (sole value `"worktree"`); `hooks`, `mcpServers`, `permissionMode` are rejected in plugin agents for security.
- Boolean frontmatter in plugin skills/commands (e.g. `disable-model-invocation`) also accepts `yes`/`no`/`on`/`off`/`1`/`0`, any casing (version >= 2.1.218; earlier only `true`/`false`).
- Hooks targeting the plugin's OWN bundled MCP server need scoped names: matcher/`if` take `mcp__plugin_<plugin>_<server>__<tool>`, an `mcp_tool` hook's `server` takes `plugin:<plugin>:<server>`. A matcher on the bare `.mcp.json` key never fires.
- Plugin agent frontmatter with no `name` field, or that fails to parse, still loads: Claude Code names the agent after the file (`agents/reviewer.md` in plugin `my-plugin` → `my-plugin:reviewer`); unparseable frontmatter additionally gets description `Agent from my-plugin plugin` and ignores every other field in the file. A project/user/managed agent file with the same defect is skipped instead. Find these with `claude plugin validate ./my-plugin/agents` (bare agents dir; version >= 2.1.233) or `claude plugin validate ./my-plugin` (plugin with a manifest).

## Plugin structure & layout

```
<plugin-name>/
  .claude-plugin/
    plugin.json          ← manifest (optional; name derived from dir if absent); ONLY file inside .claude-plugin/
  skills/
    <skill-name>/
      SKILL.md
  agents/
    <agent-name>.md
  hooks/
    hooks.json
  mcp/
    server.mjs           ← self-contained stdio MCP server (chmod +x)
  bin/                   ← executables added to PATH (must be chmod +x)
  commands/              ← legacy flat .md skills; prefer skills/ for new plugins
  workflows/             ← workflow script files
  output-styles/         ← output style .md files
  themes/                ← color theme .json files (experimental)
  .mcp.json              ← MCP server configs
  .lsp.json              ← LSP server configs
  monitors/
    monitors.json        ← background monitors (experimental)
  settings.json          ← default settings; only `agent` + `subagentStatusLine` keys honored
  README.md
  CLAUDE.md              ← NOT loaded as project context
```

- Only `plugin.json` goes inside `.claude-plugin/`. All component dirs live at plugin root.
- `skills/` preferred over `commands/` for new plugins.
- `bin/` executables must have executable bit set.

## plugin.json schema

The manifest is optional (auto-discovery when absent; the plugin name then comes from the marketplace entry, or from the directory name with `--plugin-dir`). If present, `name` is the only required field; all others optional.

### Standard metadata fields

| Field            | Type    | Required | Description                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`           | string  | Yes      | Unique identifier; kebab-case, non-empty, no spaces, `@`, `:`, path separators, control or bidirectional-formatting characters (version >= 2.1.247: own validation error, not the impersonation-name error). Used for component namespacing. If a marketplace entry lists the plugin under a different `name`, the marketplace entry's name is authoritative for `enabledPlugins` keys and `/plugin`. |
| `version`        | string  | No       | Version string, not checked against semver (e.g. `1.2.0`). Omit to use git commit SHA as version. If set, users receive updates only when this field changes; not pinned for `command`-source plugins, claude.ai-hosted-marketplace plugins, or a plugin loaded in place from a marketplace added as a local directory.                                                                               |
| `displayName`    | string  | No       | Human-readable name shown in `/plugin` picker + UI. Falls back to `name`. May contain spaces/any casing; not used for namespacing or lookup. A marketplace-entry `displayName` wins. version >= 2.1.143.                                                                                                                                                                                              |
| `description`    | string  | No       | Brief plugin description                                                                                                                                                                                                                                                                                                                                                                              |
| `author`         | object  | No       | `{ "name": "…" }` required; `"email"` and `"url"` optional                                                                                                                                                                                                                                                                                                                                            |
| `homepage`       | string  | No       | Plugin homepage or documentation URL; must parse as a URL or the plugin fails to load                                                                                                                                                                                                                                                                                                                 |
| `repository`     | string  | No       | Source code repository URL; not validated                                                                                                                                                                                                                                                                                                                                                             |
| `license`        | string  | No       | SPDX license identifier (e.g. `MIT`, `Apache-2.0`)                                                                                                                                                                                                                                                                                                                                                    |
| `keywords`       | array   | No       | Short string keywords                                                                                                                                                                                                                                                                                                                                                                                 |
| `metadata`       | object  | No       | version >= 2.1.222. Free-form object for the author's own data (catalog/entitlement fields, …); Claude Code never reads it. Non-object value is ignored with a `validate` warning. Earlier versions treat the key as unrecognized.                                                                                                                                                                    |
| `defaultEnabled` | boolean | No       | version >= 2.1.154. `false` ships the plugin installed-but-disabled (user opts in). Defaults `true`. See [Default enablement](#default-enablement). Marketplace-entry `defaultEnabled` overrides this.                                                                                                                                                                                                |
| `$schema`        | string  | No       | JSON Schema URL for editor autocomplete; ignored at load time.                                                                                                                                                                                                                                                                                                                                        |

- Reserved-name check (`claude plugin validate` only; Claude Code still installs/loads; ignores case, any run of separators = one): ERROR if `name` starts `claude-`/`anthropic-`/`anthropics-`/`cc-plugin-`, is `claude`/`anthropic`/`anthropics`/`claude-code`/`claude-mods`, or puts `official` beside `claude`/`anthropic`; WARNING if `claude`/`anthropic`/`anthropics` is a whole word elsewhere (e.g. `mcp-for-claude`). `claude plugin init`/`tag` refuse an erroring name.
- Directory-listing fields `icon` (image path inside the plugin, e.g. `./logo.png`), `documentationUrl`, `supportUrl`, `privacyPolicyUrl`, `termsOfServiceUrl` (each `https://`): read by Anthropic's directory on submission, ignored by Claude Code at load; set only in `plugin.json` (`validate` reports them as unknown fields in a marketplace entry). `validate` accepts them without warning on version >= 2.1.281; earlier versions warn `Unknown field` per field, so `--strict` fails.

### Component path override fields

Default component dirs are auto-discovered (see [Component auto-discovery](#component-auto-discovery)). These fields override the defaults.

| Field                   | Type                      | Description                                                                                                                                                                                                                                                                                                                               | Default behavior                          |
| ----------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `skills`                | string \| array           | Directories only: a dir of `<name>/SKILL.md` folders, or one folder holding `SKILL.md` directly                                                                                                                                                                                                                                           | ADDS to default `skills/` scan            |
| `commands`              | string \| array \| object | Flat `.md` skill files/dirs, or an object map (see below)                                                                                                                                                                                                                                                                                 | REPLACES default `commands/`              |
| `agents`                | string \| array           | Agent `.md` files only (directories not accepted)                                                                                                                                                                                                                                                                                         | REPLACES default `agents/`                |
| `workflows`             | string \| array           | Workflow script files/dirs                                                                                                                                                                                                                                                                                                                | REPLACES default `workflows/`             |
| `hooks`                 | string \| array \| object | `.json` hooks file path(s) or inline event map; arrays may mix both                                                                                                                                                                                                                                                                       | MERGES with `hooks/hooks.json`            |
| `mcpServers`            | string \| array \| object | MCP `.json` config path(s), `.mcpb`/`.dxt` bundle path or `https://` URL (extracted to `.mcpb-cache/` in the plugin root; any other extension fails validation), or inline map; a later server name replaces an earlier one                                                                                                               | MERGES with `.mcp.json` (loads first)     |
| `lspServers`            | string \| array \| object | LSP `.json` config path(s) or inline map; a later server name replaces an earlier one                                                                                                                                                                                                                                                     | MERGES with `.lsp.json` (loads first)     |
| `outputStyles`          | string \| array           | Output style files/dirs                                                                                                                                                                                                                                                                                                                   | REPLACES default `output-styles/`         |
| `experimental.themes`   | string \| array           | Color theme `.json` files/dirs (each `{ "name", "base": <preset, e.g. dark>, "overrides": {token:hex} }`); appear in `/theme` as `custom:<plugin>:<slug>`, read-only; `Ctrl+E` in `/theme` copies one into `~/.claude/themes/` for editing                                                                                                | REPLACES default `themes/`                |
| `experimental.monitors` | string \| array           | Monitors `.json` file path or inline array (strict entries)                                                                                                                                                                                                                                                                               | REPLACES default `monitors/monitors.json` |
| `experimental.evals`    | string \| array           | Dir below the plugin root holding `claude plugin eval` cases, when not the default `evals/` (not a component path: `./` optional, array → first entry only); `--eval-dir` overrides. version >= 2.1.269                                                                                                                                   | REPLACES default `evals/`                 |
| `settings`              | object                    | Settings applied while enabled; only `agent` + `subagentStatusLine` take effect, other keys dropped at load; root `settings.json` wins                                                                                                                                                                                                    | —                                         |
| `types`                 | string                    | `.d.ts` file declaring the `$.state` values and `$` nouns of a hooks module (mod)                                                                                                                                                                                                                                                         | —                                         |
| `userConfig`            | object                    | Values prompted at enable time; see [userConfig](#userconfig)                                                                                                                                                                                                                                                                             | —                                         |
| `channels`              | array                     | Message-injection channels bound to plugin MCP servers; strict entries `{ "server": "<mcpKey>" (required; key of an MCP server in this plugin's `mcpServers`), "displayName"? (config-dialog title, defaults to the server name), "userConfig"?: {…} (same shape as top-level) }`; `userConfig` values substitute into the server's `env` | —                                         |
| `dependencies`          | array                     | Entries: `"name"`, `"name@marketplace"`, or `{ "name", "marketplace"?, "version"? }`; see [Plugin dependencies](#plugin-dependencies)                                                                                                                                                                                                     | —                                         |

- **Path-behavior rule**: REPLACE fields (`commands`, `agents`, `workflows`, `outputStyles`, `experimental.themes`, `experimental.monitors`) skip the default dir entirely; to keep it, list it explicitly (e.g. `"commands": ["./commands/", "./extras/"]`). `skills` always ADDS. Exception: a marketplace entry whose `source` resolves to the marketplace root — declaring specific skill subdirs REPLACES the default scan.
- All custom paths must be relative, start with `./`, resolve from plugin root — except `skills`, which also accepts bare `.` (same as `./`, the plugin root); version >= 2.1.221 required for `.` to validate, use `./` for earlier versions. `mcpServers` also accepts an `https://` bundle URL. Every path must resolve inside the plugin root and exist, else it doesn't load: `/plugin` Errors tab shows `<component> path escapes plugin directory: <path>` / `<component> path not found: <path>` (`validate`: `Path contains ".." which could be a path traversal attempt` / `Path not found`); `validate` checks `outputStyles`/`lspServers`/`monitors`/`themes` paths on version >= 2.1.283.
- version >= 2.1.140: when both a default folder and its manifest key exist, the ignored folder is flagged in `/doctor`, `plugin list`, `/plugin` detail as `Default <folder>/ folder is ignored because the manifest sets "<key>"` (plugin still loads via manifest paths). No warning when the manifest key points INTO the default folder (e.g. `"commands": ["./commands/deploy.md"]`) — that path names the folder explicitly.
- `experimental.themes`/`experimental.monitors` may currently also be set at top level (`themes`/`monitors`); `validate` warns, a future release will require `experimental.*`.
- `commands` object map: key = command name after the plugin prefix (`about` in `deploy-tools` → `/deploy-tools:about`); each value sets EXACTLY ONE of `source` (`.md` path relative to plugin root) or `content` (inline Markdown) — both or neither fails validation; optional `description`, `argumentHint`, `model` (default model), `allowedTools` (usable without prompting). A `hooks` file wraps the event map in a top-level `"hooks"` key (bare event map fails to load); an inline `hooks` object is the event map itself.

### Unrecognized fields

- Top-level fields Claude Code does not recognize are stripped and the plugin loads — one manifest can double as a VS Code/Cursor/npm/MCPB manifest.
- Strict objects: `userConfig` options, `channels` entries, `lspServers` configs, `monitors` entries — an unknown key is an ERROR and the plugin doesn't load.
- `claude plugin validate` reports unrecognized fields as **warnings** (with a suggestion if 1-2 chars off a known field); wrong-type fields (e.g. `keywords` as string) are load **errors** — except `experimental` and `metadata`, where a non-object value is ignored with a warning instead of failing to load.
- `validate` results: `Validation passed with warnings` = loads but fix (unknown top-level field, non-kebab-case `name`, missing `version`/`description`/`author`); `Validation failed` = type mismatch, missing/escaping path, or unknown key in a strict object. `validate --strict` treats warnings as errors (use in CI).
- version >= 2.1.281: `validate` also checks MCP entries (`.mcp.json`, a `mcpServers` `.json` file, or inline). ERRORS: entry Claude Code would drop at load, `${user_config.KEY}` for an undeclared option, remote `url` that isn't a valid absolute URL. WARNINGS: `http://`/`ws://` URL to a non-loopback host, header value that looks like a literal credential.

### Default enablement

- version >= 2.1.154. `defaultEnabled: false` ships a plugin installed-disabled; user enables via `claude plugin enable <plugin>` or `/plugin`. Earlier versions ignore the field and enable on install.
- Precedence over `defaultEnabled`: (1) user's `enabledPlugins` entry at any scope (persists across updates/reinstalls); (2) a dependency requirement — when required by an active plugin, Claude Code writes `true` for it explicitly at install/enable, so its own default no longer applies.
- Marketplace-entry `defaultEnabled` overrides the `plugin.json` value.

### userConfig

Values Claude Code prompts for when the plugin is enabled (instead of hand-editing settings.json). Keys: letters, digits, underscores; can't start with a digit. Each option is a strict object (unknown key fails validation).

| Field         | Required | Description                                                                                    |
| ------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `type`        | Yes      | One of `string`, `number`, `boolean`, `directory`, `file`                                      |
| `title`       | Yes      | Label in the config dialog                                                                     |
| `description` | Yes      | Help text under the field                                                                      |
| `sensitive`   | No       | `true` masks input + stores in secure storage (keychain, ~2 KB total limit), not settings.json |
| `required`    | No       | `true` makes the config dialog reject an empty value                                           |
| `default`     | No       | Value used when user provides nothing (string, number, boolean, or string array)               |
| `options`     | No       | version >= 2.1.271. For `string` type only: fixed value set shown as a picker in `/config`.    |
| `multiple`    | No       | For `string`, allow an array                                                                   |
| `min` / `max` | No       | Bounds for `number`                                                                            |

- `options` applies only to a `string` field that is not `multiple`/`sensitive`: set `default` to a listed value or `required: true`; each option a plain label of 1-64 chars; a violation fails the plugin load. Declaring `options` on ANY field makes the plugin unloadable on versions before 2.1.271. Each option of each enabled plugin also gets a `/config` row (version >= 2.1.269), except `sensitive` options and `multiple` lists.
- Substituted as `${user_config.KEY}` in MCP/LSP server configs (except MCP `headersHelper`) and exec-form hook `args`; non-sensitive also in skill/agent content (a sensitive value there becomes a placeholder).
- version >= 2.1.207: fields that run through a shell REJECT `${user_config.*}` — the component fails with an error instead of substituting. Affects shell-form hook commands, monitor commands, MCP `headersHelper`. Instead: exec form (`args`) or read `CLAUDE_PLUGIN_OPTION_<KEY>` from the hook env; monitor/`headersHelper` scripts read the value from a config file they own (the `headersHelper` env carries `CLAUDE_PLUGIN_ROOT`, `CLAUDE_CODE_MCP_SERVER_NAME`, `CLAUDE_CODE_MCP_SERVER_URL`, no option values). Earlier versions substituted.
- All values exported to hook processes as `CLAUDE_PLUGIN_OPTION_<KEY>` env vars (`<KEY>` = key uppercased). Monitor processes do NOT receive them.
- Non-sensitive stored in settings.json under `pluginConfigs[<plugin-id>].options`; sensitive go to keychain (or `~/.claude/.credentials.json`).
- version >= 2.1.207: `pluginConfigs` is read ONLY from user settings, `--settings`/SDK inline settings, managed settings (precedence managed > `--settings` > user); `--setting-sources` narrows further. Project `.claude/settings.json` + `.claude/settings.local.json` entries are IGNORED (a cloned repo could otherwise feed values into hook/MCP/LSP/monitor commands); earlier versions read them. `pluginConfigs`-only — `enabledPlugins` still honors project/local.

## Path variables

Resolved inline in component fields and exported as environment variables to some component processes (see below). NOT present in the environment of commands Claude runs through the Bash tool (main session or subagent) — in skill/command/agent content write the `${...}` reference in the Markdown body instead.

| Variable                | Scope       | Description                                                                                                                                                                                                                                                                                                                                               |
| ----------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `${CLAUDE_PLUGIN_ROOT}` | per-version | Plugin install directory. Changes on each plugin update; old dir kept ~14 days then cleaned. Ephemeral — do NOT write state here. Use for bundled scripts/binaries.                                                                                                                                                                                       |
| `${CLAUDE_PLUGIN_DATA}` | persistent  | Persistent data dir, survives updates. Resolves to `~/.claude/plugins/data/{id}/` (`{id}` = plugin id, non-`[a-zA-Z0-9_-]` chars → `-`; e.g. `formatter@my-marketplace` → `formatter-my-marketplace`). Created on first reference. Use for deps (`node_modules`, venv), caches, runtime state. Deleted on uninstall from last scope unless `--keep-data`. |
| `${CLAUDE_PROJECT_DIR}` | session     | Project root (same dir hooks receive).                                                                                                                                                                                                                                                                                                                    |

- Exported as env vars per component: hooks → all three + `CLAUDE_PLUGIN_OPTION_<KEY>`; MCP `stdio` → `CLAUDE_PLUGIN_ROOT` + `CLAUDE_PLUGIN_DATA` only; LSP → all three; monitors → none. Inline substitution is per component: skill/command/agent content and hook `command`/`args`, monitor `command` → anywhere the placeholder appears; MCP `stdio` → `command`, `args`, `env`; MCP `http`/`sse`/`ws` → `url`, `headers`, `headersHelper`; LSP → `command`, `args`, `env`, `workspaceFolder`.
- Use exec form (`"args": []`) for `${CLAUDE_PLUGIN_ROOT}` in hooks (passed as one arg, no quoting); in shell-form hooks/monitor commands wrap in double quotes (`claude plugin validate` warns on an unquoted variable in a shell-form hooks-file command unless the hook sets `shell` to `"powershell"`). On Windows the substituted paths use forward slashes.
- On mid-session plugin update, hooks/monitors/MCP/LSP keep the old path; `/reload-plugins` switches hooks/MCP/LSP to the new path, monitors need a session restart. In a session with no interactive terminal, `/reload-plugins` leaves plugin MCP servers on the old path until the next session. `/reload-plugins` also keeps live connections of MCP servers whose configuration is unchanged (reconnects only changed servers).
- Plugin hook/monitor commands additionally substitute any `${ENV_VAR}`; `${user_config.*}` resolves only in exec-form hook commands and MCP/LSP configs other than MCP `headersHelper` (see [userConfig](#userconfig)).
- Dependency-reinstall pattern: a `SessionStart` hook `diff`s bundled `${CLAUDE_PLUGIN_ROOT}/package.json` vs `${CLAUDE_PLUGIN_DATA}/package.json`; reinstall when they differ (directory-existence check alone misses dependency-manifest changes across updates).

## Component auto-discovery

The manifest is optional. When `plugin.json` is absent or does not declare explicit component paths, Claude Code discovers components from the default directories (the plugin name then comes from the marketplace entry, or from the directory name with `--plugin-dir`):

| Default path             | Component type                                                                                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `skills/`                | Skills (`<name>/SKILL.md` subdirs)                                                                                                                                                                                              |
| `commands/`              | Legacy flat skills (`.md` files)                                                                                                                                                                                                |
| `agents/`                | Agent definitions (`.md` files; subfolders are part of the agent name)                                                                                                                                                          |
| `workflows/`             | Workflow script files                                                                                                                                                                                                           |
| `output-styles/`         | Output style `.md` files                                                                                                                                                                                                        |
| `themes/`                | Color theme `.json` files (experimental)                                                                                                                                                                                        |
| `hooks/hooks.json`       | Hook event handlers                                                                                                                                                                                                             |
| `.mcp.json`              | MCP server configurations                                                                                                                                                                                                       |
| `.lsp.json`              | LSP server configurations                                                                                                                                                                                                       |
| `monitors/monitors.json` | Background monitors (experimental)                                                                                                                                                                                              |
| `bin/`                   | PATH executables (invokable as bare commands in Bash tool while enabled); claude.ai and Cowork don't install a plugin that has `bin/`, incl. one distributed through claude.ai org settings (rejected on sync or direct upload) |
| `settings.json`          | Default settings (`agent`, `subagentStatusLine` only); takes priority over `plugin.json` `settings`                                                                                                                             |

- Override any default by setting the corresponding field in `plugin.json`.
- Component dirs must be at plugin root, not inside `.claude-plugin/`.
- Skills inside a plugin are namespaced as `<plugin-name>:<skill-name>`.

## Marketplace

A marketplace is a `marketplace.json` catalog that lets users browse and install plugins via `/plugin` or CLI. Full schema (required/optional top-level fields, plugin entry fields, source types, validate): see `references/claude-code-plugins-marketplace-reference.md`.

- A plugin marketplace is NOT Claude Marketplace (the claude.com/marketplace website, not addable with `/plugin marketplace add`).
- Inside a session, `/plugin marketplace add <source>` registers a marketplace like the CLI; `/plugin install <plugin>@<marketplace>` opens the plugin's details in the `/plugin` panel, where the install is confirmed.
- Entry vs `plugin.json` (entry accepts every manifest field except the directory-listing fields; `strict` defaults `true`): NO `plugin.json` → entry IS the manifest regardless of `strict`, and entry `hooks` loads only as an inline object (path/array → `/plugin` Errors tab `not yet supported in a marketplace entry`). `plugin.json` + `strict` unset/`true` → entry `commands`/`agents`/`skills`/`outputStyles`/`themes` are appended; for `hooks` the entry's matchers for an event REPLACE the manifest's for that event, manifest-only events are kept. `plugin.json` + `strict: false` → an entry declaring any of `commands`/`agents`/`skills`/`hooks`/`outputStyles`/`themes` fails the load with `Plugin <name> has conflicting manifests`.
- Precedence: entry `defaultEnabled` + display fields (e.g. `displayName`) override the manifest; manifest `version` overrides the entry's. Entry `name` = install id `<entry-name>@<marketplace>` + `enabledPlugins` key; components namespace under the manifest `name`. Installing by the manifest name when they differ → `Plugin "<manifest-name>" not found in marketplace "<marketplace>"` — keep both names identical.
- Anthropic tiers: official (`claude-plugins-official`, demo `claude-code-plugins`), community (e.g. `claude-community`), third-party (all others); official/community names are accepted only for marketplaces sourced from `github.com/anthropics/` repos. Claude Code adds the official marketplace on first interactive terminal session unless managed policy blocks it; it does not add the community or demo marketplaces on its own.

## Plugin dependencies

A plugin can depend on other plugins. Declare in `plugin.json` `dependencies` array:

```json
"dependencies": [
  "helper-lib",
  { "name": "secrets-vault", "version": "~2.1.0" },
  { "name": "other-plugin", "marketplace": "other-marketplace" }
]
```

### Dependency fields

| Field         | Type   | Required | Description                                                                                                            |
| ------------- | ------ | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| `name`        | string | Yes      | Plugin name. Resolved within the same marketplace by default.                                                          |
| `version`     | string | No       | Semver range (e.g. `~2.1.0`, `^2.0`, `>=1.4`, `=2.1.0`). Fetched at the highest tagged version satisfying this range.  |
| `marketplace` | string | No       | Different marketplace to resolve `name` in. Requires the target to be listed in `allowCrossMarketplaceDependenciesOn`. |

- Bundle pattern: a manifest can consist of only `name` + `dependencies` (no components of its own) — installing it pulls in every dependency, letting a maintainer package a curated plugin set (e.g. a team's standard toolkit) behind one `claude plugin install`. To grow a bundle, publish a new bundle version with the extra dependency; if the marketplace doesn't auto-update by default, users turn on marketplace auto-update or run `claude plugin update <bundle>` then `/reload-plugins`; admins deploy a bundle org-wide via managed `enabledPlugins`.
- An unconstrained dependency (bare `"name"` / `"name@marketplace"`) follows every release its marketplace publishes (a renamed MCP tool breaks dependents); a constraint like `~2.1.0` keeps `2.1.x` patches only — widen it by publishing a new dependent version after testing.
- version >= 2.1.110 required for dependency version constraints.
- Version ranges use Node `semver` syntax: `^`, `~`, `-` (hyphen), comparator ranges.
- Pre-release versions excluded unless range opts in with a pre-release suffix (e.g. `^2.0.0-0`).
- Resolution: against git tags `{plugin-name}--v{version}` (version matches that commit's `plugin.json`). The tag lives in the repo the plugin's `source` points at: `github`/`url`/`git-subdir` → the plugin's own repo (author tags); relative path → the marketplace repo (maintainer tags); the plugin-name prefix lets one repo host several plugins with independent histories. Create with `claude plugin tag --push` (validates the plugin, checks plugin.json/marketplace-entry version agree when the plugin dir is inside a marketplace checkout, requires clean tree under the plugin dir, refuses if tag exists; `--dry-run`, `--force`; prints `Created tag <plugin>--v<version>`, plus `Pushed to origin` with `--push`, else the `git push` command); a plain `git tag` works if you keep both versions in sync. Resolved tag's semver is recorded separately from `plugin.json` and constraint checks use the tag's version even if `plugin.json` at that commit lags (`claude plugin list` shows e.g. `2.1.0-8713c5b11005`); the tag-resolved cache dir name includes a 12-char commit-SHA suffix, so force-moving a tag to a new commit gets a fresh cache dir instead of reusing stale content. For `npm`, `archive`, and `command` sources, the constraint does NOT control which version is fetched (tag-resolution is git-only) but is still checked at load → `dependency-version-unsatisfied` if violated; for a `command` source the check uses the dependency's `plugin.json` version and ignores the content-hash suffix, so a dependency whose `plugin.json` sets no version satisfies no constraint. Claude Code never auto-installs a `command`-sourced or `headersHelper`-gated dependency — the user installs it themselves first (see `plugin install`/`update` `-y` above). version >= 2.1.196: a marketplace added as a local folder path resolves tags the same way when the folder is a git repo; earlier versions (or a non-git folder) install from the folder's current contents instead. For a relative-path plugin (in a git-hosted marketplace) with no tag satisfying the range, Claude Code installs the marketplace's current copy instead of erroring, then checks the constraint at load (copy outside the range → dependent stays disabled, `claude plugin list` shows `Requires "<dep>@<mp>" ~2.1.0, installed 3.0.0`); a remote git source (`github`/`url`/`git-subdir`) with no matching tag fails outright with `no-matching-tag` (message contains `Dependency "<dep>@<mp>" has no git tag satisfying`).
- Multiple constraints on one dependency: ranges intersected, resolved to highest version satisfying all (`^2.0` + `>=2.1` → highest `2.x` tag at or above `2.1.0`, both plugins load; `=2.1.0` alone pins the dependency, auto-update skips newer versions while that plugin is installed). Unsatisfiable combos (e.g. `~2.1` + `~3.0`) → `range-conflict` (install of the conflicting plugin fails with `has conflicting version requirements`; others stay); the message names the cause — no version satisfies all ranges, invalid semver syntax, or ranges too complex to intersect (simplify long `||` chains). Auto-update fetches a constrained dependency at the highest tag satisfying every installed plugin's range; if the ranges don't overlap, the dependency stays at its current version and surfaces in `/doctor` + the `/plugin` Errors tab, naming the constraining plugin; if they overlap but no tag falls in the range, it fetches the marketplace's current copy and skips the update when that copy's `version` is outside any installed plugin's range. Uninstalling the last plugin that constrains a dependency releases the hold — it resumes tracking its marketplace entry on the next update.
- Missing dependency recovery: `/reload-plugins` and background auto-update reinstall a missing dependency automatically if its marketplace is already configured; re-running `claude plugin install <dependent>`, or adding the marketplace with `claude plugin marketplace add`, also resolves it. A dependency from a marketplace you have not added stays unresolved.
- Cross-marketplace: `{ "name": …, "marketplace": "other-mp" }` requires `other-mp` in the **root** marketplace's `allowCrossMarketplaceDependenciesOn` (trust does not chain); else `cross-marketplace` error. Declared in a marketplace entry → the install is refused (`... is not in the allowlist`, naming the field to set); declared in `plugin.json` → the install completes without the dependency and the plugin then fails to load. The check does not apply to a dependency the user already has installed and enabled at the same scope.
- `enable`/`disable` cascade (version >= 2.1.143): enabling enables deps transitively at the same scope (writes explicit `true`, overriding the dep's own `defaultEnabled: false`); disabling fails if another enabled plugin depends on the target (error gives a chained disable command). Enable failure names the specific blocker: dependency not installed (prints the `claude plugin install` command), blocked by org policy, or force-disabled at a higher-precedence scope (enable it there, or pass `--scope`). Earlier versions enable/disable only the named plugin → `dependency-unsatisfied` on next load.
- Orphan cleanup: auto-installed deps stay after their dependents are uninstalled; `claude plugin prune` (version >= 2.1.121) removes deps no installed plugin requires (`--dry-run`, `-y`, `--scope`), or `claude plugin uninstall <plugin> --prune`. Plugins you installed directly are never pruned. Prints `Nothing to prune` when nothing qualifies (expected on a fresh install, not an error). When stdin/stdout is not a TTY, orphans are listed and nothing is removed unless `-y` is passed.
- Dependency errors (`dependency-unsatisfied`, `range-conflict`, `dependency-version-unsatisfied`, `no-matching-tag`) surface in `plugin list`, `/plugin`, `/doctor`; affected plugin is disabled until resolved. Read `errors` field via `claude plugin list --json`.
- Local dev: `claude --plugin-dir ./dep --plugin-dir ./plugin` satisfies a dependency entry with the local copy even when the entry names a marketplace, and skips checking any version constraint against it (version >= 2.1.242; earlier, a marketplace-qualified entry never matched the local copy and the plugin failed to load). Without also installing the dependency from its marketplace: disabling the local copy reports `Dependency "<name>@inline" is disabled — enable it or remove the dependency` (a bare-name entry reports the bare name); dropping the `--plugin-dir` flag reports the dependency as not installed. When both plugins sit under one parent folder, pass that folder to `--plugin-dir` once instead of repeating the flag (version >= 2.1.265; see [Session flags](#session-flags)).

## Synced plugins (Cowork / cloud sessions)

- Claude Code loads the plugins enabled for the user's claude.ai account (including org-enabled ones) alongside marketplace-installed plugins: downloads each into `~/.claude/plugins/synced/`, loads as `<name>@synced` — no marketplace, no install record; runs at the same trust as an installed plugin. version >= 2.1.239 (earlier: loaded as `<name>@inline`, the `--plugin-dir`/`--plugin-url` identity).
- Sync scope by session: Cowork/cloud sessions download into the session's own environment at session start. **Terminal sessions signed in with a claude.ai account also sync** (version >= 2.1.273; earlier: terminal sessions never synced) — checks the account once per session start, then downloads new/updated + removes turned-off plugins in the background; an interactive session shows `Plugins changed. Run /reload-plugins to activate.` when the background check changes anything. Same sign-in conditions as synced skills; needs a sign-in that grants plugin access.
- Managed setting `syncClaudeAiPlugins: false` stops claude.ai-account plugin sync org-wide (a `blockedMarketplaces`/`strictKnownMarketplaces` lockdown does NOT cover synced plugins, since they come from the account, not a marketplace).
- `claude plugin list` shows these under a `Synced from claude.ai` heading in that environment; they do not appear in the inline `/plugin list`.
- Manage by the `<name>@synced` id: `claude plugin disable`/`enable <name>@synced` in-session writes `"<name>@synced": false`/`true` to that environment's user-level `enabledPlugins`. `install`/`update`/`uninstall` don't apply to a synced plugin — turn it off for the claude.ai account instead, or set `"<name>@synced": false` under `enabledPlugins` in a project's committed `.claude/settings.json` to keep it out of that project's synced sessions everywhere.
- An enabled plugin from any other source (marketplace, `@skills-dir`, `--plugin-dir`) that shares a synced plugin's name wins; the synced copy reports as not loaded. Disable your own copy to use the claude.ai one instead. Before version 2.1.239, the synced copy won this conflict instead.

## Skills-directory plugins

Any folder under a skills directory that contains `.claude-plugin/plugin.json` loads as `<name>@skills-dir` next session — no marketplace, no install, discovered in place (not copied to cache). Scaffold with `claude plugin init`.

| What you have                                 | What it is                                                 |
| --------------------------------------------- | ---------------------------------------------------------- |
| `<skills-dir>/foo/SKILL.md`, no manifest      | Plain skill `foo`                                          |
| `<skills-dir>/foo/.claude-plugin/plugin.json` | Plugin `foo@skills-dir` (can bundle skills/agents/hooks/…) |
| `<plugin>/skills/bar/SKILL.md`                | Skill `bar` inside a plugin                                |

| Skills dir              | Scope    | Loads                                 |
| ----------------------- | -------- | ------------------------------------- |
| `~/.claude/skills/`     | personal | In every project; no restrictions     |
| `<cwd>/.claude/skills/` | project  | Only after the workspace trust dialog |

- Project-scope `@skills-dir` plugins: MCP servers go through per-server approval; LSP starts only after trust; background monitors do NOT load.
- Project-scope `@skills-dir` plugins load only from the `.claude/skills/` of the session's primary working directory — they do NOT walk up to repo root, so launching from a subdirectory misses a plugin at the repo root. Launch from repo root, or (version >= 2.1.246) move the session there with `/cd` — a plain shell `cd` does not change which directory is scanned.
- Live editing: a skill's `SKILL.md` takes effect immediately; other components (`hooks/`, `.mcp.json`, `agents/`, `output-styles/`) need `/reload-plugins` or restart.
- Stop loading: delete the folder or `claude plugin disable <name>@skills-dir` (no uninstall — nothing was installed).

## Symlink resolution

How a symlink inside a plugin dir is handled when copied to cache depends on where its target resolves:

| Target location                   | Handling                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------- |
| Within the plugin's own dir       | Preserved as a relative symlink (resolves to copied target)                   |
| Elsewhere in the same marketplace | Dereferenced — target content copied in (meta-plugin can link sibling skills) |
| Outside the marketplace           | Skipped (security)                                                            |

For `--plugin-dir`/local-path installs, only symlinks resolving within the plugin's own dir are preserved; all others skipped. Path traversal (`../shared-utils`) does not work post-install — external files are not copied.

## Node.js package dependencies

Separate from [plugin `dependencies`](#plugin-dependencies) (other plugins) — this is auto-install for a marketplace plugin's OWN `package.json` deps, into the cached copy, so its hooks/MCP servers can load them without a manual step. Runs on fresh install, on update to a new version, and at session start when an enabled plugin isn't cached yet (new machine).

| Lockfile present                            | Command                                          |
| ------------------------------------------- | ------------------------------------------------ |
| `bun.lock` / `bun.lockb`                    | `bun install --frozen-lockfile --ignore-scripts` |
| `npm-shrinkwrap.json` / `package-lock.json` | `npm ci --ignore-scripts`                        |

- Requires BOTH `package.json` and one of the above lockfiles at plugin root; first match wins in the listed order. `yarn.lock`/`pnpm-lock.yaml` are skipped (their resolution-time hooks bypass `--ignore-scripts`) — ship an npm lockfile for widest reach; for an `npm`-source plugin use `npm-shrinkwrap.json` (npm excludes `package-lock.json` from published packages).
- Frozen resolution (fails rather than re-resolve on a `package.json`/lockfile mismatch); no lifecycle scripts (native-module builds download but don't compile); 60 s timeout (a timeout can leave a partial `node_modules`). Not configurable — no setting/env var disables it.
- A failed/timed-out install never blocks the plugin; failure or a skipped yarn/pnpm lockfile logs a warning in `claude --debug` output (silent only when `package.json` has no lockfile at all).
- Fetching an `npm`-source plugin itself runs `npm install` WITH lifecycle scripts first, as a separate step before this `--ignore-scripts` dependency install.
- Deps this can't provide (lifecycle-script builds, Python, Yarn/pnpm-locked) — install from a hook into `${CLAUDE_PLUGIN_DATA}` instead (see the dependency-reinstall pattern under [Path variables](#path-variables)).

## Version resolution

Plugin version = cache key for update detection. Resolved from first set:

1. `version` in the plugin's `plugin.json`
2. `version` in the plugin's marketplace entry
3. git commit SHA of the plugin's source (for `github`/`url`/`git-subdir`/relative-path sources in a git-hosted marketplace) — every commit = new version
4. SHA-256 digest, truncated to 12 chars (for `archive` sources): the entry's `sha256` pin if set, else the digest of the downloaded file
5. `unknown` (for `npm` sources or local dirs not in a git repo)

- **`command` source** version is always derived from the command's output: a 12-character content hash alone, or `<version>-<hash>` when `plugin.json` sets `version`. The marketplace entry's `version` field is ignored for `command` sources. In link mode the hash covers the printed directory's real path and its top-level entries (not file contents). Any change in hashed output = new version, even with an unchanged `version` string.
- Explicit `version` pins: must bump on every release; pushing commits without bumping does nothing (cache kept, `/plugin update` reports already-latest). Avoid setting in BOTH `plugin.json` and marketplace entry — `plugin.json` wins silently. Auto-update is OFF by default for non-Anthropic marketplaces: users pick up a new version by enabling auto-update for that marketplace in `/plugin`, or running `claude plugin update <plugin>` (then `/reload-plugins` to install any newly added deps).
- A marketplace added from a local directory with a relative-path `source` loads plugin files in place: edits take effect at next session start or `/reload-plugins`, no `version` change needed. Marketplace-cached copies (hosted installs) update only per the rules above.
- Release channels: two marketplaces pointing at different `ref`/`sha` of the same repo, assigned to user groups via managed settings; each channel must resolve to a distinct version.

## Plugin hints

Lets a CLI/SDK prompt Claude Code users to install a plugin when the CLI detects it is running inside Claude Code. Only fires for plugins listed in `claude-plugins-official` or another marketplace with one of Anthropic's official marketplace names (the community marketplace `claude-community` is not one) (curated by Anthropic at its discretion; the in-app community submission form does NOT add a plugin there).

### Mechanism

1. CLI writes the hint tag to stderr on its own line (Claude Code scans both stdout and stderr; stderr recommended to keep it out of shell pipelines). Only Bash/PowerShell tool output triggers the prompt; in hook commands the tag is stripped and ignored.
2. Gate emission on an env var to avoid showing the hint to human users running the CLI directly. Emitting on every invocation is fine — Claude Code prompts once per plugin. Verify the emitter: `CLAUDECODE=1 <cli>` shows the tag line on stderr; `<cli>` without the variable prints nothing extra.
3. Claude Code scans + removes hint lines before output reaches the model (never counted toward tokens), checks the target is in its local copy of an official Anthropic marketplace, not already installed, not blocked by policy, not prompted before, then shows a one-time prompt naming the first word of the emitting shell command.
4. Yes → plugin installed to user scope. "No, and don't show plugin installation hints again" disables all future hint prompts. No-response within 30 s dismisses as No. One prompt per session (across all CLIs), one prompt ever per plugin regardless of the answer, none once 100 plugins have been prompted for on that machine, and only in the main interactive session the user is typing into — never for a command a subagent runs, and never in a `-p`/Agent-SDK session (the hint line is still stripped in both cases). Never on a cloud/remote workspace or unattended session (e.g. `--cloud`, Remote Control serving, an agent-team teammate). Sessions with telemetry disabled never prompt — `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, or a third-party provider (Amazon Bedrock, Google Cloud Agent Platform) where the automatic telemetry opt-out applies.

### Gate variables

| Variable                    | Set when                                                                                                                                                                                                 |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLAUDECODE`                | `1` in every Bash/PowerShell + hook subprocess, all CC versions. Also set in tmux + stdio-MCP subprocesses and IDE integrated terminals (a human may run your CLI there). Widest reach.                  |
| `CLAUDE_CODE_CHILD_SESSION` | `1` only in subprocesses CC itself spawns (tool calls, hooks, statusline). version >= 2.1.172. Avoids most human terminals; long-lived processes (tmux server) capture it. Older sessions miss the hint. |

### Marker format (BREAKING CHANGE — was `CLAUDE_PLUGIN_HINT: name@marketplace`)

Self-closing tag with three required attributes, on its own line:

```
<claude-code-hint v="1" type="plugin" value="example-cli@claude-plugins-official" />
```

| Attribute | Required | Description                                       |
| --------- | -------- | ------------------------------------------------- |
| `v`       | Yes      | Protocol version; `1` is the only supported value |
| `type`    | Yes      | Hint kind; `plugin` is the only supported value   |
| `value`   | Yes      | Plugin identifier in `name@marketplace` form      |

Example in Node.js:

```js
if (process.env.CLAUDECODE) {
  process.stderr.write('<claude-code-hint v="1" type="plugin" value="example-cli@claude-plugins-official" />\n');
}
```

- Attribute values may be double-quoted or unquoted (unquoted cannot contain whitespace); no escape sequences.
- Enforced (else dropped): tag must occupy its own line (leading/trailing whitespace OK; mid-line embedded tag ignored); `value` must reference an Anthropic-controlled marketplace (e.g. `claude-plugins-official`) — hints to other marketplaces silently dropped.
- The hint line is always removed before reaching the model, even for unrecognized `v`/`type`.

### Scope values

| Scope     | Settings file                 | Description                                                |
| --------- | ----------------------------- | ---------------------------------------------------------- |
| `user`    | `~/.claude/settings.json`     | Default. Personal; across all projects.                    |
| `project` | `.claude/settings.json`       | Team-shared via version control; requires workspace trust. |
| `local`   | `.claude/settings.local.json` | Local only; gitignored.                                    |
| `managed` | managed settings              | Managed plugins (read-only; update only).                  |

- A user-scope install in the terminal, the desktop app's local sessions, or the VS Code extension is available in all three on that computer (shared settings files). Project scope enables the plugin for everyone via committed `.claude/settings.json`, but each collaborator still installs it on their own machine. A cloud session (incl. claude.ai/code) does not load plugins from local settings.

### Session flags

- `claude --plugin-dir <path>` — load a plugin dir for this session only (no install). Accepts a `.zip` archive (version >= 2.1.128). When same-named as an installed plugin, the local copy wins for the session (except managed force-enable/disable). Repeat the flag for multiple.
- `claude --plugin-dir <folder>` — version >= 2.1.265: when `<folder>` itself has no manifest or plugin components at its top level, each immediate subfolder with a `.claude-plugin/plugin.json` loads as a separate plugin (everything else in the folder, including manifest-less subfolders, is skipped without error). In an interactive session Claude Code also watches the folder: adding/removing a subfolder loads/unloads its plugin live, or — when applying the change mid-conversation would invalidate the prompt cache — prints a line telling you to run `/reload-plugins`.
- `claude --plugin-url <url>` — fetch + load a plugin `.zip` from URL for this session only. Repeat the flag, or pass space-separated URLs as one quoted arg. A fetch failure or invalid archive surfaces as a plugin load error; the session still starts, without that plugin.
- `/reload-plugins` reloads plugins, skills, agents, hooks, plugin MCP + LSP servers without restart.

## Monitors

Background monitors watch logs/files/commands and deliver each stdout line to Claude as a notification; Claude Code starts each automatically when the plugin is active (`experimental.monitors`; version >= 2.1.105 — see [Version notes](#version-notes)). Same mechanism as the Monitor tool and shares its constraints: run only in interactive CLI sessions, unsandboxed at hook-level trust, skipped on hosts where the Monitor tool is unavailable (not run on Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry).

### monitors.json schema

Array of entries; declare inline via `experimental.monitors` (array) or load from a non-default path (relative path string).

| Field         | Required | Description                                                                                                                                                                |
| ------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | Yes      | Identifier unique within the plugin; prevents duplicate processes on plugin reload or repeat skill invocation                                                              |
| `command`     | Yes      | Shell command run as a persistent background process in the session working dir                                                                                            |
| `description` | Yes      | Short summary; shown in the task panel and notification summaries                                                                                                          |
| `when`        | No       | `"always"` (default) — starts at session start and on plugin reload. `"on-skill-invoke:<skill-name>"` — starts the first time the named skill in this plugin is dispatched |

- `command` substitutes `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}`, any `${ENV_VAR}`. Prefix with `cd "${CLAUDE_PLUGIN_ROOT}" &&` for a script that must run from the plugin's own dir.
- version >= 2.1.207: `command` may NOT reference `${user_config.*}` — it runs through a shell, so the monitor is rejected with an error instead. Monitor processes also receive no `CLAUDE_PLUGIN_OPTION_<KEY>` env vars; have the script read the value from a config file it owns. Earlier versions substituted.
- Disabling a plugin mid-session does not stop monitors already running; they stop when the session ends.
